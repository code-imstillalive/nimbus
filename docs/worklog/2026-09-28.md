## #1359 — golden snapshots as plain JSON (PR #1384, merged)

`GOLDEN_UPDATE=1` rewrote all 12 snapshots' bytes with not one recorded value
changed. `mtime=0` was already pinned; zlib's own output cannot be, and it
differs between builds — so regenerating on a different interpreter than the one
that recorded a snapshot rewrote every file, and spec 000's update rule ("the
diff goes in the PR") produced thirteen unreadable binary files.

**The issue offered content-addressed writes as sufficient and that was the
weaker half.** Storing them as text makes the invariant *expressible*, which it
was not before: gzip bytes legitimately differ per build, so no byte-level check
could ever have been written. As text there is one correct byte sequence per
record and a test can say so.

**The cost was measured, and the issue's own estimate was wrong in both
directions** — it guessed "2–3 MB expanded" (really 7.0 MB, 14 files by then)
and never considered where repository growth accumulates. Over 7 successive
one-value revisions of all 14 snapshots, in a scratch repo, gc'd:

| format | working tree | `.git` after 7 revisions |
|---|---:|---:|
| `.json.gz` | 0.25 MB | **0.92 MB** |
| `.json` | 7.19 MB | **0.25 MB** |

Text deltas across revisions; a gzip stream does not, so each revision stores a
whole new incompressible blob. Uncompressed costs 7 MB of working tree **once**
and is 3.7x cheaper in the history, which is the part that grows forever. The
`nemweb/` fixtures stay compressed: recorded *inputs*, never read as a diff.

`.gitattributes` gained `tests/golden/snapshots/** -text`, for exactly the reason
its existing comment gives about `schema/**` — without it git's eol conversion
rewrites them to CRLF in a Windows working tree, so the byte check fails on a
fresh clone while passing in Linux CI.

Verified by the defect itself: with the migration committed, `GOLDEN_UPDATE=1`
leaves `git status` completely empty. And that the new test catches what it
claims — a CRLF-converted snapshot fails 2 of its checks, a re-indented one
fails 1.

## #1358 — thermal golden scenarios (PR #1385, merged)

Two corrections the measurements forced, both worth more than the scenarios.

**1. The placement cannot be observed by running a later cycle.** I tried pinning
the LP's chosen periods with a second cycle 20 minutes in, expecting dispatch to
turn on once the clock reached the cheapest period. It does not — and the
expectation was wrong about the fixture, not the solver. **Period 0 always takes
the live price** from `sensor.fake_import_price`: the recorded series begins
`[0.30, 0.345, 0.325, …]` where the array's own first value is 0.365. The
fixture's live price is one static value, so at every cycle "now" costs 0.30
while later periods can be cheaper, a load with slack defers at every instant,
and no later cycle catches it starting.

Also measured: the household-load forecast these scenarios publish does **not**
include the controllable load's scheduled power (delta against baseline is 0.0 in
every period), so a cycle records nothing per-load except whether a dispatch call
was made.

So the placement is pinned the way the record can see it — **a pair differing
only in the price forecast**: one defers (no dispatch), one heats now
(`set_operation_mode`). Neither is worth much alone; the pair is the evidence, and
`test_the_two_scenarios_differ_only_in_price` keeps it that way.

**2. The first ladder tied with the live price.** A round 0.01 ladder had index 3
at exactly 0.30, which *is* the live price at index 0 — a tie in the solve for no
reason.

Coverage, re-measured on both sides by statement via AST (a different basis from
spec 000's "Lines" column, so the baseline was re-measured rather than compared
against that table):

|---|---:|---:|
| `build_controllable_loads` | 57/127 — 44.9% | **80/127 — 63.0%** |
| `apply_commanded_state_guard` | 145/251 — 57.8% | **153/251 — 61.0%** |

The 14 pre-existing snapshots were untouched — this issue's own acceptance

### A product gap found on the way — #1386

`Plan.thermal_guarantee_relaxed` is set by `solver/network.py` and read by
**nothing outside the test suite**. Not published, not logged, not notified. So a
household whose hot-water guarantee is silently relaxed is never told, and the
natural cause is a misconfiguration (`thermal_max_power_kw` too low, a window too
narrow, a drifted learned heating rate) which the retry absorbs every cycle
forever. #774's argument for making the bound hard covers the bound, not the
retry.

## #1360 — the instrumentation is not on the install that needs it

Went looking for the one check this issue says is available *before* a
recurrence — the healthy-cycle base rate, "the one most likely to kill the
leading hypothesis". It is still impossible, for a reason the issue does not
record.

`sensor.nimbus_solver_solve_seconds` on production carries 15 attributes and
**none** of `calibration_min_weight_fallback`, `calibration_fallback_reason`,
`calibration_weight_used`, `simplex_iterations` — absent entirely, not null. They
are unconditional `plan.*` reads in `publish_plan`'s `solve_diagnostics` on
`main`, so if the code were there the keys would be.

**Why, and it turns on the timezone:**

| event | UTC | AEST |
|---|---|---|
| `v0.94.426` tagged (`88a76c4`) | 00:40Z | 10:40 |
| production deployed | 06:10Z | **16:10** |
| **#1361 merged** (`799bbcb`, adds all four) | 10:57Z | **20:57** |

`git merge-base --is-ancestor 799bbcb v0.94.426` → false. The instrumentation
merged **4.8 hours after** production was deployed. So "What the next occurrence
will now record" describes `main`, not the running install — the next episode
records what 20 Sep recorded: a warning in a log thrown away on the next restart.

devhub cannot substitute: its own `sensor.nimbus_solver_solve_seconds_2` is
`unavailable` (only `restored`/`supported_features`), so it publishes no solve
metrics of its own; the healthy figure visible there is NUC1's mirrored row.

The deploy is the household's call and the command was handed over rather than
requested.

## #1355 — the reference install's recorder, and a trap that nearly caused a false alarm

Steps 1 and 3 done for 116KAT: the recorder excludes three entities and ten
globs, **none matching** `sensor.nimbus_solver_quality_report`, with 45-day
retention. Per day, seven days running: **3–4 recorded rows**, in a stable shape —
a carry-forward at local midnight, a provisional value, then the settled score at
06:00–06:06. Against Mark's 3 rows across five days. So the install-specific
conclusion holds, and now rests on the same quantity on both sides rather than on
the rolling `history` attribute, which is what #1248's ratchet truncates and a
different thing entirely.

Two independent corroborations appear in the rows: 26 Sep `06:05=unavailable →
06:06=81.85` (#1248's truncation event) and 25 Sep `06:02=21.11 → 11:35=68.85`
(#1214's hardcoded-SoC figure, then the repair).

**The trap.** My first attempt asked for five days in one request and got 3 rows
for the quality report, newest 24 Sep — which reads exactly like "the recorder
stopped four days ago." A **control entity** settled it:
`sensor.nimbus_solver_solve_seconds`, which changes every minute, returned 5,123
rows *also* ending 2026-09-24 11:21 AEST — exactly 24 hours after the window
start. HA's history API truncates a wide window at roughly five thousand rows and
returns the earliest, **with no indication that it did.** A 3-hour request showed
650 rows newest at the current minute.

Without the control I would have reported a four-day recorder outage on a live
install. Query day by day, and always include a high-cardinality control.

## #1357 — devhub has six controllable loads, so the scope note was wrong

This issue (mine) said *"The reference household and devhub have zero."* The
reference household's half is right — production reads
`n_controllable_loads=0` and no `controllable_load_delivery`. **devhub's half is
wrong:** its `nimbus_load` entry is `state: loaded` with six `controllable_load`
subentries, all actively scheduled, and 138 `nimbus_test_*` entities behind them.

Checked before proposing it as the instrument, because it is not self-evidently
safe: devhub's Nimbus reads production's *mirrored* sensors (which is why its
quality report reads 87.71 against production's 87.70 — same underlying data), so
the obvious question is whether its loads *dispatch* to mirrored entities, where a
write is proxied to the live install. They do not — all six targets are
devhub-local `nimbus_test_*` entities that do not exist on production, and none
carries the mirror's `unique_id` marker. That marker is a useful tell in itself:
mirrored rows expose `unique_id` as a state attribute, devhub's own do not.

Stated plainly all the same: devhub reads production's inputs, so it is not an
independent install and cannot catch anything depending on a configuration 116KAT
lacks — which for this change is most of what matters.
