## #1359 — golden snapshots as plain JSON (PR #1384, merged)

`GOLDEN_UPDATE=1` rewrote all 12 snapshots' bytes with not one recorded value
changed. `mtime=0` was already pinned; zlib's own output cannot be, and it
differs between builds — so regenerating on a different interpreter than the one
that recorded a snapshot rewrote every file, and spec 000's update rule ("the
diff goes in the PR") produced thirteen unreadable binary files.

**The issue offered content-addressed writes as sufficient and that was the
weaker half.** Storing them as text makes the invariant *expressible*, which it
was not before: gzip bytes legitimately differ per build, so no byte-level check
could ever have been written. As text there is one correct byte sequence per
record and a test can say so.

**The cost was measured, and the issue's own estimate was wrong in both
directions** — it guessed "2–3 MB expanded" (really 7.0 MB, 14 files by then)
and never considered where repository growth accumulates. Over 7 successive
one-value revisions of all 14 snapshots, in a scratch repo, gc'd:

| format | working tree | `.git` after 7 revisions |
|---|---:|---:|
| `.json.gz` | 0.25 MB | **0.92 MB** |
| `.json` | 7.19 MB | **0.25 MB** |

Text deltas across revisions; a gzip stream does not, so each revision stores a
whole new incompressible blob. Uncompressed costs 7 MB of working tree **once**
and is 3.7x cheaper in the history, which is the part that grows forever. The
`nemweb/` fixtures stay compressed: recorded *inputs*, never read as a diff.

`.gitattributes` gained `tests/golden/snapshots/** -text`, for exactly the reason
its existing comment gives about `schema/**` — without it git's eol conversion
rewrites them to CRLF in a Windows working tree, so the byte check fails on a
fresh clone while passing in Linux CI.

Verified by the defect itself: with the migration committed, `GOLDEN_UPDATE=1`
leaves `git status` completely empty. And that the new test catches what it
claims — a CRLF-converted snapshot fails 2 of its checks, a re-indented one
fails 1.

## #1388 and #1391 — #1357, the oracle can re-time Controllable Loads

Split the way Mark asked for on #768 itself: *"Build that first, land it as its
own change, then wire the LP plumbing as a second, smaller step."*

**Step 1 (#1388)** gave `compute_quality_report()` the capability, with `None` as
the default. **Step 2 (#1391)** built `build_oracle_controllable_loads()` and the
switch that gates it — `switch.nimbus_solver_score_controllable_loads_enabled`,
off by default.

**Off by default is the design, not caution.** This moves published EPR, and
#768's own thread records that the direction is not determinable from the code:
an `AdequacyLoadConfig` adds both the freedom to re-time *and* the obligation to
deliver, and those push opposite ways. A household has to be able to run the same
days both ways and compare, which a release that simply changed the number would
make impossible.

### The correctness point a naive implementation gets wrong

The subtraction goes into the oracle's own `loads=` argument **only**. Everything
above it that reads `load.forecast_kw` — `_widen_export_pin_to_achieved()` and
`_p2p_commitment_shortfall_kwh()` — describes what the **achieved** day did, and
the real house really drew that energy when it drew it. Reducing `load` once at
the top and letting it flow everywhere would rewrite history rather than model an
alternative to it. Three tests pin `j_ach`, `j_ref` and the P2P shortfall as
untouched.

### A finding I would have shipped wrong if a test had not failed

Clipping the reduced load at zero is necessary — a reconstruction can exceed the
measured house total in a period (#1231 records a 5–8% measurement-plane offset)
and a negative base load hands the oracle free energy.

**But clipping alone silently deflates EPR.** The clip removes at most what the
house drew, while the adequacy config re-introduces the reconstruction's full
figure, so the oracle serves *more* than the real house did and scores worse than
the day it is grading. Measured on the fixture: **12 kWh claimed, 4 kWh
removable, `j_star` rose from −0.851 to −0.439** — the oracle made worse by a
meter disagreement, not by anything about dispatch.

So the residue is published as `oracle_controllable_loads_unsubtracted_kwh`
rather than absorbed. A reason to distrust the day's EPR, not to adjust it — the
same posture `soc_discrepancy_power_coverage` takes. **The invariant test is the
only reason that is not shipped silently.**

Spec 003 step 2: `safe_num` (47 lines) moves verbatim from `solver_writer.py` to
`solver_shared.py`, with a facade re-export left behind.

The spec's caller analysis flags `safe_num` as facade-load-bearing and records **0
monkeypatch sites**. Both are true and neither is the problem.

**`safe_num` calls `ha_get`.** Once it lives in `solver_shared.py` it resolves `ha_get`
from *that* module's namespace -- and **60 test files patch `solver_writer.ha_get`**. A
facade fixes name resolution for the moved function's CALLERS. It does nothing for the
moved function's own dependency lookups. Every test that patched only the writer's alias
and reached `safe_num` let a real HTTP call escape and failed against a live Home
Assistant with `Connection refused`.

**My own analysis had the same hole.** I computed `safe_num`'s free names by intersecting
its reads with `solver_writer`'s module-level variables and sibling functions, and
**excluded imported names** -- `ha_get` is imported. I used the correct filter (including
imports) for the eight functions Stage B moves, and the wrong one here, which is why I
reported `safe_num` as "fully self-contained".

**And then I committed before the suite finished.** The commit message says so in its own
words: *"The full stub suite is still running locally and was at 0 failures when this was
committed."* It was at 36%. CI found **28 failures and 7 errors across six more test
files** that I had not found because I had not waited:

```
test_main_report_failures_never_break_the_solve.py          14 failed
test_solver_writer_smoothness_and_proximal_weight_wiring.py  8 failed
test_main_p2p_pin_binding_label.py                           3 failed
test_solver_push_attribute_size_budget.py                    7 errors
test_household_mode_presets.py                               1 failed
test_whole_house_live_load_diagnostic.py                     1 failed
```

Each now patches both targets -- the same fix Stage A had already applied to three files,
so the pattern was known and the only thing missing was running the suite to the end.
That is the whole lesson: 0 failures at 36% is not a result, and I reported it as one.

## Phase 3, Stage B -- eight functions into `solver_inputs/controllable_loads.py`

1,191 lines of bodies out of `solver_writer.py`, which goes **14,069 -> 12,853 lines**.
New module 1,305 lines.

**Proof the code is the same code, not merely equivalent.** Seven of the eight are
**byte-identical** to `origin/main` after stripping the inserted `sw.` /
`solver_shared.` prefixes and the `sw = _solver_writer()` binding. The eighth,
`_sample_load_run_state`, differs by exactly one line: `sw._NATIVE_HASS` is three
characters longer than `_NATIVE_HASS`, which pushed a `_Store(...)` call past 88 columns
and `ruff format` reflowed it. All eight are **AST-identical** after unqualifying, via
`ast.dump(include_attributes=False)`. Byte-for-byte before formatting, AST after -- the
claim the plan set out to make.

**Qualification was done over tokens, not with a regex.** `tokenize` gives STRING and
COMMENT their own token types, so a name inside a docstring can never be rewritten. These
bodies' own docstrings mention several of the qualified names, and a regex pass would
have corrupted the prose while looking like it worked.

### Two monkeypatch sites spec 003's caller table records as zero

Both real, both found by running rather than by reading.

- **`_sample_load_run_state`.** `test_solver_writer_thermal_load_resolution.py` replaces
  `solver_writer._sample_load_run_state` and then calls `build_controllable_loads`. Once
  both live in the new module, the callee reads the bare intra-module name, so patching
  the facade became a **silent no-op** -- exactly the #1316 failure mode
  `tests/gates/noop_patches.py` exists to catch. It surfaced as a real assertion failure
  only because that test checks a *learned* rate the module default does not produce. A
  test asserting something the default also satisfies would have gone green with zero
  coverage of the path it exists to check. Now patched on
  `solver_inputs.controllable_loads`.
- **`solver_writer._parse_done_when`.** Not in the spec at all. It was an import alias
  for `done_condition.parse_done_when`, used only by the eight moved bodies -- so when
  they left, the alias became unused and I removed it. Six tests read it. **Restored**,
  because spec 001's identity invariant is that every name in scope before a relocation
  still resolves after it. Worth recording *how* it went wrong twice: `ruff check --fix`
  offered to delete the restored import as unused and I let it, which silently undid the
  fix in the `except ImportError` branch only -- so it looked restored and still failed.

`_resolve_controllable_load_tuning` is patched on `solver_writer` by
`test_commanded_state_guard_reports_its_own_failure.py` and **still works**, because
`apply_commanded_state_guard` stays in `solver_writer` and reads the module global there.
Checked rather than assumed.
