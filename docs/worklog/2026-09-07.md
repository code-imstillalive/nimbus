## #484 — relay-chatter guard, decision layer only

Sub-issue 8/10 of #476, built directly on #479's store. The real motivation
(Mark's own HAEO incident, quoted above) is exactly what this closes: every
solve now computes each Controllable Load's raw on/off decision from its own
just-solved period-0 scheduled power and persists a DEBOUNCED
`commanded_state`/`commanded_since` — deliberately separate from #479's own
`currently_on`/`on_since`/`off_since`, which track the load's real MEASURED
power, not what the Solver last commanded.

Getting the debounce semantics right took a real design correction mid-pass.
First attempt: adopt a disagreeing raw value once `min_hysteresis_seconds`
had elapsed since the *last real change* — a rate limit, not a debounce.
Traced through #484's own acceptance scenario by hand (ten solves,
raw decision alternating every single tick) and found it would still produce
~5 real published changes over a 50-minute/10-min-hysteresis window, nowhere
near the required "≤ 1 change." Root cause: elapsed-since-last-change has no
memory of whether the CURRENT challenge has been consistent — it just lets a
new flip through once enough wall-clock time has passed, whatever the raw
signal has been doing in between. Rebuilt as a real debounce instead:
`pending_state`/`pending_since` track how long the CURRENT disagreeing value
has held *consecutively*; a raw value that reverts to agreeing with
`commanded_state` even once clears the whole challenge, not just pauses it.
Traced through the alternating-decision scenario again by hand: every "high"
tick starts a fresh challenge that the very next "low" tick immediately
clears, so the challenge NEVER reaches the 2-period threshold — zero real
published changes across all ten solves, not "one every hysteresis window."
This is the correct reading of "stays commanded on for at least
`min_on_periods`... regardless of the 5-minute re-solve" — a settling
requirement, not a rate limit.

To make the mapping from a solved plan entry back to its real per-load
run-state store entry possible at all, `SheddableLoadConfig`/
`AdequacyLoadConfig` (`elements.py`) and `SheddableLoadPlan`/
`AdequacyLoadPlan` (`network.py`) each gained an optional `subentry_id`
field, propagated straight through network.py's existing plan-construction
comprehensions — `name` alone was never reliably unique
(`build_controllable_loads()` falls back to `subentry_id` AS `name` only
when no real name is configured).

Scoped the same honest way as #479/#486: the guarded decision itself is real
and persisted every solve, but nothing publishes it as an HA sensor yet
(#465's own sub-device pattern, still the real documented gap) — so there is
still no automation this can actually drive today. The rest of #484's own
spec (`scheduled_kw`/`actual_kw`/`tracking_fidelity_24h`/
`tracking_error_cost_24h`/the plain-language status sensor/
`delivered_today_kwh` vs `target_today_kwh` display) is deferred to the same
follow-up that builds the sensor platform — building the analytics layer
before there's anywhere to show it would mean building it twice.

19 new tests (8 for `decide_commanded_state()`'s own pure logic including
the exact acceptance scenario, 3 for the real `solver_writer.py` wiring
running the same scenario end to end). Checked again for the exact
leaked-event-loop bug class #479 had already caught once — clean.

Not released/tagged — foundation-only, same reasoning as #477/#486/#479.

## Dashboard: chart/table layout saga (v0.94.144 → v0.94.150)
Direct household ask, from an annotated screenshot: chart-left-2/3 + table-right-1/3,
side by side, narrower TIME/SOURCE columns, taller chart. Landed across several releases,
each genuinely shipped and CI-verified, but reported still broken on the actual page after
every one — "TABLE STILL SCROLLING - SOURCE STILL NOT FIXED, PLAN STILL NOT FULL HEIGHT -
EMBARRASING", then still broken after a full browser restart and a fresh incognito window.

Every environment theory was tested and ruled out directly: browser disk cache (ruled out
by curl on NUC1 confirming the exact newest CSS markers were being served, and a DevTools
Network capture showing genuine fresh 200 fetches, not disk-cache hits), the HA frontend
service worker, custom-element redefinition surviving across reloads (ruled out by a full
app restart + a separate incognito test, both still broken).

**Root cause, found by re-reading the actual CSS rather than guessing another pixel value**:
the 2/3+1/3 split used a fixed CSS grid fraction (`2fr 1fr`) gated by a hand-computed
`@container` breakpoint (1708px, derived from `--ftable-min-width * 3 + gap`). This is the
same failure class as #391/#395/#400/#407 (three earlier breakpoint mismatches this project
already hit) — giving the table column a fixed *fraction* of the row caps its width
regardless of what the table's real content needs, so no hand-picked breakpoint can stay
correct once anything about the table's own real minimum width shifts (row padding, font
size, a header's own text width). Three same-day tweaks to bar width, `--ftable-min-width`,
and the SOURCE header's own font/letter-spacing all genuinely reduced the table's real
minimum width, but none of them could reliably close the gap against an independently-fixed
1/3 share of the row.

**v0.94.150 fix**: replaced the grid+breakpoint with flexbox (`table-col: flex:0 0 auto`,
`chart-col: flex:1 1 480px`). Confirmed live: killed the scrollbar but broke the intended
2/3:1/3 ratio — table's own content width turned out comparable to the chart's, so
flex-grow left chart-col only about half. **v0.94.151** tried CSS Grid with
`minmax(max-content,1fr)` instead — confirmed live this let the table's real content
(~1450px on a P2P-heavy render) dominate the row, squeezing the chart to a sliver on
devhub and forcing full stacking on a narrower real card width. **v0.94.152** tried
`grid-template-columns: minmax(320px,1fr) max-content` (chart gets everything left over
after table claims exactly its own content, the mathematically maximal chart size) —
confirmed live this was *worse*: tiny chart AND a horizontal scrollbar reappeared, since
the table's real content on that render nearly filled the whole row.

**Real fix, v0.94.153**, after a direct household correction ("why won't you design
containers for these items first — 2/3 and 1/3 of width — and then place objects in
them"): stopped trying to size either box to its own content at all. `grid-template-
columns: 2fr 1fr` with `min-width: 0` explicitly set on both columns (overriding CSS
Grid's own default auto-min-size, which is otherwise each item's max-content width and
would silently override the fr split the moment either side's content exceeds its own
fraction — the actual mechanism behind all three prior failures). chart-col is now always
exactly 2/3 of the row, table-col always exactly 1/3, regardless of content; if the
table's real content is wider than its 1/3 box, `.ftable-wrap`'s own `overflow-x:auto`
scrolls within that box only, never crushing the chart or widening the row. **Confirmed
working live** on the next screenshot.

**v0.94.154**: two final small, bounded tweaks on top of the now-working layout — SOURCE
column padding 4px→2px (bar width/font explicitly untouched), and the chart now stretches
vertically to fill table-col's own row-driven height (`.chart-col` flex-column under the
grid's `align-items:stretch`, `.timeline-wrap` `flex:1`, SVG `preserveAspectRatio`
changed from `xMidYMid meet` to `none` so it actually stretches rather than letterboxing).
Not yet re-confirmed live as of this entry (shipped to devhub only, household going to
bed) — check on next session.

Also (earlier in the saga): dispatch-plan chart clipped to 3 days / 72h instead of the
full 96h forecast (chart-only), and the chart's own SVG `viewBox` height raised 220 → 275
(+25%) per direct request.

**Lesson, stated plainly for next time**: every failed attempt was reasoned from an
*estimated* table content width, never a real DevTools measurement. The household's own
correction (fixed containers, not content-aware sizing) was the right call — simpler,
predictable, and the only approach that actually held up across renders with genuinely
different row content.
