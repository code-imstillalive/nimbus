## #937 stage 3 — the metric the issue is about now exists on every install

[PR #1307.] #937 measured naive persistence beating the ML load forecaster on 11
of 14 days (mean **-$0.71/day**) and named its own top action: *"more days."*

consumes it. Eleven attributes, including the three **attribution** terms (load

because *"#937 assumes the load forecaster is the dominant term and nobody has
checked."* All five extra scenarios were already being computed and discarded, so
publishing them costs nothing the LP was not already paying.

16,384-byte cap, taking the projected remainder at full retention from ~49% to
~52%.

Deliberately "Part of", not "Fixes": the issue wants more *days*, and days come
from time. This removes the reason there were none.

## Two measurement tools, because two report errors kept recurring

[PRs #1315 and #1316.] `tests/analyse_module_dependencies.py`.

**Dependency mode** answers what an extraction costs. Phase 2 of #1298:
**3,115 lines, 65 blocking dependencies**, and two things that were not obvious
before measuring — `_compute_report_for_window` belongs **last** (1,280 lines, 31
blockers, and it calls nine of the other seven's helpers), and the most-shared
blockers are recorder-access and config-resolution helpers, which are not
reporting concerns and so do not belong in `solver_reports/`. That is a
prerequisite PR, not part of the reporting move.

**Caller mode** answers Mark's #1298 question — whether the compatibility façade
requirement should stand — and the phases disagree:

```
--callers --phase 2   2 production callers, 11 monkeypatch sites  -> facade IS load-bearing
--callers --phase 3   0 and 0                                     -> facade preserves nothing
--callers --phase 6   0 and 0                                     -> same
```

Phase 2's two callers are `services.py`'s `compute_quality_report` and
`rescore_history` handlers — a documented public surface, not an unused internal
one. And `services.py` resolves them as **module attributes at call time**, so a
re-export preserves both the handlers and all 11 monkeypatch sites. Migrating the
caller instead would make those patches land on an attribute nobody reads: the
tests would pass having exercised the real scorer. Green CI, no coverage.

So the criterion worth recording is not *"is a façade required"* but **"does
anything outside the module resolve this name at call time"**, which each phase
can now answer for itself.

## #1290 — earning the carve-out the fix shipped without

[PR #1317, open.] Reading `docs/release-process.md` before cutting a tag stopped
the tag.

#1290 changes how an all-day calendar event is read — UTC midnight to LOCAL
midnight — which moves an EV departure deadline by the whole UTC offset, ten
hours here. That is the one category the policy holds overnight. There is a
carve-out for a change that cannot affect an install which has not opted in, but
it requires *a test in the same PR demonstrating that*, and says explicitly that
asserting it in the PR description does not qualify.

**#1312 shipped it without that test.** The gating is real — one caller, behind a
trip-calendar guard — but "the gating is real" is exactly the claim the policy
rejects. #1317 closes the gap.

**The positive control is the part worth keeping.** A test asserting an opted-in
participant *does* reach the call, because without it "never called" is vacuous.
It failed twice for two different real reasons: the fixture lacked a SoC sensor
(participant skipped before the guard, with a warning nobody would have read) and
the stub lacked `safe_num` (raised before the guard). Both would have left the
negative tests green while proving nothing.

It also replaced a first draft of that file whose "behavioural" half asserted
that a fixture lacking a key lacks it, and that `bool("")` is `False` — testing
Python, not this codebase, while its docstring claimed to count real calls.

## Spec 001 (solver_shared.py, Phase 2a) — merged, plus a design decision peer
## review caught wrong on first draft

Docs only, `docs/specs/001-solver-shared-ha-io-core.md` (PR #1347, squash
`373a8f1`) — the "2a" prerequisite #1301's own thread flagged as needing a
decision before Phase 2 proper (moving 8 reporting functions out of
`solver_writer.py`) can start. `solver_shared.py` gets a home for the ~19
non-reporting names those 8 functions and `solver_inputs/*.py` both depend
on (`ha_get`, `ha_post_state`, `_cfg_num`, `_LOGGER`, etc.), in a new layer
below `solver_inputs`/`solver_reports`. Every name in scope keeps a re-export
in `solver_writer.py` (the façade criterion) given the monkeypatch scale —
`ha_get` alone has 48 sites, `ha_post_state` 29+.

**First draft got `_LOGGER` backwards, but named the right question.** It
proposed keeping `solver_writer.py`'s own independently-created `_LOGGER`,
separate from `solver_shared`'s, reasoning that a test might assert on the
logger's name string — and its own Migration step 3 asked a reviewer to grep
the suite for exactly that before assuming it was safe. The draft picked the
wrong side of the risk it identified; the check it asked for is what caught
it. A concurrent peer session reviewing the PR ran that check: zero tests
assert by name string, but four suites (`test_solver_inputs_solar.py`,
`test_solver_writer_battery_participants.py`, `test_solar_source_shape_and_dedup.py`,
`test_quality_report_achieved_energy_and_reliability.py`) assert via
`assertLogs(solver_writer._LOGGER, ...)` on the object itself, to capture log
lines from the very `solver_inputs/*.py` modules this spec repoints onto
`solver_shared`'s logger. Since `assertLogs` on a Logger object only captures
records through that exact object (logging's hierarchy propagates by dotted
name, and `nimbus_load.solver_writer`/`nimbus_load.solver_shared` are siblings,
not ancestor/descendant), keeping them separate would have broken those four
suites — the opposite of the original reasoning. Verified independently
(`test_solver_inputs_solar.py:144`'s own `assertLogs` call, plus a repo-wide
grep for name-string-scoped loggers returning zero hits) before accepting it.
Fixed: `_LOGGER` is now a genuine alias like every other name in scope.

Same review also caught a real bug in `tests/analyse_module_dependencies.py`'s
`--callers` mode (fixed separately in #1348, merged): it over-counted bare name
references without checking they resolved to `solver_writer`, inflating
`_LOGGER`'s production-caller count from a true 6 to a reported 19. The
corrected 6 are, name for name, six of the seven `solver_inputs/* ->
solver_writer` layer violations #1338's `nimbus-layers` import-linter contract
already tracks as `ignore_imports` exceptions — a stronger case for the façade
than the original 19 suggested, and now a checkable Acceptance item: Phase 2a
retires those six exceptions (the six modules import `_LOGGER` from
`solver_shared` instead of reaching into `solver_writer`), leaving one.

**Along the way, PR #1347's own CI hit the #1330/#1331 flake live** — a docs-only
PR failing `test_main_golden_output_guardrail.py` on `forecast[1]['shadow_price']
= 0.2999` against the pinned `0.3`. A fix (#1332, from the same peer session)
already existed and was green (8/8): every one of `solver_writer`'s four
persisted state paths, not just the one instance already patched around, now
gets redirected into a per-test `tempfile.TemporaryDirectory()`, enforced by a
new AST-based guard test so a fifth main()-driving test can't reintroduce the
old `/tmp/nonexistent_*.json` convention. Reviewed and merged (squash `37189e0`),
which closed #1330 and #1331; merged `main` into the spec branch to pick it up
rather than gamble on a lucky re-run, and #1347 went green and merged clean.
The peer's own root-cause story ("stale runner state carries over between CI
jobs") did not survive a second look — GitHub-hosted runners are ephemeral and
`/tmp` starts empty — and was retracted in the same thread rather than left
standing; the fix does not depend on which mechanism actually produced the
collision, and #1332 covers it either way.

**Left genuinely open, not just fixed: why #1330/#1331 reached CI at all.**
Every job runs on a fresh `ubuntu-latest` runner (`/tmp` starts empty), there's
no `-n`/xdist, the second pytest invocation is scoped to `tests/hass_integration/`
and never collects the guardrail, and the literal path string
`/tmp/nonexistent_plan_state_golden_test.json` has exactly one writer in the
tree (the guardrail itself, after its own assertion). None of that explains how
the file existed when the assertion ran. One candidate, offered unverified by
the same peer: #1329's double-import hazard (`pythonpath = ["custom_components/
nimbus_load", "tests"]` letting a module exist twice) — five test files import
`test_main_golden_output_guardrail` by bare name, which could in principle
drive `main()` against that path more than once in a session, though #1337
deliberately didn't qualify those five imports because none writes
`sys.modules`. #1332 removes the shared path either way, so this doesn't block
anything — but "fixed" here means "cannot recur," not "understood," and it's
worth not letting that distinction blur the next time this file is read cold.

An implementation agent picked up Phase 2a itself once the spec settled,
carried through both corrections mid-flight via `SendMessage`; verification of
