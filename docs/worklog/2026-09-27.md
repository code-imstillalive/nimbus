## Two measurement tools, because two report errors kept recurring

[PRs #1315 and #1316.] `tests/analyse_module_dependencies.py`.

**Dependency mode** answers what an extraction costs. Phase 2 of #1298:
**3,115 lines, 65 blocking dependencies**, and two things that were not obvious
before measuring — `_compute_report_for_window` belongs **last** (1,280 lines, 31
blockers, and it calls nine of the other seven's helpers), and the most-shared
blockers are recorder-access and config-resolution helpers, which are not
reporting concerns and so do not belong in `solver_reports/`. That is a
prerequisite PR, not part of the reporting move.

**Caller mode** answers Mark's #1298 question — whether the compatibility façade
requirement should stand — and the phases disagree:

```
--callers --phase 2   2 production callers, 11 monkeypatch sites  -> facade IS load-bearing
--callers --phase 3   0 and 0                                     -> facade preserves nothing
--callers --phase 6   0 and 0                                     -> same
```

Phase 2's two callers are `services.py`'s `compute_quality_report` and
`rescore_history` handlers — a documented public surface, not an unused internal
one. And `services.py` resolves them as **module attributes at call time**, so a
re-export preserves both the handlers and all 11 monkeypatch sites. Migrating the
caller instead would make those patches land on an attribute nobody reads: the
tests would pass having exercised the real scorer. Green CI, no coverage.

So the criterion worth recording is not *"is a façade required"* but **"does
anything outside the module resolve this name at call time"**, which each phase
can now answer for itself.

### v0.94.426, cut for a reason that arrived at 04:45

The household's NUC1 backup failed overnight: aborted after 24 seconds having
written ~20 MB. Production's own error log named it exactly, so no inference was
needed:

```
FileNotFoundError: [Errno 2] No such file or directory: '/config/nimbus_solver_writer.lock'
  securetar/__init__.py  _atomic_contents_add -> tar_file.add(...)
  tarfile.py             add -> gettarinfo -> os.lstat(name)
```

`securetar` enumerates `/config`, then `os.lstat()`s each entry it found. The
solver released its lock and **deleted** the file between those two steps. One
missing entry aborts the whole archive.

**The property that matters is deletion, not writing** — an overwritten file still
exists when `lstat()` reaches it. That is what decided the scope: of four
persisted paths, only the two the solver *unlinks* moved to a temp dir. The lock,
and the load-forecast-error sentinel, which is the same race at lower frequency
and would have survived a lock-only fix. The two JSON state files stayed: plain
overwrites, never unlinked, and real state a restore must bring back.

The temp filename carries a per-install hash of the config dir. `/config` is
per-install but a temp dir is shared, so without it two HA instances on one host
would collide on a lock whose entire job is keeping them apart — a worse bug than
the one being fixed.

Not disk: the node reported 30% used and 613 GB free.

#1324 / PR #1325, then **v0.94.426**. So "no tag was cut" lasted a few hours, and

### #496 — the flag that already existed was the wrong flag

`grid_import_headroom_kw` read 0.0 for five hours while export reached 19.069 kW.
Plausibly correct — headroom is bound ranging, and a pinned variable has zero width
— but nothing published could confirm it, because `_headroom_up()` returns 0.0 both
when ranging says zero width and when there is no entry at all.

The obvious fix is `Headroom.degenerate`: it exists, it is computed, and
`LoadSignals.degenerate[t]` already publishes it. **The first attempt did exactly
that and its own tests rejected it.** `_headroom_from()` sets it when *either* side
is zero-width — right for `LoadSignals`, which builds its band from both sides;
wrong for `GridSignals`, which publishes only the up side and whose variables
routinely rest at their lower bound with `down_raw == 0`. It would have read True
for both export's 19.069 and import's 0.0.

The clamped case needs no flag at all: anything below 1e-9 becomes exactly 0.0, so a
published 0.0 already says "zero ranging width". Only the missing-entry case is
invisible. So the field is `unranged`, and the rejected reasoning is pinned in
`TestDegenerateIsTheWrongFlagHere` rather than left to be rediscovered.

## Spec 001 (solver_shared.py, Phase 2a) — merged, plus a design decision peer review caught wrong on first draft

Docs only, `docs/specs/001-solver-shared-ha-io-core.md` (PR #1347, squash
`373a8f1`) — the "2a" prerequisite #1301's own thread flagged as needing a
decision before Phase 2 proper (moving 8 reporting functions out of
`solver_writer.py`) can start. `solver_shared.py` gets a home for the ~19
non-reporting names those 8 functions and `solver_inputs/*.py` both depend
on (`ha_get`, `ha_post_state`, `_cfg_num`, `_LOGGER`, etc.), in a new layer
below `solver_inputs`/`solver_reports`. Every name in scope keeps a re-export
in `solver_writer.py` (the façade criterion) given the monkeypatch scale —
`ha_get` alone has 48 sites, `ha_post_state` 29+.

**First draft got `_LOGGER` backwards, but named the right question.** It
proposed keeping `solver_writer.py`'s own independently-created `_LOGGER`,
separate from `solver_shared`'s, reasoning that a test might assert on the
logger's name string — and its own Migration step 3 asked a reviewer to grep
the suite for exactly that before assuming it was safe. The draft picked the
wrong side of the risk it identified; the check it asked for is what caught
it. A concurrent peer session reviewing the PR ran that check: zero tests
assert by name string, but four suites (`test_solver_inputs_solar.py`,
`test_solver_writer_battery_participants.py`, `test_solar_source_shape_and_dedup.py`,
`test_quality_report_achieved_energy_and_reliability.py`) assert via
`assertLogs(solver_writer._LOGGER, ...)` on the object itself, to capture log
lines from the very `solver_inputs/*.py` modules this spec repoints onto
`solver_shared`'s logger. Since `assertLogs` on a Logger object only captures
records through that exact object (logging's hierarchy propagates by dotted
name, and `nimbus_load.solver_writer`/`nimbus_load.solver_shared` are siblings,
not ancestor/descendant), keeping them separate would have broken those four
suites — the opposite of the original reasoning. Verified independently
(`test_solver_inputs_solar.py:144`'s own `assertLogs` call, plus a repo-wide
grep for name-string-scoped loggers returning zero hits) before accepting it.
Fixed: `_LOGGER` is now a genuine alias like every other name in scope.

Same review also caught a real bug in `tests/analyse_module_dependencies.py`'s
`--callers` mode (fixed separately in #1348, merged): it over-counted bare name
references without checking they resolved to `solver_writer`, inflating
`_LOGGER`'s production-caller count from a true 6 to a reported 19. The
corrected 6 are, name for name, six of the seven `solver_inputs/* ->
solver_writer` layer violations #1338's `nimbus-layers` import-linter contract
already tracks as `ignore_imports` exceptions — a stronger case for the façade
than the original 19 suggested, and now a checkable Acceptance item: Phase 2a
retires those six exceptions (the six modules import `_LOGGER` from
`solver_shared` instead of reaching into `solver_writer`), leaving one.

## #1314 decided, and #485's schedule half finally built

`select.nimbus_household_mode` has changed dispatch since v0.94.315, but only
through the **quantity and value** levers — `deferrable_target_kwh`,
`deferrable_value_per_kwh`, `deferrable_shortfall_price`,
`controllable_load_max_activations_per_day`, `solver_degradation_cost_per_kwh`.
#485's own acceptance criterion 1 asks `away` to *"drop the HWS deadline spike,
pool heater band, and reduce the pump target to the maintenance quota"*. Two of
those three were shipped. The band was not, and **a multiplier cannot express
it** — which is exactly why #1314 was split out rather than left as a partly-met
criterion inside a closed issue.

### The decision: option 2 for the band, option 3 for the clock levers

@purcell-lab had already confirmed (2)+(3) on the issue, so this is a
ratification and an implementation, not a fresh call. What the implementation
added was the *reasons*, read out of the code rather than reasoned about:

- **`ThermalLoadConfig.__post_init__` raises `ValueError`** when
  `comfort_floor_c > target_temperature_c`, or when the target exceeds
  `max_temperature_c`. `build_controllable_loads()` constructs it with **no
  `try` around the call**. So a band preset that broke either ordering does not
  degrade one load — it aborts the entire solve, battery and every other load
  with it, over one temperature. That is the single strongest argument for
  keeping the band in its own table with its own ordering repair, and it was not
  visible from the issue text.
- **`build_controllable_loads()` already `continue`s** — silently drops a load
  out of the plan for that cycle, warning only — whenever a resolved
  `deadline_period` lands before its `earliest_period`. So an *hour* preset
  could remove a real load from a real plan with nothing but a log line. That is
  a structurally different failure from scaling a price, which the LP absorbs,
  and it is the code-level reason (3) is right for `deadline`/`allowed`.
- **`enabled` is not a decision at all.** There is no `enabled` field on any
  controllable load. #485's spec named one before the schema existed. Same for
  `quota_kwh_per_day`: `CONTROLLABLE_LOAD_KIND_QUOTA` is reserved in `const.py`
  and not selectable, so there is no configured lever for a preset to reach.

The one place the implementation departs from a literal reading of (2) is that
it keeps #1314 **option 1's** good property without its mechanism:
`THERMAL_BAND_PRESETS` is a separate, named table so *"the diff between 'scale a
number' and 'change a constraint' stays visible at the table, not buried in a
float"*. Same `_apply()` machinery, no new operations.

### Degrees, not factors — and the width is what is preserved

A multiplier on a Celsius setpoint has no physical meaning: 0.9 × 55 °C is an
arbitrary 5.5 °C, not "10% less heat". So every band entry is a `DELTA` in
degrees on the household's own configured setpoint — still relative, same
correctness property the rest of the module has.

`away` translates the whole band down 5 °C, `guests` up 2 °C. Translating rather
than scaling each end independently means the band's **width** is preserved and
the floor structurally cannot cross the target; `_repair_thermal_band()` is the
backstop for a future entry that moves only one end, not the mechanism.

`economy` moves the **floor only**, never the deadline target. A cost mode may
decline to pay for a mid-day reheat; it must not quietly deliver a colder tank
than the household asked for. That asymmetry is otherwise invisible, so it has
its own test.

Worth writing down before anyone retunes the `away` delta: on a domestic tank a
setback has a real legionella dimension, and this module cannot tell a hot-water
tank from a pool. −5 °C off a household's own 60 °C is a 55 °C tank, chosen to
stay inside the range a real install already runs.

### What is verified, and what is honestly not

Verified against the real LP, not just the table: `away` schedules strictly less
thermal energy than `home`, `guests` strictly more, both `optimal`, both with
`Plan.thermal_guarantee_relaxed == []` — so the hard constraint is still hard in
every mode. Every mode across 32 baseline band shapes builds a valid
`ThermalLoadConfig` rather than raising. And `home`'s LP arrays (`power_kw`,
`temperature_c`) are element-wise **identical** to an unmoded solve, which is
#485's second acceptance criterion demonstrated rather than asserted.

Not verified: devhub. No devhub access in this session, and the honest marker for
this change is a per-load DEBUG line inside a real native solve. Stated as "not
claimed, because X" per the release-validation directive rather than dressed up.

**One real upgrade note.** An install already sitting in `away`, `guests` or
`economy` *and* running a thermal load will see its band move on the first solve
after this ships, with no further action. The reference household reads `home` —
checked read-only through the REST API at 16:10 AEST today, not recalled — so it
is unaffected, and `home` remains the identity transform for everyone else.

### The mechanism: `select.nimbus_solver_load_forecast_source_policy`

Four options, default `off`:

- `off` — reads no evidence at all. The short-circuit is *before* the record is
  consulted, which is why `days_scored` comes back 0 rather than 14, and why
  "off is a no-op" is a property with a test rather than a default with a
  comment.
- `measure` — compute and publish the recommendation, keep using the ML
  forecast. The position this issue has effectively been in for two weeks,
  except deliberate and visible.
- `blend` — persistence weight = **the fraction of trailing scored days
  persistence won**. On #937's own series that is exactly 11/14. Deliberately
  not a dial: a dial invites picking the number that produces a liked answer,
  and no measurement supports any particular value.
- `persistence` — weight 1.0.

Four gates sit before any policy acts, each with its own reason code: no
trailing record; fewer than 7 scored days in the 14-day window; mean value-add
at or above -$0.10/day; and `measure`, which passes every gate and still does
not act. The 7-day floor is #937's own caveat about its own sample, not an
arbitrary number — rows are legitimately sparse and a mean over two rows is a
verdict about two days. The 10c threshold is measured against the issue's own
spread: three of its days sit inside +-$0.10 while the losses it exists to catch
are -$0.71 mean and -$3.42 worst, so it screens out a forecaster merely
*indistinguishable* from persistence while leaving 7x headroom to the real
signal.

The trailing window is **calendar-based, not most-recent-N rows**. Sparse rows
mean most-recent-14 can reach back two months and present a stale verdict as
current; a calendar window thins the sample instead, `days_scored` says so, and
the minimum-days gate refuses to act on it.

### Where it touches the live dispatch path, and how the position was chosen

`build_load_arrays()` in `solver_inputs/load.py`, in exactly one place, between
two existing landmines:

- **after** `summed_18_now_kw = load_kw[0]`, so the forecast-vs-forecast
  cross-check diagnostic keeps comparing the two genuine forecasts it was built
  to compare (#100/#429) instead of silently becoming blend-vs-forecast;
- **before** the live period-0 anchor, so a real measured meter reading still
  wins period 0 whatever the policy says. Persistence has nothing useful to add
  about the instant a meter is currently reporting.

The uncertainty band moves with the central array by the same weight, treating
persistence as a point value — a naive baseline carries no uncertainty
quantification, so at weight 1.0 the band correctly collapses onto it. Blending
the centre alone would leave `lower <= central <= upper` intact only by luck,
and the stochastic LP reads all three.

Persistence itself is seasonal-naive at a 24 h lag off
`solver_whole_house_cross_check_sensor` — the same entity
`_compute_report_for_window()` already resolves as "the real household load" for
the day-ahead scorer, so the policy acts on the *same* baseline the -$0.71/day
was measured against rather than a near-relative of it. One 24-hour recorder
read serves any horizon: a single shifted lookup grid (`gt - k*24h`,
`k = max(1, ceil((gt - now)/24h))`) is resampled once rather than resampling per
lag, and the read is cached per hour so a 1-minute cadence does one read an hour
rather than sixty. None of that runs at all under `off`.

An unconfigured cross-check sensor, an empty recorder read, or an all-zero
baseline each refuse with `persistence_baseline_unavailable` and keep the ML
forecast, logged at WARNING with the evidence intact — so *"I set the policy and
nothing changed"* is answerable from the published attributes alone.

### Published

Seven new scalars on `sensor.nimbus_solver_battery_forecast`, beside
`load_forecast_source_used` (which says which *sensors* the forecast was read
from — a different question; the two together are the whole provenance of the
load array): `load_forecast_source_policy`, `load_forecast_source_selected`,
`load_forecast_persistence_weight`, `load_forecast_source_reason`,
`load_forecast_source_days_scored`,
`load_forecast_source_days_persistence_won`,
`load_forecast_source_mean_value_add_dollars`. Always all seven, always present,
None together on a caller that supplies no decision — #589.

### Deliberately not done

**Not ported to the standalone/cron writer.** Every mechanism is portable — the
policy arrives on `sensor.nimbus_solver_config` which that copy already reads
over REST, `ha_get` reads the record, `fetch_entity_history_range` +
`resample_history_mean` both have REST paths — so calling it native-only would be
untrue, and it goes into the drift guard's `KNOWN_OPEN_DRIFT` list with that
stated. What makes it defensible to defer: the drift is **inert**, because an
unported install reads no policy and dispatches on exactly the array it
dispatches on today. That is a materially different situation from the #370
zero-load-fallback case the list was created for, where the unported side was
actively producing wrong plans.

**No automatic enablement, and no recommendation to enable it.** The evidence is
14 days from one install, and the issue itself says *"One household. The
forecaster trains per-install, so this may not generalise at all."* The honest
sequence is: let `"f"` accumulate on production and devhub, then set `measure`
and read what it recommends for a week, then decide. Deploying to production is
the household's own call, and the P2P window rules apply.

**The -$0.71/day is not re-measured here.** It cannot be: the series ended
2026-09-12 and restarts from zero. Nothing in this change claims otherwise.

## #1259 — the nowcast decay was NOT built; the measurement that settles it was

Picked up ~18:40 AEST with an instruction to "implement what the issue asks
for" — two mechanisms: a short-horizon nowcast decay blending `solar_kw[0]`'s
live anchor forward into the first few forecast periods, and an optional
delivery-ratio bias correction. Read the issue and its comments before writing
any code, which is the only reason this entry does not describe building the
wrong thing: the issue had already moved past both proposals.

**The decision on record, and it is not mine to re-open by writing code.** A
comment on #1259 tested mechanism 1 against the issue's own recorded figures:

```
live anchor @12:30  (solar_kw[0])   1.78 kW
forecast    @12:35  (solar_kw[1])  15.89 kW
ACTUAL      @12:35  (live sensor)  17.88 kW
```

The pure forecast was off by 1.98 kW. Linear decay over 3 periods would have
been off by 9.04 (4.6x worse), over 6 periods 13.74 (6.9x), exponential
half-life 2 → 11.96 (6.0x), and even a gentle `w = 0.25` → 5.51 (2.8x). Every
shape proposed degrades the exact event that motivated the proposal, because
the forecast was *right* — a real cloud-clearing ramp was already underway
(2.65 → 4.93 → 17.71 kW inside 90 seconds) — so the anchor was the stale
number, and blending a stale **level** forward can only drag a correct forecast
toward it. The live sensor's useful content that minute was its **direction**,
which a level blend discards.

Mark Purcell's reply, verbatim: *"Agreed — the table settles it... Decision:
don't build mechanism 1. Mechanism 2 (delivery-ratio bias correction) stays as
documented future work, unforced by this — today's 0.975 ratio shows it
correctly wouldn't have fired anyway... Leaving open as a measurement task
rather than an implementation one, unless a second real event shows a different
shape."*

So the work #1259 actually asks for now is its own point 4: measure how often
index 1 disagrees sharply with index 0, and when it does, which one is closer to
what happened — using `update_solar_delivery_ratio()`'s existing
queue-and-resolve plumbing.

**What shipped** (`update_solar_nowcast_disagreement()` in `solver_writer.py`):
the same "record a prediction now, grade it once reality catches up" shape as
the #128 delivery ratio, sharing its state file, its history reader, its
rolling-window prune and its never-raise contract. Two deliberate differences —
the horizon is `grid_times[1]` (the next period, not ~60 minutes, because index
1 is the whole subject), and **both** candidates are stored so resolution grades
them against the same actual. Only cycles where the two sit at least 3.0 kW
apart are queued, so the history fetches this adds are bounded by how often the
phenomenon happens rather than by the solve cadence; cycles that were
*considered* are counted regardless, at zero cost, which is what makes a rate
publishable rather than a raw event count. Published as one nested
`solar_nowcast_check` dict on `sensor.nimbus_solver_battery_forecast`, present
only when the measurement ran.

**Off by default**, behind a new `switch.nimbus_solver_nowcast_measurement_enabled`, for
two separate real reasons. It can never change a plan — it only reads history
and publishes — but it *does* add a recorder fetch per resolved event, and this
project has a measured solve-time incident from exactly that class of ambient
cost (flex signals: median 1.16s → 10.3s, and a 145s cycle against a 60s tick).
And a measurement whose purpose is to settle one open design question should be
switched on deliberately, on the installs whose data is wanted.

**Absent-when-off is load-bearing, not tidiness.** With the switch off the
published attribute set is byte-identical to before, so all 12 golden-master
snapshots and the golden guardrail's own exact-dict comparison are untouched —
which is also the honest evidence that a live install sees no change until
someone flips the switch.

Two tests are the point of the test file: one replays the real #1259 event end
to end and asserts the instrument reaches the conclusion the arithmetic in the
issue reached (forecast closer, by 8.1x), and one replays it with reality on the
other side, because an instrument that can only return one answer measures
nothing. A third pins the *absence* of mechanism 1 — no write to `solar_kw[1]`,
no `nowcast_weight`, no `decay_w` anywhere in the solar input path — with a
failure message pointing back at #1259 rather than at a style rule.

**Mechanism 2 deliberately not built.** Mark's own words put it as documented
future work unforced by this issue, and the day's own 0.975 delivery ratio says
it would correctly not have fired on the reported event. Building it here would
be inventing a reason to act past a decision that was already made.

## Issue 768 — the blocker that sat for a fortnight is built, and the decision it was waiting on arrived

Issue 768 asked two things in September: score the whole battery fleet, and let
the oracle answer *"could we have optimised better by moving a controllable
load's own timing?"* The first half shipped in v0.94.268 and Mark confirmed it
live (`scored_participants` → `["home", "ev_m3p"]`, EPR 80.45% → 57.53%). The
second half has been open since, blocked on exactly two things — one decision
and one capability. Both are now settled.

**The decision, Mark, 2026-09-27 18:11 AEST:**

> Decision: **real-delivered kWh**, not the configured target, for the oracle's
> `target_kwh` when re-timing a controllable load. […] Sequencing: the
> historical controllable-load delivery reconstruction is the real prerequisite
> and gates everything else — don't wire `adequacy_loads=`/`sheddable_loads=`
> into `compute_quality_report()`'s oracle call until that reconstruction
> exists […] Build that first, land it as its own change, then wire the LP
> plumbing […] as a second, smaller step.

So the options review that issue's title asks for is answered rather than
re-opened: **Option 1, second stage** — Option 2 is what actually happened
(battery half first), and Option 3 lost its cost advantage when
`fetch_entity_power_history_kw()` landed for an unrelated reason. This work is
the first of the two steps Mark named, exactly as scoped.

### What was built

`custom_components/nimbus_load/solver_inputs/controllable_load_history.py` —
the controllable-load counterpart of `battery_participants.py`. Per configured
`controllable_load` subentry, over an already-elapsed window:

- resolves the load's power sensor through the existing resolver, so a load
  relying on v0.94.292's device-registry discovery is covered rather than
  silently unscorable;
- fetches real recorded power with `fetch_entity_power_history_kw()` (#843,
  per-row unit scaling — the function built because Mark's EV pack reports `W`
  for ~80 s on wake);
- resamples to the scored grid and **zeroes every period the resample only held
  a stale reading over**, via `_stale_power_period_indices()` and therefore
  `load_run_state.MAX_SAMPLE_GAP_HOURS`, read rather than restated. This is the
  trap the issue itself named: `resample_history_mean()` carries the last
  sample forward indefinitely, which is right for a STATE and fabricates energy
  for POWER. An unguarded integration credited 28.8 kWh for a pool pump
  observed once, in the test that pins it;
- clamps negative readings to zero rather than subtracting them — #768's own
  manual reconstruction found "a real **-17.48 kWh** of negative-signed
  readings" on a real sensor with no mechanism that explains them, and excluded
  them;
- reports **not scorable with a reason** for a load with no power sensor or a
  day before that sensor existed. `delivered_kwh` is `null`, never `0.0` — the
  same honest-absence posture `offered_up_kwh` takes.

Published on `sensor.nimbus_solver_quality_report` as
`controllable_load_delivery`: one compact entry per **configured** load,
scorable or not, so a household can see the loads the day's score could not
read. The per-period series is deliberately not published — 288 floats per load
would put one field past the recorder's 16 KB attribute cap (#944), and nothing
outside the process needs it.

### It moves no scored number, and that is asserted rather than argued

`compute_quality_report()`'s oracle build is untouched: no `adequacy_loads=`,
no `sheddable_loads=`. `tests/test_768_delivery_is_published_without_moving_the_score.py`
scores the same window twice, identical inputs, the only difference being
whether a Controllable Load exists, and requires `epr`, `epr_pct`, `j_ref`,
`j_ach`, `j_star`, `regret_dollars` and `scored_participants` to be equal —
with a non-vacuity check that the reconstruction really did run and really did
find 1.95 kWh. "Present and unwired" and "present and quietly wired" look
identical in a diff that adds both a reconstruction and a report field, which is
#1267's own lesson in the other direction.

Measurement before adjustment is also the order #1242 used for
`soc_discrepancy_power_coverage`, and for the same reason: this issue's history
is a run of confident numbers that turned out wrong for reasons only a published
intermediate would have shown (#949's blended SoC, #1012's efficiency, #1228's
mean-vs-point artifact).

### Scope, stated because getting it wrong has cost a correction before

Structurally inert on the reference household and on devhub — both have **zero**
controllable loads, so this publishes an empty list there. Verification has to
happen on Mark's own production install, the one with `ev_m3p`/`ev_my`. This
repo has already told him once that something could not explain his numbers on
the basis of a reading taken from a different install (#1222/#1211); the note is
here so that is not repeated.

### Where the rest went

**#1357** is the second step, written specifically rather than as "and then wire
it": fill `adequacy_loads=`/`sheddable_loads=` on the scorer's oracle from this
reconstruction, **subtracting each load's reconstructed consumption from the base
load series first** (the real series already contains it, so passing the loads as
re-timeable on top of an unchanged base would double-count them — the issue
itself flagged this), exclude a not-scorable load from the oracle entirely, and
default the whole thing off for its first release so a household can compare EPR
with and without it on the same days. `kind=thermal` stays out, per Mark's own
call.

Issue 768 is closed as superseded by #1357 — its options review is answered, its
`target_kwh` decision is made, its battery half shipped, and its prerequisite is
built; what is left is one specific, scoped change rather than a review.

### Three decisions worth writing down

**The fake `homeassistant.*` modules are installed in the child process only.**
`scenarios.names()` runs at pytest collection time, so a module-scope
`sys.modules["homeassistant"] = <fake>` anywhere in the scenario import chain
would shadow the real package for every other test in the run — the
cross-contamination #1329 already exists for. `install_native_modules()` is
therefore called from `golden/child.py` and has no import-time side effect. It
also *overwrites* rather than `setdefault`s, deliberately: whether a real
`homeassistant` is installed in the environment must not change what a golden
scenario records.

**`add_job` blocks instead of scheduling.** Real HA's is fire-and-forget, which
would make the order of the `posted` list depend on event-loop timing. That is
the one observable difference from real native behaviour and it is stated in the
module docstring rather than left to be discovered.

**Handlers are registered for all eleven `_NATIVE_MANAGED_ENTITY_IDS`,** as
`sensor.py` does on a real install. Without that, `ha_post_state` takes its
#312 ghost-state guard for exactly those entity_ids and drops the write, so the
scenario would solve correctly and snapshot an empty `posted` list.

### Both loads' answers are forced, and the first draft's were not

A golden snapshot has to pin a uniquely-determined LP answer. With the flat
prices the Part A config uses, a load with slack has many equally-optimal
placements — and the first draft of the deferrable load had exactly that: a
target equal to what its window could deliver, which HiGHS satisfied by
starting the load **25 minutes in**. Not wrong, just not something a snapshot
should be pinning. The shipped scenarios use `min_fraction = 1.0` for the
sheddable load and, for the deferrable one, a target above what the window can
deliver against a shortfall price ($4.00/kWh) far over the import price
($0.30/kWh), so every period in the window must run at the cap.

`kind=thermal` is left uncovered on purpose and filed as **#1358**: its target
is a hard LP constraint with an infeasibility-relaxation retry behind it, so
the only configuration that forces a unique answer sits within ~0.01 °C of
unreachable. A snapshot that can flip between two structurally different solves
on a float is worse than no snapshot.

### A real finding about the update rule itself — #1359

`GOLDEN_UPDATE=1` rewrote all 12 pre-existing snapshots. Decompressing both
sides and comparing the parsed JSON: **all 12 identical in content and in
length, different only in bytes** — zlib's own output differs between builds
(recorded on CI's 3.14, regenerated locally on 3.12), and `_dump()` can pin
`mtime=0` but not that. So the update rule's "the diff goes in the PR" clause
currently hands a reviewer twelve unreadable binary files. Restored the 12 by
hand so this branch's diff is purely additive, and filed #1359 with two
options (store the records uncompressed; or only rewrite a snapshot whose
decompressed JSON actually changed).
