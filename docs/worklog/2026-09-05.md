**#365's last remaining piece (v0.94.108-109) is a real lesson worth keeping: a same-day CI-caught regression in the fix itself, not just in the target code.** `async_run_solve()`'s dispatched executor future is now tracked so `async_unload_entry()` can `await` it (bounded, via `asyncio.shield`) before tearing down platforms — closing the real race where an uninterruptible executor job could keep writing state after unload. But v0.94.108's own first cut didn't handle `asyncio.CancelledError` bubbling out of that shielded await: `async_unload_entry`'s own `old_startup_task.cancel()` (called just before the new wait) can propagate a cancellation into the SAME shared future if that task was still suspended awaiting it — `asyncio.shield()` only protects against the *outer* wait being cancelled, not the wrapped future being cancelled by another path, and `CancelledError` isn't a subclass of `Exception` in Python 3.8+, so the existing broad `except Exception` silently let it through, aborting `async_unload_entry` mid-teardown. CI's own real `hass_integration` reload-loop test caught this deterministically (confirmed via `gh run rerun --failed`) with a "Lingering timer" + `CancelledError` failure — genuinely un-reproducible locally in this dev environment (Python/HA version mismatch against the pinned test harness), root-caused purely by reading the CI traceback and reasoning through the exact asyncio mechanics, then verified with a mutation-tested regression test rather than an empirical local repro. **Worth remembering for any future `asyncio.shield()` use alongside a `.cancel()` call on a Task that might be awaiting the same shared awaitable: `except Exception` is not enough, `CancelledError` needs its own explicit handler.**
