## #843 — finishing the unit fix (v0.94.287, v0.94.288)

v0.94.285 (13 Sep) fixed the *smear* half of #843: `resample_history_nearest()`
returning samples from the future, so one bad reading propagated across eight
hours. That left the reading itself. Mark chose option C — do both halves of
the costed A/B/C steer — and both shipped today.

**v0.94.287, option B: a physical sanity bound.** Any participant power sample
beyond `10 × max(max_charge_kw, max_discharge_kw)` is discarded, filtering raw
history *upstream* of the resampler so a bad value never enters a period mean.
The multiple sits deliberately in the middle of the three-orders-of-magnitude
gap between plausible hardware overshoot and a 1000x unit error: a 25 kW device
briefly reading 30 kW (1.2x) is kept, a household who configures `5.0` for a
real 25 kW charger (5x) keeps all their data, Mark's actual corrupt sample
(~60x) is discarded, and a full W-vs-kW error is caught with two orders of
magnitude to spare.

It **discards rather than clamps**, and that distinction matters more than it
looks. Clamping 1514 kW down to the 250 kW bound would assert a value that was
never measured and is still ~10x what the device can physically do — converting
an obviously-absurd number into a plausible-looking but still-wrong one, which
is strictly worse for a figure feeding a real cost calculation because it stops
tripping suspicion.

**v0.94.288, option A: per-row unit scaling.** The root cause was never the
magnitude, it was that `_kw_scale_factor()` reads a sensor's *current live*
`unit_of_measurement` exactly once and applies that single scale across a whole
day of history — structurally unable to see a sensor whose unit changes
mid-window. Mark pulled the raw history with attributes and found the exact
rows: his EV pack sensor reports `W` for ~80 seconds as the car wakes, then
`kW`. A live check hours later returned `kW`, so `1514.417` was scaled by 1.0.

New `fetch_entity_power_history_kw()` fetches **with** attributes on both the
native and REST paths and converts each row by its own recorded unit, mirroring
the thermal-history path's existing precedent rather than inventing a second
convention for the same problem. Where B *discards* an implausible sample, A
*corrects* it — the real 1.514417 kW reading survives into the reconstruction
instead of being thrown away.

**Deliberately one function with exactly one caller.** Preserving attributes
makes a recorder read materially heavier — a separate join, on a report that
fetches a full day per sensor per participant — so every other history read
keeps the cheap attribute-stripped path. That scoping is what made option A
affordable at all. `_kw_scale_factor()` is untouched and still correct for its
seven other callers.

26 new tests across the two, with Mark's four real rows verbatim. #843 closed.

**Devhub cannot validate either fix** and this was stated plainly on the issue
rather than papered over: devhub's `Test EV` uses synthetic sensors with no
sleep gap and never reproduced the failure. The real check is Mark re-running
`compute_quality_report` for 13 Sep on his own data.

case. One was mutation-checked (flipping drop→zero-fill makes it fail) to
confirm it wasn't vacuous.

This is a better argument for continuing the refactor than the line count:
logic guarded by text-matching since it was written became executable tests in
one extraction. Each later stage should be scoped to do the same.

**"No behaviour change" was verified, not asserted.** A normalised diff of the
original 388-line block against the relocated code left **zero unexplained
differences** — the only deltas were the 53-line header comment becoming the
function docstring, three ruff reflows, and six signature changes where the
closures now take `grid_times`/`n_periods` explicitly. Plus: the repointed
inspection tests still pass with assertions otherwise unchanged, `main()` has no
orphaned references, and the full suite is green (2292 passed).

Live on devhub: `optimal` over 203 periods, period 0 solar = 4.524 kW against a

applying to index 0 only.

**Known cost, carried forward.** `solver_inputs/` modules reach back into

issue's own staging to do `ha_bridge` before stages 2-4 replicate the wart three
more times.

## The release-workflow encoding failure

v0.94.288's Release workflow failed and published nothing:
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0x97 in position 636`.

Cause: a changelog-editing script used `pathlib`'s **default** encoding, which on
Windows is cp1252 — every em dash in the new entry was written as a bare `0x97`
byte, and the release job's UTF-8 read died on it.

Two things worth keeping:

- **The first repair attempt would have made it worse.** A blanket byte-level
  `replace(b'\x97', ...)` also hits *valid* UTF-8 continuation bytes elsewhere in
  a 500 KB file. The fix that worked was iterative — decode, catch, fix that one
  byte, repeat — and ultimately a rebuild from the `v0.94.287` tag's known-good
  copy with an explicit UTF-8 write, giving a +11-line diff and nothing else.
- **Every subsequent changelog edit now asserts before and after**: uniform line
  endings (this file is 100% CRLF, and writing LF would have produced a
  whole-file spurious diff), a unique anchor, and a successful UTF-8 decode of
  the result. The v0.94.289 entry caught two real problems this way before
  writing — a non-unique anchor, and the CRLF trap.

Two agents were working this repo in parallel. Seeing v0.94.288's release job

had *already* fixed it via PR #854, and v0.94.288's release had since succeeded.

release correctly failed.

deleted (they would otherwise have blocked a legitimate future v0.94.289 — which
is exactly what this file's own #735 entry above then needed).

Two rules out of it, both applied for the rest of the day:

1. **Re-check that a problem still exists before acting on it.** Parallel agents
   make stale premises very easy to acquire, and a failing CI job is a
   *timestamped* observation, not a current state.
2. **Never push a tag without first verifying the merge landed** — `git log` on
   `main` plus the manifest version, not an assumption that a green PR merged
   itself.

Both were followed for v0.94.289: merge confirmed on `main` at the right SHA
with `manifest.json` reading `0.94.289`, and the tag's availability re-checked
against both local and remote before creating it.

**#860:** the anti-drift test blocks stages 2-4, in two ways. Six names in
`KNOWN_OPEN_DRIFT_INTEGRATION_ONLY` would trip the staleness guard on

across the writer and every extracted module; validated both directions by
simulating the real stage-2 move (pre-change: 2 failures; post-change:
green).

**#861 reverses stage 1's own recommendation.** That write-up called the
deferred by-module import (`sw.ha_get(...)`) a wart to be removed by doing
`ha_bridge` first. Checking the assumption before acting on it is what
caught the error: moving a helper also moves its *internal callers*, which
then resolve each other through the new module's namespace and escape every
`patch.object(solver_writer, ...)` in the suite. `entity_exists()` calls
`ha_get()` directly — move both and a patched test silently attempts a live
HTTP request. Reproduced minimally: `writer.uses_ha_get -> MOCKED`,
`writer.entity_exists -> REAL-HTTP-CALL`. Blast radius: 31 test files patch
`ha_get`, 24 `ha_post_state`, 14 `fetch_entity_history_range`.

So the deferred import is not a staging cost, it is what keeps those seams
intact, and it stays regardless of `ha_bridge`. **Revised staging:**
prices/load/p2p → publish → element construction → `ha_bridge` **last**,
and only with an explicit seam design.

**The pattern across both:** neither blocker was visible from reading the
code being moved. Both only appeared from asking what *else* resolves the
names involved. Stage 1's "mechanically safe" framing was right about the
code and wrong about its surroundings, twice.

**3. #773 auto-closed for the fourth time, by me, on the exact rule that
exists to prevent it.** PR #870's body read *"Does not resolve #773's

issue number and ignored the negation.

## #757 root-caused, in full — v0.94.296 → v0.94.302

The long-running "battery_participant subentry silently excluded from
solve" issue. It had been open through **ten separate investigations that
disagreed with each other** about whether it even reproduced. Two real
defects were behind that, both now shipped and confirmed live, and a third
question remains genuinely open.

### The first defect: failed solves overwrote good plans (v0.94.301)

`_infeasible_plan()` builds a well-formed but **entirely zero-filled**
`Plan` for any non-optimal solve — no batteries, no loads, every array
`zeros(n)`. `publish_plan()` published that like any other plan. On a
dashboard that is indistinguishable from a real solve that decided to do
nothing.

Live evidence that settled it: `build_plan()` returned
`batteries=['home','Test EV']` with `status='optimal'` on **24 of 24**
cycles, while **7 of 10** actual publishes in the same window carried
`batteries=[]` with `status='error'`, each on a different worker thread.
Nothing was ever excluded. Whoever looked next saw whichever write landed
last — which is precisely why ten readings of one system disagreed.

Scoped to `"error"` only via a new `Plan.solver_failed`. `"infeasible"` is
a real modelling *answer* the household needs to see, and #773's fallback
depends on it being published. A test asserts `solver_failed` is **not**
`not is_optimal`, because the tempting one-line version passes three of
four status tests and is wrong.

### The second defect: the overlap guard never guarded (v0.94.302)

`acquire_lock()` is a PID file. In native mode every solve runs in the
*same* process on different executor worker threads, so the PID is always
our own — and #346's own branch reads that as a stale file:

```python
if old_pid == os.getpid():
    pass  # stale file from an unclean stop -- safe to reclaim
```

#346 was a real bug and that fix was right for it. But "this PID is our
own" is **also** exactly what a genuine concurrent in-process solve looks
like, and a PID file has no information left to tell the two apart.
Reproduced in three lines:

```
thread A acquires: True
thread B acquires WHILE A HOLDS IT: True
```

Confirmed live, not only in a harness — HA itself logged `Setup timed out
for bootstrap waiting on {...}` naming **four** concurrent
`_run_price_change_solve()` tasks in flight at once, each holding an
executor worker, blocking HA's own startup.

Fixed with a process-local `threading.Lock`, non-blocking, alongside the
PID file. Both kept: a PID file cannot see a sibling thread, a
process-local lock cannot see a sibling process.

### Three lessons worth carrying

- **A guard that cannot fail is indistinguishable from a guard that
  works.** Nothing in the logs said the overlap guard was broken — it was
  silent, which read as "no overlaps". The absence of #315's WARNING was
  the evidence, and absence is what nobody checks.
- **Re-run the whole suite, not the new file.** The full run caught that
  #346's own regression tests had started **passing for the wrong
  reason**: `test_lock_held_by_a_real_different_running_process_is_still_
  respected` expects `False` and was getting `False` from a leaked
  process-local lock, never reaching the PID check it exists to verify.
  Running only the new file would have shipped a silently-broken guard
  test.
- **My own #594 guard caught me.** Bumping to 0.94.301 made v0.94.300 an
  enforced release, and CI failed because v0.94.300's entry had no
  `Devhub validation:` line — the deploy was done, the recording was not.
  The rule worked on its author.

### Deliberately not overclaimed

I first wrote that the issue's premise was wrong, and corrected that on
the issue. What the evidence supports is narrower: **the ten disagreeing
investigations are explained.** It does not follow that the exclusion was
never real — on v0.94.301, with clobbering stopped, the verification
install still publishes `n_batteries: 1` while the EV participant's own
three entities are healthy (`available: on`, SoC 25.33, power 0.000).

That reading is *not* usable as evidence in either direction, because the
same install is simultaneously serving surfaces from several releases back
(`sensor.nimbus_solver_config` missing fields added two releases ago while
`solver_writer.py` demonstrably runs the current one). Known,
separately-tracked environment defect; logged, not chased.

**So #757 stands at three items, not two:** clobbering (fixed, confirmed);
overlap guard (fixed, confirmed); and whether a healthy battery
participant is genuinely dropped — still open, and not answerable from any
install currently visible.

### Knock-on: #773 and #875

**#773** gained a concrete, falsifiable hypothesis for the strand that had
resisted explanation (*"even the plain non-calibrated solve occasionally
hits HiGHS's 60s per-call limit"*): **HiGHS's time limit is wall-clock, not
CPU-time.** Four concurrent solves contend; a solve that finishes in 15s
alone can blow a 60s limit with three siblings. That accounts for every
property — intermittent, `solve_now` succeeds right after, *never
reproduces locally* (one solve at a time, so the failure mode cannot exist
there), and correlates with the large fleet. That last point cuts against
my own earlier triage on that issue, which blamed problem shape.

Time-limit failures went 31 → 7 → **0** across the three versions. Caveat
recorded on the issue rather than buried: serializing also means fewer
solves run, so part of that is fewer attempts. The `Infeasible` strand is
genuinely separate — a time-squeezed solve reports `kTimeLimit`, which maps
to `"error"`, never `"Infeasible"` — and stayed untested in the window, so
it was reported as untested rather than counted as a pass.

**#875** (Mark Purcell): the `command_divergence_seconds` detector shipped
in v0.94.296 fired on a real divergence within minutes of his deploying
it, in the opposite direction from his original report — device heating at
418.6 W since 19:50 while commanded *off* since 16:40, ≈54 min. He asked
whether it correlated with the #757 work before calling it a separate root
cause. It does, via a specific path: `LoadRunStateStore.async_write()`
holds a lock but `async_read()` does not, and the whole read → solve →
write sequence is unprotected, so two concurrent solves lose an update —
thread B dispatches ON and writes `true`, thread A (no transition seen, so
no dispatch) writes `false` last. Device physically on, stored state
false, `commanded_since` stuck at the older timestamp. Exactly his shape.
Confirmed the only writers are on the solve path, so v0.94.302 genuinely
closes that window.


## #773 root-caused — five hypotheses, five refutations (runs into 09-15)

Releases v0.94.303 → v0.94.305, all diagnostics. The issue is **not** closed;
what changed is that it now has measurements instead of theories, and a
much shorter list of things it could be.

### The list, in order, with what killed each

| # | Hypothesis | Refuted by |
|---|---|---|
| 1 | A large fleet pushes the lex phase infeasible | `calibrated_objective_enabled` is **off** on the affected install — that phase was never running |
| 2 | Wall-clock contention between concurrent solves | v0.94.302 made the overlap guard genuinely refuse (75 skips, 3.07/min); failure rate unchanged, 0.92 → 0.91/min |
| 3 | The offer-curve ranging walk | A-B-A: **0.91** on / **0.84** off / **0.77** restored. No effect either way — and `sweep_seconds` was **47 ms**, which should have ruled it out before the experiment |
| 4 | LP degeneracy / simplex cycling | `n_binary=1134` — it is a MIP, and `primary_minimize` reaches `Optimal` at 49–52 s much of the time, so it is not pivoting forever |
| 5 | The objective-setting API (`h.minimize(qsum)` vs `changeColsCost`) | Local A/B: identical iteration counts in all three pairs, 849/849, 765/765, 1721/1721 |

### The two that were my own fault, not the data's

**Using a reading I had already declared untrustworthy.** I eliminated the MIP
path using `n_controllable_loads: 0` from a published sensor on an install I
had — *on that same issue, in writing* — said could not be trusted in either
direction because it serves surfaces from several releases back. The log lines
come from the process actually solving and are self-consistent; the published
attributes disagree with them. That disagreement is more evidence for the
two-process theory, not something to reconcile.

**Reading a post-restart window too early.** Reported `"Time limit reached"` at
**0** after deploying v0.94.302 and called it confirmed. Twenty more minutes
reversed it completely: normalised, 0.92/min before and 0.91/min after. The
raw `31 / 7 / 0` table I posted compared three windows of wildly different
lengths as if equivalent — the v0.94.301 figure was a 78-second burst that
should never have been in the table.

### What actually moved it forward each time

Not a better theory — a field on a log line.

- `simplex_iterations` (v0.94.303) answered cycling-vs-stuck on the **first
  cycle after deploy**.
- `n_vars` / `n_binary` (v0.94.304) overturned the pure-LP conclusion **within
  the hour** — and that release existed only because I had shipped the fields
  as `None` and flagged it as a gap in my own work rather than leaving it.
- `mip_node_count` / `mip_gap` (v0.94.305) separates the last two candidates:
  a huge search tree versus never leaving the root.

Each was cheaper than the argument it replaced. That is the lesson worth
keeping.

### The measurement that closed off a whole class of explanation

A synthetic model **larger than production in the dimension that looked
decisive** — 8,800 variables and **4,800 binaries**, against the real
~11,800 and **1,134** — solves in **0.2 s at 1,721 iterations**, where the real
one runs **157,000–214,000**. The fixture carries the full adequacy-load
structure (on/start binaries, startup linking, daily energy target, SoC
coupling across periods).

So size, binary count and general problem shape are all ruled out. The
difficulty lives in the **real instance**, which means synthesising it has
failed and the next step is to capture it (`h.writeModel()` on a slow call)
rather than reconstruct it. That is waiting on Mark: a model file embeds a
household's real prices and load shape, so whether it may be written at all,
and whether behind an opt-in switch, is not my call.

### Two real bugs found along the way, both in code I shipped

- **v0.94.301 hid the symptom it protects against.** Its publish guard returns
  early on a failed solve, and `solve_seconds` is published ~750 lines past the
  return — so `sensor.nimbus_solver_solve_seconds` reported **only successful
  solves**, exactly hiding the ~60 s durations #773 needed. Fixed in v0.94.303
  by logging the elapsed time in the branch that already logs the reason.
- **The #773 cooldown falls back to the most expensive path.** On a lex
  failure it returns `options=None` for five minutes — the path measured at
  49–60 s, versus the lex path's 15–33 s. Added to protect the instance from an
  expensive failure; on this problem it selects a more expensive one.
