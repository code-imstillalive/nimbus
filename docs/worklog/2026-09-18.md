## #1012 — closed, and not a Nimbus defect

Twenty-six comments of narrowing by measurement. All three candidates in the
issue's own body are eliminated:

| candidate | verdict |
|---|---|
| `solver_efficiency_percent = 85.8` is wrong | **not the cause** — the instrument returns implied efficiency *above unity* (1.026–1.049), which is not a tuning error but proof an input is incomplete |
| the counters sit at a different **reference plane** | **refuted by the test I proposed for it** — `logger_battery_power` is DC pack power in *both* directions, V×I matching the sensor to 0.3–0.5% charging *and* discharging |
| configured capacity / SoC scaling is wrong | **settled and already applied** — 119.72 kWh, not the 122.16 nameplate (#1013); back-computing `residual_pct_of_capacity` across three days gives 119.75–119.80 |

Also eliminated, each by measurement: **rate** (1.080–1.104 kWh/point across three
days and a 33% current spread), **solar** (near-identical solar with 5× different
excess), and **blend weighting** (two packs differing 39% in capacity giving
identical kWh/point). Plus a null result kept deliberately: `combined_battery_charge`
is `SoC × 1.1972` to ±0.2% across the whole 2–100% range — a display conversion
carrying no information the SoC sensor does not already carry, so it cannot
corroborate anything about linearity because linearity is assumed in its
construction.

**The DC-coupling hypothesis was mine, and the measurement I specified for it
killed it.** Worth recording as the good case: the hypothesis was falsifiable, the
test was cheap, and it came back negative.

What survives has homes rather than being left implied: the **fleet-blend artefact**
→ #949 (the install scoring this is currently on two participants, so the headline
number is materially that artefact), and **SoC hysteresis** → #1086. The residual
finding is real — the SoC scale is direction-dependent by ~5% within a band, so
full-day closed loops give physically possible round-trip efficiency (0.978, 0.982)
while a band-restricted window gives an impossible **1.049**.

Closed as *not a dispatch defect*, which the body had raised the stakes on
specifically: `solver_efficiency_percent` feeds the live LP, not only the
scorecard. Measured answer — the live path is unaffected; the formulas on both
sides are identical and only the reconstruction's *inputs* differ.

## #1086 — filed, then twice qualified by my own testing

`solver_efficiency_percent` looks ~6 points pessimistic one-way, ~11 round-trip,
from closed-loop energy balance over three consecutive days (mean **0.982** against
a configured 0.9263). The method's appeal is that `in·e − out/e = stored_delta` is
capacity-independent when the loop closes, so it sidesteps the hysteresis #1012
documents.

Then two negative results, both against my own work:

- **Cut-sensitivity is 1.2 points** — larger than the day-to-day spread the estimate
  was being read as meaningful against.
- **Floor-anchoring, which I proposed as the fix, makes the scatter *worse* (2.5
  points).**

Honest state: 0.9689–0.9937 across five windows against a configured 0.9263. The
gap still exceeds the scatter, so the finding survives — but I have no remaining
proposal for tightening it on this install, and the recommendation is a second
install rather than more windows on this one.

Shipped alongside: **`energy_out_exceeds_in_on_closed_loop`** (v0.94.382). A day
returning to its starting SoC cannot deliver more than it received; 13 Sep did, by
5.2 kWh, while finishing within 0.11% of throughput of where it started. The report
*had* been flagging that day — as `mixed_window_not_decisive_implied_above_unity`,
which is true and sends the reader to the battery when the actual finding is that a
**recorder** input is incomplete. Every other reason in that diagnostic describes
reduced *confidence* in a sound number; this one says the inputs do not add up,
which is a different claim and earns a different word.

## #1089 — the day's real find, and the day's real mistake

**A day the household did $3.50 worse than doing nothing published as EPR 242.7%.**

```
EPR = (j_ref - j_ach) / (j_ref - j_star)

j_ref   5.4897      numerator    j_ref - j_ach  =  -3.4975
j_ach   8.9872      denominator  j_ref - j_star =  -1.4411
j_star  6.9308      EPR = +2.427   ->   published 242.7%
```

**Both terms are negative and the signs cancel.** A negative numerator is honest —
EPR goes negative and the dashboard says so. A negative denominator inverts it,
which makes this **the only failure mode in this scorer that makes the headline read
better than the truth.** The same report published `theoretical_maximum_yield:
-1.4411` — "the best available outcome was worse than nothing" — and nobody had
noticed.

Nothing caught it because **neither existing reliability signal involves `j_ref`**:
`soc_discrepancy_reliable` (#533) tests the SoC reconstruction, `regret_reliable`
(#956) tests `j_ach - j_star`. `regret_dollars` was **+2.0564** — positive — so
`regret_reliable` was True and `epr_reason` was None. Regret ≥ 0 asks "did the oracle
beat the achieved dispatch?", never "did the oracle beat *idle*?".

The day was flagged at all only by an **unrelated** SoC disagreement. **With a clean
reconstruction, 242.7% would have published as fully `epr_reliable`.** It escaped by
coincidence, not design.

Two of the three days in that report's own history carry structurally impossible
arithmetic by two different routes — 15 Sep with `regret_dollars` **-0.3977**, 17 Sep
with the negative denominator. Only 16 Sep, the day the P2P-gating fix was verified
on, is sound.

### The mistake

I wrote the fix on the claim that `j_star <= j_ref` holds **by construction** — the
oracle may always choose to do nothing, so it cannot be beaten by doing nothing —
making any violation proof of a computation fault, specifically #1081's pricing-path
mismatch.

**That claim is wrong, and this repo had measured why on 2026-09-16.**
`_widen_export_pin_to_achieved()`'s own docstring, written for #1001:

> Then the commitment is a **loss the oracle cannot decline** ... a 12 kW commitment
> over seven hours at 7.5c export against 37c import gives **`j_star` $2.43 worse
> than doing nothing at all** and regret -$4.95.

`fixed_export_kw` pins the oracle's export in every committed P2P period, so idle is
**not in its feasible set** and it can be beaten by idle with no pricing mismatch at
all. I presented as a new structural impossibility something already written down
here — **the same error corrected on #999 the day before.** That is twice in two
days, and the reusable lesson is not "read more carefully" but *check whether the
codebase already answers the question before deciding the answer is new.*

The 17 Sep report carries evidence of both mechanisms against its -1.4411
denominator:

```
p2p_commitment_shortfall_kwh   2.0036     -> #1001, a committed export pin was active
j_star_path_delta              2.4889     -> #1081, LP objective vs evaluator pricing
```

Either alone accounts for the sign and the report cannot apportion between them.

### What the correction improved

It made the reason string's wording load-bearing rather than incidental.
`oracle_not_better_than_idle` names the **observation** and no cause — which matters
because under #1001 a household hitting this has **nothing to fix in the code**, so a
reason blaming a pricing bug would be wrong roughly half the time. There is now a
test that fails if anyone renames it to something diagnostic.

The guard is right under either mechanism, for different reasons: under #1001 the
arithmetic is sound and the **interpretation** breaks (EPR measures capture against an
idle baseline the oracle was never free to choose); under #1081 the two inputs are
non-comparable. Both times the published percentage is not a score, and both times
the remedy is a decision rather than a patch — so it reports and leaves the number
alone.

### Two smaller things from the same change

- **`solver/epr.py`'s docstring was part of the defect.** It named exactly one
  mechanism for `epr > 1` — "j_ach beat j_star" — so a reader diagnosing 242.7%
  follows that advice, checks regret, finds +2.06, and concludes the number is sound.
- **A bare `j_star > j_ref` test fires on float noise.** `compute_epr()` has always
  treated `abs(j_ref - j_star) < 1e-9` as "no opportunity existed" and reported 1.0
  inside it, so a -1e-12 denominator on a genuinely flat day would have been reported
  as a perfect 1.0 **and** as unreliable simultaneously. The band is now a shared
  constant so the two cannot disagree about the same day — reuse, not a new
  threshold.

The check lives in `solver/epr.py` and is computed inside `compute_epr()`, so it
rides on `EPRResult` and every consumer gets it for free. That is what lets the
**standalone/cron writer** publish it: that deployment emits `epr` and
`theoretical_maximum_yield` and has never carried *any* of the three reliability
signals. Putting the check next to the arithmetic makes it free there rather than a
second copy that can drift (#357). The other two remain absent — a #944-family
structural gap, tracked rather than quietly closed.

## #937 — a prediction of its own, tested

#937's body explicitly rules out comparing its day-ahead figures to the one-step
`load_nowcast_skill_*` fields, and *predicts* those will "look considerably better
without the forecaster having improved one bit." Reading the issue first is what
stopped a false comparison being posted; the prediction itself was then testable
against four full days:

```
mean nowcast value-add      +$0.097 / day   (+$0.161 excluding a 0.958-coverage day)
#937's day-ahead figure     -$0.71  / day
```

Prediction holds. The part that was not predicted: **the magnitudes are not
comparable either, and not in the forecaster's favour.** Nowcast wins are small
(best day +$0.45, three of four under ±$0.10) while day-ahead losses average ~7×
larger and reach -$3.42. A forecaster that adds cents where decisions are cheap and
costs dollars where they are expensive is still costing dollars — and day-ahead is
the horizon that drives dispatch. That sharpens #937 rather than softening it, and is
consistent with the horizon-mismatch mechanism already established there.

### #773 — the production path was reporting a solvable model as infeasible

The pinned-LP tolerance work started as a `LexOptions`-only curiosity and turned into
the day's most consequential fix. `_lp_tolerance_matching_mip()`'s docstring claimed
`phase2_pin_resolve` was *"the single place asking an LP to re-certify a point a MIP
already accepted"*. There were **five**, and one was guarded.

`phase3_lex_restore` reproduced deterministically on unmodified code — the first
end-to-end reproduction #773 has had that does not require disabling a fix first,
which is the gap #999 filed. Then, following the mechanism into the mode production
actually runs:

```
CalibratedOptions →  Plan.status "infeasible", total_cost None
LexOptions        →  Plan.status "optimal",    cost 24.4997
```

Same model. `_calibrate_blend_weight()` ran its probes on pinned binaries through raw
`h.run()`, and `_primary_acceptable()` treats a non-optimal status as *"this weight is
unacceptable"* — so a probe landing in the band never raised, logged no diagnostic,
and **never reached `network.py`'s fallback**. Dispatch went unavailable with the
documented safety net not firing, because nothing raised.

Two things worth keeping. The mechanism was established by **elimination** — widening
phase 3's secondary-bound epsilon one hundred fold left the failure bit-identical,
which killed the competing #981-class explanation. And wrapping only the probe was
measured and found **insufficient**: non-optimal runs went 3 → 1 and the status stayed
`infeasible` until the final blended solve was wrapped too.

Mark independently re-verified this by reverting to `129a500` and confirming the test
genuinely fails without it. **What it does not fix** is pinned by its own test: a
violation of **1.92e-06**, above `mip_feasibility_tolerance` itself, which matching
tolerances cannot reach by construction.

### Mark's IV&V pass — three findings, two on same-day code

**#1104** landed on #1089's guard, shipped hours earlier, and found a claim in its
docstring that was simply false. *"Sharing the constant is what keeps the two from
disagreeing"* — except `compute_epr()` tested it with `<` and `denominator_reason()`
with `>`, and two strict operators around one boundary leave a gap at it. Reproduced
exactly at `j_ref=0.0, j_star=1e-9`: **EPR 4e+09 published, denominator negative,
unflagged.**

The first reproduction attempt *failed*, because `5.0 - (-1e-9)` does not round-trip
exactly — the same reason Mark noted it needs a computation to land on the exact
float.

**Why this project's own test missed it is the instructive part**, and there were two
independent reasons: the assertion covered one direction of a biconditional (never
"divided-by, negative, and NOT flagged"), and its fixture could not reach the boundary
anyway. Either alone would have been enough to hide it.

**#1102** — the #1076 AST guard only ever parsed the native copy. The cron copy had
four unguarded clock reads, three convention risks and one real:
`seconds_to_settlement_capture()`'s `now.minute % 5` is only invariant under a
whole-hour UTC offset. Brisbane is UTC+10; **Adelaide is UTC+9:30**.

**#1103** — the P2P bonus gate's pinning test could not see NaN uncommitted periods,
the majority case, because every numpy comparison against NaN except `!=` is False.
Production was correct; the guard was blind. Mark's new test covers it, and the
original blind mask was also fixed — verified by reintroducing the defect and
confirming **both** tests now fail, where that one previously passed.

### #1098 — and the diagnosis that was better than mine

On #1086 I had hypothesised that an above-unity EV efficiency meant the car was
charging where the home sensor could not see it. Mark checked the sensor config first
— both EVs already use comprehensive pack-level readings — and found the real cause:
**Nimbus deliberately masks away-window power** (#768/#467, correctly) while SoC
telemetry reports everything. Two sides of the balance answering different questions.

His `ev_my`, away three times on 17 Sep (~4h56m), reported `implied_charge_efficiency
1.2849` under the label reserved for genuine reference-plane errors.

Now `participant_away_during_window`, checked **first** — a precedence his filing
implies without stating, because a mostly-away participant has masked throughput and a
moving SoC, which is exactly `soc_moved_without_throughput`'s trigger, and that branch
accuses the power sensor of failing. Here the sensor was fine and this code masked it
on purpose. His suggested plumbing turned out unnecessary: the mask already arrives on
the participant's own `BatteryConfig`.

### #1109 and #1111 — the same drift, twice, found by asking rather than noticing

Checking whether #768's stated prerequisites had actually been satisfied found that
one had only half carried. `_resolve_battery_participant_history()` — by its own
docstring *"the history-based sibling of `build_extra_batteries()`"* — set
`unavailable_period_indices` but not `shared_charger_group`/`shared_charger_max_kw`.
The oracle could charge two EVs on one 25 kW charger simultaneously.

Rather than stop there, diffing the two siblings' `BatteryConfig` keyword sets — a
five-line AST script — found **four** differences. Two were legitimate and documented.
The other two were `must_have_soc_by_period_index`/`must_have_soc_kwh`: a **hard**
constraint (*"a real EV genuinely needs a real SoC by a real time"*) that let the
oracle leave the car empty at departure and bank the arbitrage.

Both are now fixed, both **widened** rather than passed straight through — adding a
constraint narrows the oracle, and #956 records what that costs when the achieved
trajectory falls outside it. For the departure deadline the failure is *ordinary*: a
household that simply did not plug in has a day that misses its own target.

The durable half is a **parity test** asserting the only remaining differences are the
three with written reasons. The check that found both is now automated, so a third
instance fails rather than waiting to be noticed.

### A negative worth as much as the findings

Applying the same diff to the three counterfactuals in `quality_report.py` came back
**clean** — every difference deliberate and documented. Recorded as a negative rather
than written up as a finding.

And on `build_plan()`'s seven call sites: `thermal_loads` is absent from the scorer's
oracle and **#768's own inventory does not name it**, having been written before
`ThermalLoadConfig` existed. My first reading — that a handicapped oracle flatters the
household — did not survive checking what those classes are: adequacy and thermal
loads impose a *requirement* as well as granting freedom, and the real load series
already contains what they consumed. **Direction unknown**, recorded as such, because
#1109 and #1111 were both unflattering and it would be easy to assume the class runs
one way.
