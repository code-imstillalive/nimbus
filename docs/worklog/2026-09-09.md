# 2026-09-09

## #582: deferrable Controllable Load dropped for its entire active window

Mark's install hit this on the very first live morning of the #534 heat pump as a
real Controllable Load (deferrable, earliest 6am, deadline 4pm, 2 kWh at 0.65 kW,
device entity set from #578). The 05:56 solve (one period before the window
opened) resolved it normally. From the 06:01 solve onward -- every solve for the
rest of the 06:00-16:00 window -- the load was silently excluded entirely:

```
Nimbus: controllable load 'Hot Water Heat Pump' (deferrable) resolved
deadline_period (33) before earliest_period (61) for this cycle's own 'now'
-- skipping until the window resolves normally
```

Root cause, precisely diagnosed in the issue report itself: `_resolve_hour_to_
period_index()` always resolves "the next real occurrence of this hour from
now" independently for each hour field. Once `now` (06:01) passed today's own
6am earliest-hour, the earliest instant rolled forward to TOMORROW 6am, while
the deadline (4pm) stayed today -- `build_controllable_loads()`'s own ordering
guard (`if deadline_period < earliest_period: continue`), written for the
genuine overnight case (earliest 10pm, deadline 6am spanning midnight), then
silently dropped the load for the rest of its own active window -- the exact
opposite of correct behavior, since the window being open is precisely when
deadline pressure needs to apply.

Fixed exactly per the issue's own suggested approach: when the ordering
conflict is detected, check the load's own UNROLLED earliest/deadline instants
for today directly -- if `now` genuinely falls between them, the window opened
earlier today and is still active, so `earliest_period` resolves to "right
now" (0) instead of tomorrow. The pre-existing genuine overnight case (checked
well before it opens) is unaffected -- confirmed with a dedicated regression
test alongside the exact 06:01 repro (using a real `build_tiered_grid()`, not
a synthetic grid, matching the issue's own suggested test) and a same-day-
before-it-opens guard test.

**Known, honestly-scoped remaining gap, not covered by this fix**: an
overnight window where `now` is already INSIDE it (e.g. it's 11pm and the
window opened at 10pm, or it's 3am and the window opened at 10pm the night
before) hits the same underlying "earliest resolves to the wrong day" pattern
via a different path, and this fix's same-day check doesn't catch it either
(today's unrolled earliest/deadline instants don't bracket `now` the same way
for a window that spans midnight). Left open deliberately -- #582 itself only
reported and asked for the same-day case; inventing a fix for the overnight-
in-progress case without a real report or real data to verify against would
be exactly the kind of unrequested scope creep this project's own practice
warns against. Flagged in the CHANGELOG and left for its own future issue if
it turns out to matter on a real overnight-window install.
