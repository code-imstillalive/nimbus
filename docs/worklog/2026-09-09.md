## #582: deferrable Controllable Load dropped for its entire active window

Mark's install hit this on the very first live morning of the #534 heat pump as a
real Controllable Load (deferrable, earliest 6am, deadline 4pm, 2 kWh at 0.65 kW,
device entity set from #578). The 05:56 solve (one period before the window
opened) resolved it normally. From the 06:01 solve onward -- every solve for the
rest of the 06:00-16:00 window -- the load was silently excluded entirely:

```
Nimbus: controllable load 'Hot Water Heat Pump' (deferrable) resolved
deadline_period (33) before earliest_period (61) for this cycle's own 'now'
-- skipping until the window resolves normally
```

Root cause, precisely diagnosed in the issue report itself: `_resolve_hour_to_
period_index()` always resolves "the next real occurrence of this hour from
now" independently for each hour field. Once `now` (06:01) passed today's own
6am earliest-hour, the earliest instant rolled forward to TOMORROW 6am, while
the deadline (4pm) stayed today -- `build_controllable_loads()`'s own ordering
guard (`if deadline_period < earliest_period: continue`), written for the
genuine overnight case (earliest 10pm, deadline 6am spanning midnight), then
silently dropped the load for the rest of its own active window -- the exact
opposite of correct behavior, since the window being open is precisely when
deadline pressure needs to apply.

Fixed exactly per the issue's own suggested approach: when the ordering
conflict is detected, check the load's own UNROLLED earliest/deadline instants
for today directly -- if `now` genuinely falls between them, the window opened
earlier today and is still active, so `earliest_period` resolves to "right
now" (0) instead of tomorrow. The pre-existing genuine overnight case (checked
well before it opens) is unaffected -- confirmed with a dedicated regression
test alongside the exact 06:01 repro (using a real `build_tiered_grid()`, not
a synthetic grid, matching the issue's own suggested test) and a same-day-
before-it-opens guard test.

**Known, honestly-scoped remaining gap, not covered by this fix**: an
overnight window where `now` is already INSIDE it (e.g. it's 11pm and the
window opened at 10pm, or it's 3am and the window opened at 10pm the night
before) hits the same underlying "earliest resolves to the wrong day" pattern
via a different path, and this fix's same-day check doesn't catch it either
(today's unrolled earliest/deadline instants don't bracket `now` the same way
for a window that spans midnight). Left open deliberately -- #582 itself only
reported and asked for the same-day case; inventing a fix for the overnight-
in-progress case without a real report or real data to verify against would
be exactly the kind of unrequested scope creep this project's own practice
warns against. Flagged in the CHANGELOG and left for its own future issue if
it turns out to matter on a real overnight-window install.

3 new tests, all passing alongside the existing 64. Full local stub-based
suite re-verified clean. `ruff check`/`ruff format --check` clean. Released
as v0.94.187.

Not merged in this session -- same review discipline as every other PR this
marathon, left for the coordinating session to review and merge.

## #586: quality-scorer oracle no longer rushes a below-floor recovery

Filed as a sub-issue of Mark's own automated 9 Sep day-ahead report (#584),
alongside #585 (scorer scope on the multi-battery install -- see below).

8 Sep started with the pack at 0.0% against its 13% floor (#571, confirmed
real the same day). The oracle's first move in the scorecard: import 5.4 kWh
at 20.2c/kWh at midnight purely to reach the floor, then sit idle for six
hours, when the day's own real cheapest power (4.9c/kWh) arrived at 14:00 --
`j_star` ends up about $1.08 higher than a genuine perfect-foresight cost
would be, regret understated by the same amount, and the 00:00 scorecard row
reads as "the household beat the oracle at midnight," a nonsensical
characterization of the real day.

Root cause: `compute_quality_report()`'s own oracle `build_plan()` call used
the SAME auto-derived `soft_soc_penalty_per_kwh` the LIVE solver correctly
relies on to recover a below-floor SoC promptly (steep by design --
`DEFAULT_SOFT_SOC_PENALTY_MULTIPLIER` times the day's own MAXIMUM real
price) -- exactly backwards for a RETROSPECTIVE oracle, which has no reason
to value promptness at all, only genuine price advantage.

First fix attempt, caught and rejected by this fix's OWN regression tests
before shipping: deriving the penalty from the day's own MINIMUM price
instead of its maximum, still applied every period. Worked out by hand and
confirmed by a failing test -- the penalty accrues PER PERIOD for every
period spent below floor, so even a much lower per-kWh rate still costs far
more than the one-time expensive-but-prompt recovery once enough hours
separate the start of the day from the cheap window (14 hours x 5.2 kWh x
even a "low" $0.50/kWh rate is ~$36, dwarfing the ~$1.05 cost of just paying
20.2c/kWh immediately) -- a lower recurring rate never removes the urgency,
it only raises the bar for how much delay reproduces the same rush. Kept as
a permanent regression guard test
(`test_a_merely_lower_recurring_penalty_still_rushes_to_recover`) so this
same wrong fix can't quietly come back.

Real fix: the auto-derived penalty is completely untouched for the ordinary
case (a battery starting the day AT OR ABOVE its own floor never triggers
the new branch at all -- confirmed byte-identical to before this fix). Only
when the day's own starting condition is already below floor (a fact about
history the oracle had no way to have prevented within the scored window,
not a choice it made) is the penalty relaxed to exactly zero for that one
oracle solve -- the floor stays a real, fully-priced preference on every
other, well-behaved day; this narrowly removes the false "must recover
immediately" pressure precisely in the one case #586 describes.

6 new tests across two levels (direct `build_plan()` comparison proving the
mechanism, and `compute_quality_report()` end-to-end proving the published
`j_star_hourly` no longer shows the early expensive charge), full local
stub-based suite re-verified clean, `ruff check`/`ruff format --check`
clean. Released as v0.94.188.

**Deliberately not attempted in this pass**: #585 (the scorer only scores
the home Sigen pack, blind to the two `battery_participant` EVs even though
`build_plan()` now solves the full three-battery fleet) -- a substantially
larger architectural piece (per-participant SoC integration, grid
reconstruction, oracle re-run against the full fleet with shared-charger/
availability constraints), left for its own dedicated session.

## #581: Controllable Load day-ahead plan forecast published

Mark's household ask, 05:30: "chart the day-ahead plan for the heat pump" (the
#534 water heater, configured 8 Sep as a deferrable Controllable Load, 06:00-
16:00 window, 2 kWh target). Genuinely impossible from outside the
integration today, and he confirmed it thoroughly before filing #581: tried
backing the load's own draw out of the published power balance (`solar +
import - export + battery - load_kw`) on the 05:56 solve, found the residual
is a smooth 0.1-1.3 kW curve across the whole day (AC-bus losses and inverter
self-consumption) that a 0.65 kW load can't be separated from -- so there's
no honest derivation, only real publishing closes the gap.

Root cause, confirmed by reading the code directly: `solver/network.py`
already builds a full per-period plan for every Controllable Load
(`AdequacyLoadPlan.power_kw`/`delivered_by_deadline_kwh`/`shortfall_kwh` for
deferrable, `SheddableLoadPlan.served_kw` for sheddable) -- every solve,
every period. `apply_commanded_state_guard()` (`solver_writer.py`) read
exactly `power_kw[0]`/`served_kw[0]` to decide the current on/off state and
discarded the rest, every single cycle.

Fixed by publishing the full series as new attributes on
`sensor.nimbus_<load>_commanded_state` (the sensor #578/#579 already built,
which already carries the load's own device_entity/hold/cap config) --
`plan_forecast` (the standard `{"time", "value"}` shape every other Nimbus
forecast sensor already uses), plus deferrable-only `plan_delivered_kwh_
forecast`/`plan_target_kwh`/`plan_shortfall_kwh`/`plan_earliest_period`/
`plan_deadline_period` and sheddable-only `plan_nominal_kw`. Deliberately did
NOT need to plumb the original `AdequacyLoadConfig`/`SheddableLoadConfig`
objects through from `build_controllable_loads()` -- `apply_commanded_state_
guard()` already reads `subentry.data` directly for the device-dispatch
fields (#578), and the same `data.get(CONF_DEFERRABLE_TARGET_KWH)` plus a
second call to the same `_resolve_hour_to_period_index()` `build_controllable_
loads()` itself uses gets the identical resolved window with zero duplicated
logic risk. Added a new `period_hours_arr` parameter (the one real new
plumbing needed, threaded from `main()`'s own already-computed array) so
cumulative delivered-kWh can be computed correctly against this tiered
grid's own non-uniform period lengths, rather than guessing a single
period-hours constant.

Refreshes every solve cycle regardless of whether `commanded_state` itself
changed -- unlike the change-gated dispatch/write logic, a stale day-ahead
schedule would defeat the entire point. Confirmed this needed the same
`_unrecorded_attributes` treatment nimbus issue #362 already established for
`NimbusHealthReportSensor`'s own per-poll-churning fields (`generated_at`/
`subentry_status`) -- applied it to all seven new attributes up front, rather
than waiting for the recorder-churn bug to actually reproduce live a second
time.

Purely additive: every pre-#581 caller of `apply_commanded_state_guard()`
(and every existing test) invokes it with the old 3-arg signature, and
`period_hours_arr` defaulting to `None` skips all new logic entirely -- a
dedicated test confirms this stays a complete no-op, not just "doesn't
crash." 12 new tests across `load_run_state.py`'s own round-trip/pure-
function coverage, `solver_writer.py`'s wiring, and the sensor's attribute
exposure + recorder-exclusion. Full local stub-based suite: 1544 passed, 13
skipped, zero regressions (689.97s). `ruff check`/`ruff format --check`
clean. `tests/hass_integration/` not runnable locally -- pre-existing,
documented gap (this machine's pinned `homeassistant` package predates
`ConfigSubentry`); only CI's real harness can confirm that suite clean.

## #590: Controllable Load device page gains real schedule/status entities

Sub-issue 1/3 of #589, itself Mark's own real complaint the same morning
reading the #534 heat pump's device page right after #582 removed its error
message: "removed the error message, but I don't know if it is scheduled,
what time and for how long. how much will it cost, what are the forecasts
for temp and power consumption?" The device carried exactly one entity
(`Commanded State: Off`) -- every one of those answers already existed
inside the run-state store (#479) and the plan series (#581), just never
published as anything a person would look at.

Added seven new sensors on the SAME device as Commanded State (per the
issue's own explicit preference for real separate entities, not more
attributes on one sensor): `next_start`/`next_end` (timestamps),
`planned_duration` (h), `planned_energy` (kWh), `delivered_today` (kWh --
#479's own already-sampled field, just not previously top-level),
`target_today` (kWh, deferrable only -- a sheddable load has no daily kWh
target concept in this project's data model), and `status` (the
plain-language line: "scheduled HH:MM-HH:MM", "running", "will miss target
by x kWh" -- the #477 soft-shortfall decision made visible -- "capped
(n/n)", "done" or "done (tank X °C)" when a water_heater/climate
done_entity is configured, "shed x kWh today" for sheddable loads, or
"outside window").

All seven are pure arithmetic over what's already persisted --
`load_run_state.derive_schedule_view()` scans the load's own
`plan_forecast` (#581) for the current-or-next contiguous run above the
on-threshold, reads `plan_delivered_kwh_forecast`'s cumulative series for
a deferrable load's own planned energy (tiered-grid-aware, no new
period-duration plumbing needed), and falls back to integrating the plan's
own power values directly for a sheddable load (no cumulative series to
lean on). No new solver work at all -- every number was already being
computed and discarded every cycle.

**Real refactor along the way**: the water_heater/climate
`current_temperature` read #534 built into `solver_writer.py`'s own
`_evaluate_done_condition()` needed to be reused here for the "done (tank
X °C)" status text, but `solver_writer.py` imports numpy/highspy at module
level -- confirmed live earlier this project (#349) to be unsafe to import
from a plain event-loop context before the first real solve has already
paid that cost once, which a freshly-added device-page sensor's own first
poll can't guarantee. Factored the domain list and the read itself out
into a new, deliberately dependency-free `done_condition.py` that both
`solver_writer.py` and `sensor.py` import directly -- one real
implementation, neither call site pays the other's import cost. Kept
`solver_writer.py`'s own dual-mode (package / bare-top-level-module)
import shape intact via the same try/except pattern already established
elsewhere in that file, confirmed against `test_docs_writer_function_set_
drift.py`/`test_solver_writer_controllable_loads.py`'s own bare-module
import.

24 new tests (`derive_schedule_view`/`_find_current_or_next_run` pure-logic
coverage, `done_condition.py`'s own read, and the seven sensors' entity_id/
device/async_update wiring), full local stub-based suite re-verified clean
(1568 passed, zero regressions). `ruff check`/`ruff format --check` clean.
Released as v0.94.190.

**Deliberately not attempted in this pass**: #591 (cost -- planned kW x
hours x the plan's own blended import price) and #592 (tank-temperature
forecast, groundwork for #481's own full thermal model) -- both explicitly
scoped out of #590's own directive, left for their own passes.
