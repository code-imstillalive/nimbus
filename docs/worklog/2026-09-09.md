## #582: deferrable Controllable Load dropped for its entire active window

Mark's install hit this on the very first live morning of the #534 heat pump as a
real Controllable Load (deferrable, earliest 6am, deadline 4pm, 2 kWh at 0.65 kW,
device entity set from #578). The 05:56 solve (one period before the window
opened) resolved it normally. From the 06:01 solve onward -- every solve for the
rest of the 06:00-16:00 window -- the load was silently excluded entirely:

```
Nimbus: controllable load 'Hot Water Heat Pump' (deferrable) resolved
deadline_period (33) before earliest_period (61) for this cycle's own 'now'
-- skipping until the window resolves normally
```

Root cause, precisely diagnosed in the issue report itself: `_resolve_hour_to_
period_index()` always resolves "the next real occurrence of this hour from
now" independently for each hour field. Once `now` (06:01) passed today's own
6am earliest-hour, the earliest instant rolled forward to TOMORROW 6am, while
the deadline (4pm) stayed today -- `build_controllable_loads()`'s own ordering
guard (`if deadline_period < earliest_period: continue`), written for the
genuine overnight case (earliest 10pm, deadline 6am spanning midnight), then
silently dropped the load for the rest of its own active window -- the exact
opposite of correct behavior, since the window being open is precisely when
deadline pressure needs to apply.

Fixed exactly per the issue's own suggested approach: when the ordering
conflict is detected, check the load's own UNROLLED earliest/deadline instants
for today directly -- if `now` genuinely falls between them, the window opened
earlier today and is still active, so `earliest_period` resolves to "right
now" (0) instead of tomorrow. The pre-existing genuine overnight case (checked
well before it opens) is unaffected -- confirmed with a dedicated regression
test alongside the exact 06:01 repro (using a real `build_tiered_grid()`, not
a synthetic grid, matching the issue's own suggested test) and a same-day-
before-it-opens guard test.

**Known, honestly-scoped remaining gap, not covered by this fix**: an
overnight window where `now` is already INSIDE it (e.g. it's 11pm and the
window opened at 10pm, or it's 3am and the window opened at 10pm the night
before) hits the same underlying "earliest resolves to the wrong day" pattern
via a different path, and this fix's same-day check doesn't catch it either
(today's unrolled earliest/deadline instants don't bracket `now` the same way
for a window that spans midnight). Left open deliberately -- #582 itself only
reported and asked for the same-day case; inventing a fix for the overnight-
in-progress case without a real report or real data to verify against would
be exactly the kind of unrequested scope creep this project's own practice
warns against. Flagged in the CHANGELOG and left for its own future issue if
it turns out to matter on a real overnight-window install.

3 new tests, all passing alongside the existing 64. Full local stub-based
suite re-verified clean. `ruff check`/`ruff format --check` clean. Released
as v0.94.187.

Not merged in this session -- same review discipline as every other PR this
marathon, left for the coordinating session to review and merge.

## #586: quality-scorer oracle no longer rushes a below-floor recovery

Filed as a sub-issue of Mark's own automated 9 Sep day-ahead report (#584),
alongside #585 (scorer scope on the multi-battery install -- see below).

8 Sep started with the pack at 0.0% against its 13% floor (#571, confirmed
real the same day). The oracle's first move in the scorecard: import 5.4 kWh
at 20.2c/kWh at midnight purely to reach the floor, then sit idle for six
hours, when the day's own real cheapest power (4.9c/kWh) arrived at 14:00 --
`j_star` ends up about $1.08 higher than a genuine perfect-foresight cost
would be, regret understated by the same amount, and the 00:00 scorecard row
reads as "the household beat the oracle at midnight," a nonsensical
characterization of the real day.

Root cause: `compute_quality_report()`'s own oracle `build_plan()` call used
the SAME auto-derived `soft_soc_penalty_per_kwh` the LIVE solver correctly
relies on to recover a below-floor SoC promptly (steep by design --
`DEFAULT_SOFT_SOC_PENALTY_MULTIPLIER` times the day's own MAXIMUM real
price) -- exactly backwards for a RETROSPECTIVE oracle, which has no reason
to value promptness at all, only genuine price advantage.

First fix attempt, caught and rejected by this fix's OWN regression tests
before shipping: deriving the penalty from the day's own MINIMUM price
instead of its maximum, still applied every period. Worked out by hand and
confirmed by a failing test -- the penalty accrues PER PERIOD for every
period spent below floor, so even a much lower per-kWh rate still costs far
more than the one-time expensive-but-prompt recovery once enough hours
separate the start of the day from the cheap window (14 hours x 5.2 kWh x
even a "low" $0.50/kWh rate is ~$36, dwarfing the ~$1.05 cost of just paying
20.2c/kWh immediately) -- a lower recurring rate never removes the urgency,
it only raises the bar for how much delay reproduces the same rush. Kept as
a permanent regression guard test
(`test_a_merely_lower_recurring_penalty_still_rushes_to_recover`) so this
same wrong fix can't quietly come back.

Real fix: the auto-derived penalty is completely untouched for the ordinary
case (a battery starting the day AT OR ABOVE its own floor never triggers
the new branch at all -- confirmed byte-identical to before this fix). Only
when the day's own starting condition is already below floor (a fact about
history the oracle had no way to have prevented within the scored window,
not a choice it made) is the penalty relaxed to exactly zero for that one
oracle solve -- the floor stays a real, fully-priced preference on every
other, well-behaved day; this narrowly removes the false "must recover
immediately" pressure precisely in the one case #586 describes.

6 new tests across two levels (direct `build_plan()` comparison proving the
mechanism, and `compute_quality_report()` end-to-end proving the published
`j_star_hourly` no longer shows the early expensive charge), full local
stub-based suite re-verified clean, `ruff check`/`ruff format --check`
clean. Released as v0.94.188.
