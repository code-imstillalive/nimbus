## #919 shipped to `main` (PR #936), and the sensor choice was the whole fix

A deployed install can now answer *"is the ML load forecaster actually beating
naive persistence on my data?"* — which no HACS install, on any household, had
ever been able to answer. `forecast_regret.py` has computed it since #273, but
only ever driven by `reference_benchmark.py` against synthetic scenarios.

**The design published on the issue the night before was wrong, and wrong in the
direction that would have looked like success.** It proposed recovering the
forecast trail from `sensor.nimbus_household_load_total_forecast`'s recorded
state, on the correct observation that its state is `round(load_kw[0], 3)`.

But `solver_inputs/load.py` overwrites `load_kw[0]` immediately before that
publish — #429's live anchor, which is correct and doing its job:

```python
live_load_kw = float(sw.ha_get(whole_house_cross_check_sensor)["state"])
load_kw[0] = max(0.0, live_load_kw)
```

`whole_house_cross_check_sensor` is **the same sensor
`_compute_report_for_window()` uses as its real-load ground truth**. So the
proposed trail is the ground truth echoed back. It would have driven
`j_forecast` onto `j_star` and published near-perfect forecast skill on every
install, forever.

And not as an edge case: a report returns `None` without that sensor
configured, and the anchor fires exactly when it is configured. **The
precondition for computing the metric was the precondition for it being fake** —
100% of installs that could publish it.

Confirmed live before concluding it, three hours of real recorded history:

| time | proposed "forecast" | real load |
|---|---|---|
| 01:40:29 | 0.90 | 0.90 |
| 01:39:25 | 0.91 | 0.91 |
| 01:38:54 | 0.97 | 0.97 |
| 01:37:32 | 0.94 | 0.94 |

Identical to the cent on every row, a few seconds apart.

**The fix is a different sensor.** `whole_house_now_kw` and `summed_18_now_kw`
are both snapshotted *before* the anchor, precisely so #429's cross-check
compares two genuine forecasts, and both are already flattened to recorded
entities. The right one is
`sensor.nimbus_solver_load_whole_house_cross_check_now_kw` — the forecast **of**
the ground-truth sensor, so forecast-of-X against measured-X with nothing to
reconcile. Over the same window it read 1.001–1.052 against a real 0.89–0.97:
real error, ~10% high.

Two deliberate scope decisions, both recorded in the module docstring:

- **Solar is held at its real measured values in every scenario.** Nimbus
  publishes no solar nowcast — Solcast/Open-Meteo do, and their accuracy is not
  this project's to report. Holding solar at truth makes the delta attributable
  to *load* forecast quality alone. The perfect-trail test is what proves this is
  actually wired that way: if solar were not held at truth, a perfect load trail
  would still carry solar-attributable regret and that test would fail.
- **Named `load_nowcast_skill_*` throughout.** The trail measures one-step-ahead
  skill, not the day-ahead forecast the dispatch was built on. Both are real
  questions and they are different ones; the prefix stops anyone comparing it
  against `reference_benchmark.py`'s own day-ahead figure. The naming call was
  taken rather than holding the build another day for it.

A negative `value_add_dollars` publishes plainly rather than being suppressed —
an install where persistence wins deserves to be told.

21 new tests. Full local suite on a clean, unswitched tree: 2685 passed, 14
skipped, 334 subtests, exit 0.

## Measured: persistence has been beating the forecaster (#937)

Checking whether six new attributes risked the 16 KB recorder cap turned up
something much larger. The reference household's install — which runs the
standalone/cron quality writer, the only code path that emits the
`forecast_regret` key — **has been computing the real day-ahead decomposition
since 2026-08-30**, and nobody had read it.

Fourteen scored days: **naive persistence beat Nimbus on 11**, mean
`nimbus_value_add_dollars` **−$0.71/day** (worst −$3.42, best +$0.80).
Roughly −$260/year against "tomorrow looks like today".

Caveats that genuinely matter: it prices the forecast's effect *through the LP*,
not raw accuracy (a lower-MAE forecast can plan worse, since an error at an
expensive hour costs real money and the same error at a cheap hour costs almost
nothing); 14 days spanning heavy solver churn; data ends 09-12; one household.
And it is **day-ahead**, so it is not comparable to #919's new one-step-ahead
number — a nowcast is much easier, and those figures should look considerably
better without the forecaster having improved at all.

Filed as **#937** rather than left in #919, because instrumentation and
forecaster quality are different problems. It also reframes a claim this project
has made freely: that the ML forecaster is what makes Nimbus better than a naive
baseline. On the only install measuring it, over the only window available, it
mostly is not.

Also resolved a provenance question cleanly, which is what made the finding
trustworthy: the native integration's own quality report (current,
`latest_date: 2026-09-15`) has **no** `forecast_regret` key at all, and the key
is written in exactly one place in the repo. So #919's premise was precise, not
approximate.

## #933: a published negative result was wrong

The day before, the near-zero summed-forecast condition was reported as "not
observed", resting on 24 h of raw history and on a belief that only two days of
long-term statistics existed. **Eleven days exist, and the summed 18-circuit
total hit exactly 0.0 on five of them** (08-27 → 08-30 consecutive, plus 09-01,
whose daily *mean* is also only 0.359 kW against 1.0–2.5 kW either side).

Exactly 0.0 is the tell. HA's statistics compiler skips non-numeric states, so
`unavailable` is excluded rather than stored as zero — a recorded minimum of 0.0
means the sensor genuinely published `0.0`, which on the summed path requires
*every* contributing circuit to have taken the `continue` branch. An 18-circuit
household cannot draw exactly nothing.

Raw history for those dates is purged, so the cause is undetermined, and the
**benign reading is the more likely one**: circuits still being added and trained
in late August fail the fetch exactly like circuits that are transiently down,
and 09-01's depressed mean fits "many circuits not reporting yet" rather than a
brief glitch. But the cause changes the expected *frequency*, not the
*reachability* — and "not observed" was the only thing holding the fix back.

Recommended a refinement safer than either variant the issue proposed: gate on
`failed_entities and nonzero_fraction < 0.1` rather than the near-zero test
alone. Otherwise a household adding circuits one at a time would see Nimbus
refuse to plan with no visible reason. Strictly narrower than 10%-alone, strictly
wider than all-failed-alone, and it still catches the 14-of-18 partial case.
Awaiting the household's decision; it changes solve behaviour, so it holds
overnight under #594 regardless.

## #773: candidate 3 does not reproduce

The third proposed cause for `phase2_pin_resolve` returning `Infeasible` — HiGHS
applying `mip_feasibility_tolerance` (1e-6) while a MIP runs and
`primal_feasibility_tolerance` (1e-7) once the model is a pure LP, which the
pinning makes it — **did not reproduce.**

Ten trials driving the real sequence (MIP solve → the actual
`_pin_binaries_to_current_solution()` on `main` → re-solve): five with equality
pairs placed on a feasibility knife edge, five more adding the structure the
first batch lacked, continuous variables already pinned `lb == ub` the way
`grid_export_bounds()` pins a P2P commitment, pushed hard against the linking
bound (`5.999`, `5.99999` against 6.0). Every trial returned `kOptimal` with
`worst_integrality_gap == 0.0`.

Recorded as a negative result rather than left unstated. It does not retire the
candidate — this repo already has a case where six synthetic reproductions failed
and only real household data reproduced the bug — but no cheap local experiment
finds it, and the merged diagnostic still needs a real deploy to discriminate.

diagnostic, #936's #919 scorer) with **no clean release possible**.

PRs #930 (#875) and #931 (#897) are held overnight for the household under

later merge a version *downgrade* on `main`.

So the release waits for those two to land, then ships everything in order. This
is a deliberate exception to the "always cut a release after every merged PR"
rule, recorded here rather than silently skipped — the rule exists because
releases were once silently forgotten.

**It has a real cost worth naming**: the #773 diagnostic's entire value is in
being deployed, since it only reports from an install that actually reproduces
the failure. The version queue is currently what holds up #773's measurement.
