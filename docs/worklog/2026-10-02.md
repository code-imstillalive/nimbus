## The setup guide, rewritten (#1507)

Split into **Part 1 — Basic** (the minimum that produces a real plan) and
**Part 2 — Advanced** (everything else). The shape matters more than the length:
a reader can stop after Part 1 and have a working install.

Part 1's order was chosen from where people actually get stuck:

1. **Create the whole-house Power Signal *before* the Solver wizard.** The wizard's
   required load-forecast field has nothing to offer until that entity exists, so
   skipping it makes the wizard look impossible to finish. This is now its own
   numbered step rather than a remark.
2. **Only 5 fields across the 3 Solver screens are required** — SoC sensor, import
   and export price, solar forecast, load forecast — out of roughly thirty on
   screen. Said explicitly so a reader stops filling in the other twenty-five.
3. **Setting the `number.*` entities is its own step**, because battery capacity
   starts at a **0.1 kWh** placeholder that solves happily and produces a
   completely useless plan with no error and no warning.
4. **A real acceptance test**, built on `sensor.nimbus_solver_lp_status` reading
   `optimal` rather than on `solver_config` reading `configured`, with a
   paste-ready Developer Tools → Template block and a worked example of what a
   healthy install returns.

Field labels, help text, required-field markers and service descriptions were taken
from `translations/en.json` so they match the UI verbatim instead of being
paraphrased.

**Ten screenshots**, all real captures from a live install. `load-controls.png` is
cropped to drop its leftmost column, which carried real costs and earnings; six
further captures were left out entirely rather than committed unused, since an
unused image in a public repo is still public.

## Two entity IDs in the README that do not exist (#1509)

The README's "naming quirk" section claimed every entity carries the `nimbus_load`
domain, citing `sensor.nimbus_load_solver_config` and
`number.nimbus_load_solver_grid_max_export`.

**Measured against a real install: zero entities contain `nimbus_load`.** The
*domain* is `nimbus_load` — hence `nimbus_load.retrain` and the
`custom_components.nimbus_load.*` logger paths — but *entity IDs* are `nimbus_*`.
The README contradicted **its own verify step**, which named
`sensor.nimbus_solver_config` three paragraphs earlier.

### Why no guard caught it, and the hole that is now closed

There are two README guards, and they check **opposite directions**:

| guard | asserts | catches |
|---|---|---|
| `test_readme_entity_references_exist` | the README still **mentions** entities that exist | a rename that leaves the docs silent |
| `test_entities_doc_references_exist` | every ID a doc **names** is real | an ID that never existed |

Only the second catches this class, and **README was excluded from it** — on the
recorded grounds that it *"deliberately shows `nimbus_load`-domain spellings while
explaining that naming quirk, which this check would misread."*

That rationale did not survive being checked. The spellings were simply wrong, so
**the exemption was protecting an error rather than a deliberate spelling.** README
is now in the guarded set, and the guard was verified to bite rather than pass
vacuously: re-injecting `sensor.nimbus_load_solver_config` fails the test, removing
it passes.

### The same guard caught four errors of mine

`test_entities_doc_references_exist` failed #1507's first CI run on four IDs the new
guide named that do not exist — `number.nimbus_solver_{min_soc,max_soc,soh}_percent`
(the real ones are prefixed `battery_`), plus `sensor.nimbus_house_total_power_forecast`,
which was invented to illustrate a naming pattern. **A concrete entity ID in a doc is
a promise that it exists**, so the example was reworded to describe the derivation
without naming one. Fixed against the live install's real entity set and re-run
locally before pushing.

## What Nimbus controls — said out loud (#1508, #1509)

The README had **zero occurrences** of `set_operation_mode`, `set_hvac_mode`,
`turn_on` or "device to command". Its entire framing was *"published as normal HA
sensors so any dashboard, automation or third-party MPC layer can consume it."*

That is true of the battery/inverter path and **not true overall**:
`solver_dispatch/guard.py` commands `switch` (`turn_on`/`turn_off`),
`water_heater` (`set_operation_mode`, `performance`/`eco`) and `climate`
(`set_hvac_mode`) whenever a Controllable Load has a `device_entity` set.

For a public README of software that will switch someone's hot water system and air
conditioner, that was not an acceptable omission. There is now an explicit
what-it-does-and-does-not-control table immediately after the banner, and the three
supported domains are documented where they bite.

The same omission ran through "Understanding the configuration model", which
described **5 subentry types and two concerns** when there are **seven and three** —
Controllable Load and Battery Participant were missing entirely. Its heuristic was
also now actively wrong:

> *"If a subentry doesn't produce a `_forecast` sensor, it's topology metadata."*

True with five types, false with seven, and exactly backwards for the one that
switches hardware. Replaced with the real test: **what consumes the subentry — the
ML engine, the LP solver, or only the diagram.**

## The production record, with numbers rather than adjectives (#1508)

*"Graduated out of observe-only shadow mode"* appeared twice with nothing behind it.
Replaced with a **Proven in production** section carrying the reference household's
real hardware — 2 Sungrow hybrids (**SH25T** and **SH15T**), 2 dual battery stacks =
4 towers, 122.2 kWh usable, 40 kW charge/discharge, 42/40 kW grid, 85.8 % measured
round-trip efficiency, 18 metered circuits — and measured performance: ~1.2 s solve
over a 202-period / 96.3 h horizon, EPR 76.12 % for 1 Oct, P2P rate reached ~28 s
*before* the window.

**On the duration claim.** The README says *"continuously since early September
2026"*, and it is worth recording why that wording rather than a longer one. The
automation entity's first recorded row is **2026-09-05 15:58**, matching the
`116KAT-HA-AI` worklog where PRs #837/#838 created it that day; its last off→on
transition is **2026-09-11 01:20** with no state change since — 21 days continuously
on, 27 since first dispatch. A longer figure was suggested during drafting; it is
not what the recorder or the worklog show, so it is not what went into a public
README.

The single-install caveat was kept and sharpened rather than dropped.

## Licensing hygiene ahead of wider release (#1510, #1512)

`schema/PROVENANCE.md` recorded the upstream repo, pinned commit, date, sha256 and
raw URL for the vendored `telemetry.schema.json` — **everything except the licence
and the copyright holder.** MIT's one real obligation is that the notice travels
with copies.

Which licence took checking rather than assuming. `nem-flex-telemetry` is
**dual-licensed**: `LICENSE-CODE` (MIT, © 2025 Mark Purcell and contributors) and
`LICENSE-DATA` (CC BY 4.0). `LICENSE-DATA` scopes itself explicitly to *"All data
files in `data/` and `site/data/`"*, and the schema lives in `schema/`, so
`LICENSE-CODE` applies. A JSON Schema could plausibly have been read as *data*,
which is why the determination is written down with its reasoning. The upstream file
is `LICENSE-CODE`, not `LICENSE` — the plain path 404s, and chasing that is how the
dual licensing surfaced at all.

#1512 added a Contents list (13 sections, no navigation before, and "Proven in
production" sat at line 743) and an inbound = outbound line stating contributions are
under the project's MIT licence, with **"there is no CLA"** said out loud.

## Process notes worth keeping

**A monitor reported a stale green, and verifying against the head SHA caught it.**
A background watch on #1509 reported *"ALL CHECKS COMPLETE AND PASSING"* — from the
**first** commit's run. The current head had **six checks still in progress**.
Merging on the monitor's word would have been precisely the failure the NEVER CHEAT
directive exists to prevent. Every merge tonight was verified by re-reading
check-runs for the PR's current `headRefOid` immediately before merging.

**One check needed diagnosing rather than waiting out.** #1510's `PR Body Hygiene`
sat `in_progress` for ~30 minutes. Reading the record rather than assuming flaky: it
carried `conclusion=success` and `completed_at` five seconds after it started, its
parent CI workflow run read `status=completed conclusion=success`, and all four
workflow runs for that SHA were complete and successful. A stale `status` field on
one job record, contradicted by its own `completed_at`. Named, then merged — not
assumed.
