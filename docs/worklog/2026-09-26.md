## #773 — located, and every prior theory on it was aimed at the wrong thing

The captured real instance settled it, and the answer was not in HiGHS's search at all.

`nimbus_773_fail_phase2_secondary.mps`, 1,412 integer columns of 12,138, at production's own 60 s per-call limit:

| | status | elapsed | simplex iters | nodes |
|---|---|---:|---:|---:|
| unseeded | Time limit | 60.0 s | 411,903 | **0** |
| unseeded | Optimal | 253.4 s | 1,314,628 | 1,017 |
| **seeded, integral** | **Optimal** | **31.0 s** | **62,816** | **52** |
| integers pinned (pure LP) | Optimal | 0.2 s | 3,193 | — |

**Zero MIP nodes.** Branch-and-bound never begins — the budget is gone before the search starts. Confirmed identical across eight option configurations (default, `solver=ipm`, `presolve=off`, `simplex_strategy=4`, `mip_heuristic_effort=0.5`, `mip_detect_symmetry=off`, `run_crossover=off`, `simplex_scale_strategy=5`), against an LP relaxation that solves the whole continuous problem in **0.6 s / 6,260 iterations**.

So no option that tunes the search could ever have helped. **I was wrong about this twice in one evening** — first that the cost was per-node LP work (~230,000 iterations per node), then that it was cut generation. Both were readings of `nodes=5` from a 180 s run as "the search is slow". At production's actual 60 s budget there is no first node.

### The fix came from the phase sequence, not from the solver

Phase 2's feasible set is phase 1's intersected with the primary-bound row, and phase 1's own optimum satisfies that row **by construction** — the row is built from it. So an integer-feasible point for phase 2 was already in hand when phase 2 started, and **unseeded phase 2 was spending its entire budget failing to rediscover a point the caller was holding.**

Two tiers:

- **tier 1** `_offer_mip_start()` hands phase 2 phase 1's integral point. No weakening of #702's tie-break: a MIP start supplies only an upper bound, the solve still proves optimality.
- **tier 2** `_pin_binaries_to_values()` — if phase 2 still cannot finish, pin phase 1's assignment and run phase 2 as a pure LP.

Tier 2 replaces a **cliff with a step**. Before it, a phase-2 failure discarded the secondary channel *entirely* for the cycle — all four tie-break mechanisms — plus a 5-minute cooldown over which every later cycle also went without them. Tier 2 keeps the primary guarantee exactly and keeps the secondary tie-break for every continuous variable. What it honestly loses is a tie-break expressed purely through *which* binaries are chosen, which is #702's regression — hence tier 2 and not the default.

Pinned from an **explicit capture**, never `h`'s live state: a timed-out phase 2 holds either no solution at all or an unproven node relaxation. `_capture_integral_point()` reads `getSolution()` rather than `h.val()`, which #773's own pin diagnostic already records a standing suspicion about after a MIP solve.

### Validated on BOTH captured instances, not just the one it came from

Done because a fix justified on a single model and never checked against the second available one is the narrow claim this project's own rules warn about. The two files fail *differently*, so the second is a real test.

|---|---|---:|---:|---:|

And one detail that sharpened the diagnosis: this file had been characterised on the issue as the one that *does* find incumbents and cannot close — at **180 s** it reached obj 19.0509 with **595 nodes** and a 1.15% gap. At production's actual **60 s** limit it reports **zero nodes**, exactly like the other file. So that description was true of a 180 s probe and false of the budget production uses. **Both captured instances fail the same way at the real limit.** That is the same correction I already had to make once on this issue, now applying to both files rather than one.

### #999's negative result, explained rather than contradicted

That experiment seeded the LP relaxation's optimum — **fractional**, so HiGHS must repair it via a sub-MIP and on this instance cannot. An **integral** seed is a materially different ask, and the table above is the difference. #999's measurement was sound; the conclusion drawn from it was too broad. Closed on that.

## #1228 — the SoC discrepancy was comparing a mean against an instant

`_soc_discrepancy_stats()` differences `resample_history_nearest(...)` — a **point sample** at `HH:00:00` — against `j_ach_hourly["soc_pct"]`, that hour's **mean**.

The function's own docstring says every comparison point is "genuinely the same real hour on every side". True about **alignment**, and read for a long time as though it settled **comparability**. It does not. Differencing a mean against an instant injects roughly half the hour's ramp rate as artifact, largest where SoC moves fastest.

24 Sep: published **max 21.17 / mean 9.88**, max landing on **hour 12, the steepest charge ramp of the day**, against a like-for-like **max 11.82 / mean 6.46** that passes both thresholds. That artifact alone accounts for `epr_reliable: False` on an install whose sensors are fine.

Fixed on the **achieved** side, via a new `QualityReport.j_ach_soc_pct_at_hour`. Both sides could have been made to match; point-sampling the achieved side is the one that agrees with `resample_history_mean()`'s own documented principle — SoC is a **state**, sampled and held, not a flow to be averaged — and it leaves the real side untouched.

The per-period array is `initial + cumsum(delta)`, i.e. **end-of-period**, so the value at the instant hour *h* begins is the end of the period *before* that hour's first period, and for hour 0 it is the initial SoC. Off by one period there reintroduces a slice of the same artifact in the other direction, so it has its own test — as does the requirement that the new keys match `_hourly_means_by_key()`'s **exactly**, since a key mismatch would make the whole fix silently inert.

`j_ach_hourly["soc_pct"]` stays a mean deliberately: it feeds apexcharts rows where a mean is right to plot, and #356 commits that a ≤24 h window produces byte-identical output. Falls back to the mean when the mapping is absent and publishes **which basis it used** (`soc_discrepancy_basis`) rather than quietly reverting.

**Raised for review rather than treated as settled** — it is a genuine design fork, and averaging the real side would also work at the cost of contradicting that principle.

## #1181 — the home battery's reconstruction had no gap guard, and half a charge window was invented

`_stale_power_period_indices()` (#1161) had exactly **one** call site: the participant path. Every install has a home battery; most have no participants — so on a typical install the guard protected nothing, and the one power series that always exists was unmeasured.

Measured over the 20 Sep charge window: 640 points in 11.0 h, median gap 30.2 s, largest gaps **1777 s (30 min)** and 1456 s, and **5.93 h — 54.0% of the window — inside gaps longer than two minutes**. `resample_history_mean()` holds the last observed value across each gap, so more than half that phase was integrated from a reading last seen up to half an hour earlier.

**Shipped the detection, deliberately not the adjustment.** Zeroing stale periods is conservative for *throughput* but the wrong direction for a *trajectory*: the home reconstruction already under-rises through charge, so zeroing would deepen that, increase `soc_discrepancy`, and make a household's EPR read *less* reliable because of a fix. The same detection wants opposite treatments from its two consumers.

New `_power_history_coverage()`, published as `soc_discrepancy_power_coverage`. Two fractions, and the gap between them *is* the problem: `time_in_long_gaps_pct` is threshold-free by construction (a gap longer than one grid period guarantees a period with no sample of its own), while `stale_periods_pct` is the same permissive **one-hour** measure the participant path acts on. A 30-minute hole is invisible to the second and obvious to the first — pinned as its own test, and it is why a participant-style measure alone would have called this install fine.

Returns `None`, not `0.0`, when there is nothing to measure. "No data" reading as "perfect coverage" is the exact failure this issue is about.

Option 3 — refuse the day above a coverage threshold, in #984's shape — remains the likely endpoint and is **not** done here: a threshold cannot be chosen responsibly while the quantity it would gate on is published nowhere.
