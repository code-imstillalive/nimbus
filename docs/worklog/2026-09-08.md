**#535 (most severe — real dispatch-bookkeeping impact today):**
`_sample_load_run_state()` (#479, the session before) read a Controllable
Load's power sensor's raw state as already being kW, with zero unit

## #534 item 1 — `water_heater`/`climate` done sensors read `current_temperature`

Started on #534 (the real SG-Ready heat-pump HWS feature request, read
in full earlier today but not yet touched). It bundles three asks; only
the first is genuinely independent of already-deferred work: `#480`'s
`_evaluate_done_condition()` could not evaluate a `water_heater`'s own
*state* (`eco`/`performance` — a mode string, not a number) against a
numeric `done_when`, so a household pointing Done sensor at the heat
pump entity directly got nothing — they had to find the device's
separate `sensor.*_current_temperature` helper instead. Fixed by
reading the `current_temperature` attribute (not `state`) whenever the
done entity's domain is `water_heater` or `climate`, and defaulting an
unset Done condition to `>= <the entity's own "temperature" attribute>`
(its live setpoint) rather than the `binary_sensor` "state == on"
default every other domain uses. Same fail-open contract as #480
throughout — real value here specifically, since this device's MQTT
bridge republishes availability roughly hourly, blipping every entity
on it through `unavailable`/`unknown`.

No wizard/config-flow change needed — the Done sensor field's
`EntitySelector` already accepts any domain (deliberately unrestricted,
per its own existing comment). 8 new tests
(`TestEvaluateDoneConditionAttributeDomains`), all 54 tests in
`test_solver_writer_controllable_loads.py` green. Deliberately NOT
touched this pass, both explicitly deferred to their own separate
issues by #534 itself: seeding a thermal-kind load's own
`min_temp`/`max_temp`/`temperature` from the entity (#481, not started
— thermal kind doesn't exist yet), and commanding a `water_heater`/
`climate` load via `water_heater.set_operation_mode` with a per-load
hold/activation cap (needs #484/#486's own still-undelivered per-load
output — no controllable load is actually commanded by Nimbus on any
domain today). Foundation-only in the same sense as #479/#484/#486 —
no release cut for this alone. Released as v0.94.167.

## #538 — SoC-discrepancy reliability was blind to in-range disagreement

Real follow-up from Mark's own Claude Code, found the day after v0.94.166
(#532/#533) shipped: rescoring 7 Sep after his own configured battery
capacity was raised from 100 to 160 kWh flipped `soc_discrepancy_reliable`
(and `epr_reliable`, #533's own new sensor) from false to true, with
NOTHING about the underlying data having changed — the larger capacity
just kept the achieved SoC integration inside [0, 100], the only test
`_soc_discrepancy_stats()` had. The real disagreement against
`sensor.combined_soc` (up to 40.7 points max, 10.85 mean — the #532 root
cause: an unweighted-mean SoC sensor across packs the power sensor
doesn't match 1:1) never went away; the flag just stopped seeing it.

Fixed exactly to Mark's own three-part ask: (1) a second, independent
agreement test — max/mean discrepancy against the real sensor, in
points, now also has to clear a threshold — exposed as two new
dashboard-editable `number.nimbus_solver_soc_discrepancy_max_threshold_pct`
(15)/`_mean_threshold_pct` (8) fields, not a hardcoded constant, per
this project's own standing "every value is a real config field" rule;
(2) `epr_reliable` already mirrored `soc_discrepancy_reliable` exactly
(#533's own design), so it follows the combined verdict for free — only
the WARNING log needed to start naming which test actually failed
(`reason=out_of_range` vs `reason=disagreement`), since a single message
that always read as the out-of-range case would misdiagnose the more
common cause; (3) `soc_discrepancy_reason` (`"out_of_range"` |
`"disagreement"` | `None`) published on the parent report and flattened
onto the Quality sub-device as `sensor.nimbus_quality_soc_discrepancy_reason`.

**A real, independent find while wiring the two new number entities
through**: auditing every existing `number.nimbus_solver_*` field for
the same "live entity exists, but the bridge sensor reads it from stale
entry.options instead" bug class (already twice-documented in this
codebase, 2026-08-23 and 2026-09-02) turned up two more real, live,
pre-existing instances — `solver_fixed_daily_charge` and
`solver_post_window_self_consume_hours` were BOTH missing from
`sensor.py`'s own `_SOLVER_NUMBER_ENTITY_KEYS`/`_SOLVER_ALL_KEYS`
entirely, meaning `fetch_solver_config()` never saw either field's real
value at all. Concretely: any household who ever adjusted "Fixed Daily
Charge" or "Post-Window Self-Consume Hours" from the dashboard had
**zero effect on the actual solve** — both silently kept using their
hardcoded fallback defaults (1.95, 4) forever. Fixed alongside the #538
work, plus a new generic regression test
(`tests/test_sensor_solver_config_keys.py`) that now checks EVERY
`number.py` field against this exact pairing, not just the two new ones
— closing this bug class for good, not just patching the two instances
found today.

17 new tests (8 in `test_sensor_solver_config_keys.py`'s new
