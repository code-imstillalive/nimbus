## #546 — a real regression in #542's own fix, same day it shipped

Mark's own Claude Code verified v0.94.169 live on his install within
minutes of the HACS download (restart 10:22, back 10:24, zero errors,
zero solar-source warnings -- #543's own half genuinely worked) and
found #542's own item 2 (the double-counting dedup) made the plan
*worse*, not just double-counted: on the same real forecasts, next-24h
plan solar dropped from 252.8 kWh (v0.94.168) to 172.4 kWh (v0.94.169).

Root cause, precisely diagnosed in his own report: #542's dedup skipped
the ONE overlapping entity from the auto-include Solcast pair -- but
Solcast's own native `detailedForecast` entity only ever covers ONE
day (today, or tomorrow), so removing the shared entity left the
auto-include fetch reading only the OTHER day. Combined with the
now-working configured source (today only), the blend went from a
healthy 2-member mean (Solcast 2-day + Open-Meteo 8-day, exactly what
v0.94.168 already had, just now shape-correct) to a 3-member mean with
at least one near-zero holdover member every single day --
`resample_forecast()` holds the nearest real point for every grid time
outside a series' own native coverage, and that nearest point is
always close to a dawn/dusk value near zero.

Fixed by moving the dedup from the ENTITY level to the INTEGRATION
level: a new `_is_known_solar_integration_entity()` decides whether a
*configured* source is one of Solcast's/Open-Meteo's own known
entities, and if auto-include is on, that source is skipped as a
standalone member ENTIRELY -- never fetched on its own at all -- since
the auto-include fetch is about to read every one of that integration's
own entities together anyway. This exactly restores v0.94.168's own
two-member blend structure, just with Solcast's shape now correctly
read (the actual, intended effect of #542 item 1). The `skip_entities`
parameter is gone from `fetch_open_meteo_solar_raw()`/
`fetch_solcast_solar_raw()` entirely -- both always read their
integration's FULL entity set now, never a partial one.

Real, immediate lesson for this session: "avoid double-counting" and
"restore correct coverage" are NOT the same requirement, and the
narrower one (entity-level skip) silently violated the wider one
(integration-level coverage) in a way no test caught before shipping --
neither the original #542 unit tests nor CI exercise the actual blend
math end-to-end (main()'s own nested-closure size makes that
prohibitively heavy to mock, matching this file's own established
precedent for testing this exact code path via source-inspection
instead). 5 new tests directly covering
`_is_known_solar_integration_entity()`'s own real decision logic, plus
updated source-inspection tests confirming `skip_entities` is gone and
the new call-site dedup is wired correctly. Ported to the standalone/
cron docs copy too. Released as v0.94.170, deployed to devhub, restart
verified clean -- no new errors, same pre-existing noise only. Devhub
has no Solcast/Open-Meteo entities configured, so this fix's own live
confirmation rests on its unit tests plus Mark's own real install
(where the regression was found and will be re-verified next time his
Claude Code reads the log).

## Real production finding: NUC1's own first day of live dispatch shows LP degeneracy -- fixed properly, not just explained away

Direct household report with a screenshot from NUC1's own live "Nimbus
Dispatch" card (the very automation wired up earlier this same day, see
the 116KAT-HA-AI-side battery-automation work referenced near the top of
this file): battery_kw jumped from -16.2 to -25.9 kW mid-band while the
real import price hadn't actually changed yet (still 3.9c, the drop to
1.3c was a full period later) -- "why is it so dumb?"

Investigated by reading `network.py` directly rather than guessing:
confirmed the LP genuinely has no cost preference for HOW it shapes a
charge schedule within a single flat-price band -- any allocation
delivering the same total kWh at the same price costs exactly the same,
so HiGHS returns one of many equally-optimal vertices, and nothing
picked the smooth one over a jagged one. Also confirmed a real,
already-built mechanism exists for exactly this
(`_add_intraplan_smoothness_penalty`, mechanism 4, added 2026-08-20 --
its own docstring literally documents this exact symptom: "a single
solve's own battery_kw swung -1.25 -> -33.15 -> -0.30 kW ... classic LP
degeneracy, not a real decision") -- but it was ALWAYS passed
`network.py`'s own hardcoded `DEFAULT_SMOOTHNESS_WEIGHT_KW` constant at

## #473: fixed the real test-flakiness bug (not the live restart race above)

Household pointed at #473 next. Read the issue: filed against a genuine CI
flake on PR #472 (a version-bump-only PR, zero Python changes) --
`test_exactly_one_instance_per_push_entity_after_reload` failed once, then
passed clean on an immediate rerun with the same commit. Root cause exactly
as the issue's own analysis suspected: the test's pre/post-reload identity
check compared raw `id()` integers, and CPython's `id()` is just the current
memory address -- once the OLD, correctly-torn-down entity instance is
genuinely garbage collected (the CORRECT outcome of a reload), the allocator
is free to hand that exact address to the NEW instance, making `id(old) !=
id(new)` a false assumption even when reload behaviour is completely
correct.

Fixed per the issue's own suggested direction: replaced the `id()` capture
with `weakref.ref()` on the pre-reload instance, added an explicit
`gc.collect()` after the reload (SensorEntity instances commonly sit in
reference cycles -- e.g. a callback closure holding `self` -- so without a
forced collect a properly-torn-down instance could still be alive as
unreachable cycle garbage for a nondeterministic number of GC generations,
which would make the check flaky in the OTHER direction), then compared the
weakref's dereferenced object via `is` against the live post-reload
instance -- real object-identity comparison, not an address-integer
coincidence. Test-only change; no production entity-registration code
touched. Confirmed this is a genuinely different finding from the live
duplicate-unique_id restart-race event immediately above -- that one is a
real HA-core race under an unusual double-restart operational pattern, not
the CPython `id()`-reuse test fragility this fix addresses; noted explicitly
so a future session doesn't conflate the two.

Local stub-based suite unaffected (this file lives under
`tests/hass_integration/`, which needs the real HA harness -- this repo's
own local Python/homeassistant package is too old to run it locally,
`ConfigSubentry` import fails; confirmed via CI instead, same documented
limitation as this repo's own CLAUDE.md "Testing" section already flags).
`ruff check`/`ruff format --check` clean. Released as v0.94.177.
