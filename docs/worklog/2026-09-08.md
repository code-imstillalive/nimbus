## Mark's live 8 Sep dispatch report — three real findings, all fixed

Mark's own Claude Code posted a full day-ahead dispatch report (#531,
8 Sep 06:10 plan + 7 Sep full-day scorecard) with two real sub-issues
filed, plus a separate, independently-found bug (#535) while
investigating a feature request (#534, still open/unstarted — a
`water_heater` entity integration for Controllable Loads). All three
bugs fixed and shipped as v0.94.166:

**#535 (most severe — real dispatch-bookkeeping impact today):**
`_sample_load_run_state()` (#479, the session before) read a Controllable
Load's power sensor's raw state as already being kW, with zero unit
check — the exact same class of bug this codebase had already found and
fixed once for the Solver's own solar/load/battery quality-report
sensors (`_kw_scale_factor()`). Mark's own real repro: a heat-pump HWS
power sensor reporting 4.6W standby was read as 4.6 kW, so
`currently_on` was permanently true and `delivered_today_kwh` accrued
roughly 1000× too fast. Fixed with the same `unit_of_measurement`
check, read directly off the already-fetched state object (no second
round-trip needed, unlike `_kw_scale_factor()`'s own REST-shaped
caller). Logs once per sensor (#313/#314 discipline) when the
correction actually fires. Real, immediate impact: this bookkeeping
isn't consumed by the LP yet (#479/#480/#484's own documented scope),
but would have become wrong DISPATCH the moment it is.

**#532 (real household data, the concrete case for #467/#418):** a
combined `sensor.combined_battery_power` helper summing the home
battery pack AND a shared EV DC-charger channel feeds a single
`capacity_kwh: 100` model on Mark's real install — more than 100 kWh
moved through it in one calendar day with genuinely complete recorder
history (not the #445 partial-history case `_soc_discrepancy_stats()`
already handles). Exposed `achieved_energy_in_kwh`/
`achieved_energy_out_kwh` on the quality report so a household can
compare against their own configured capacity and tell a history gap
from a sensor covering more physical storage than the capacity
describes, without a manual recorder pull. Deliberately NOT an
automatic cause-classifier — that needs a real recorder-gap detector,
scoped out this pass; the two honest numbers are enough for a human (or
a future check) to draw the same conclusion Mark did by hand. Also
documented the real invariant in `docs/configuration-reference.md`:
the battery power sensor and `solver_battery_capacity_kwh` must
describe exactly the same physical storage, and a combined SoC sensor
must be capacity-weighted, never a plain mean.

**#533:** the EPR headline used to publish a clean-looking percentage
even when `soc_discrepancy_reliable` said the underlying integration
was unreliable — the flag lived only as a parent attribute, invisible
to a consumer reading the flattened EPR sensor alone. Added
`epr_reliable` (named for what it qualifies, same value) right next to
the flattened Quality EPR sensor, plus the three `soc_discrepancy_*`
fields as their own diagnostic entities on the Quality sub-device.
`publish_daily_quality_report()` now logs once per scored day (not
every cycle) when a day's report is unreliable.
