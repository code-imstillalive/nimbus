## v0.94.396 — two IV&V fixes

Mark's PR #1142 merged that morning carrying `xfail(strict=True)` pinning tests for
#1140 and #1141, both still open. That is a deliberate handshake: fixing the bug
makes the test XPASS and **fails CI** until the marker comes off. Both markers are
now gone, so the tests guard the fixes instead of documenting the defects.

**#1140 — the shared-charger widening ignored discharge.**
`_widen_shared_charger_cap_to_achieved()` exists because of #956: narrowing the
scorer's oracle below the trajectory that genuinely happened sends regret negative
and makes the comparison invalid. It computed "the largest simultaneous draw" from
`charge_kw` alone. The live constraint it widens against sums
`charge_vars[m][t] + discharge_vars[m][t]` into one ceiling — physically right,
since one connector's throughput is bounded regardless of direction. So a V2H
participant discharging through the shared charger was **invisible to the
widening**, and the cap could stay narrower than the real combined draw,
reintroducing #956's failure for the discharge case specifically.

Untested, too: the existing pinning test only ever passed zero for discharge. And
the docstring claimed the function measured "the largest simultaneous draw the
group actually made" — what it *should* do, not what it did. Corrected alongside
rather than left for the next reader to re-derive.

**#1141 — the flex signals parent's payload never reached diagnostics.**
`_flex_diagnostics()` never called `hass.states.get()` on
`sensor.nimbus_flex_signals` at all, on the strength of a docstring stating that
entity "carries no payload attributes at all". It does:
`publish_flex_signals()` posts ten scalars (all flattened) **plus**
`battery_signals`, `load_signals` and `generated_at`, none of which are flattened
anywhere. All three were silently absent from every diagnostics download — the
per-battery and per-load breakdown, and the timestamp saying when the snapshot was
taken, which is most of what someone downloading diagnostics to debug flexibility
actually wants.

#116's failure class again, relocated to the **seam** between the two mechanisms
rather than living inside either one.

Fixed by spreading the parent's attributes minus those that already have a
flattened child. **The exclusion is derived from `FLATTENED_ATTRS_FLEX` rather
than hand-listed** — that is the entire point, since a curated allowlist here is
precisely what drifted in #116. Add a flattened row and it drops out for free; add
a parent-only field and it appears for free. The payload is spread *before* the
structural keys, so a future colliding attribute name can never shadow them.

### The wrong docstring claim was not careless, and that is the interesting part

Measured on the dev install, "carries no payload attributes at all" is **true**.
That entity is `unknown` there with only metadata attributes, because flex never
populates on that install. The error was generalising one install's state into a
claim about the code.

Which is also why neither fix could earn a live verification, and the CHANGELOG
says so rather than papering over it: the dev install has no shared-charger group
that discharges, and no flex payload to spread. "Devhub validation: not claimed,
because X" is a first-class answer and was the honest one twice today.

One small thing fell out of the #1141 fix that is worth keeping: the dump now
carries `signals_entity_found` and `signals_state`. On an install where flex never
populates, `signals_state: "unknown"` **self-documents** exactly the situation that
produced the wrong docstring. Had that been in the dump, the claim would have been
visibly install-specific rather than looking like a fact about the code.

## #1120 part 3 — `nimbus_load.rescore_history`

That issue's own last comment calls this "the only substantive item left"; parts 1
and 2 shipped earlier (the per-row version stamp in v0.94.392, and the trend
card's axis clipping).

A day is scored **once**, the morning after, and frozen. Nothing recomputes an
entry, so every scoring-formula change splits the table into two incomparable
halves on the same card. `compute_quality_report()` already scores an arbitrary
window correctly — it *returns* the answer and writes nothing back, so an operator
who knows exactly which row is stale still has no way to fix it.

**A separate service rather than a `persist: true` flag**, which is the choice the
issue leaves open. `compute_quality_report` scores an **arbitrary window**; this
table is keyed by **calendar day**. Persisting a 6-hour or 3-day window would mean
either silently rounding it to a day key — wrong, and invisibly so — or rejecting
most calls. Whole days are the only unit the table can hold.

Design points that each earned a test: day boundaries derived exactly as the daily
scorer derives them (local midnight to local midnight, `allow_partial=False`), so
a rescored row is comparable to an ordinary one; a failed day skipped with its
reason rather than aborting a run in which every prior day cost a MILP; rows
written through `_carry_forward_quality_history()` so a rescored row is stamped
with the release that produced it, preserving part 1; and — the subtle one — if
the rescored day **is** the published day, the headline attributes and state
channel move too, because the "Yesterday" card reads top-level attributes while
the trend card reads `history`, and correcting one without the other *is* the
defect #1120 describes.

**Two of the thirteen new tests were mutation-checked rather than trusted.**
Dropping the headline sync, and letting a raising day abort the run, each fail
exactly the test written for them and restore green. Writing a test that passes
first try is when to check it discriminates.

**The #357 function-set drift guard caught the new public function, correctly.**
It is listed in `INTENTIONAL_NATIVE_ONLY` beside its four quality siblings,
because the docs copy compared against is the **forecast** writer, which carries
no quality machinery at all — quality has its own separate script. The annotation
deliberately does **not** claim the body is native-only in principle, since it
isn't, and says to re-examine if the quality script ever becomes the comparison
target. A factually false annotation there is what that guard's own docstring
warns against.

## #1149 — the gap that made that day unreadable, shipped as v0.94.398

Every figure in the second table came from hand-summing 24 `j_ach_hourly`/`j_star_hourly`
rows, because the quality report publishes **no oracle-side energy totals and no grid
figures for any trajectory**. `fleet_achieved_energy_in_kwh`/`_out_kwh` give the achieved
half; there has never been a counterpart to difference it against.

`energy_decomposition`: four rows (`reference`, `achieved`, `oracle`,
`achieved_minus_oracle`), each `charge_kwh` + `discharge_kwh` + `grid_import_kwh` +
`grid_export_kwh`, built from arrays already in hand where the hourly rows are assembled,
so no extra solve.

Three properties that each earned a test:

- **The achieved row reconciles with the two existing `fleet_achieved_energy_*` fields by
  construction** — same arrays, same hours. Two independently-derived answers to one
  question is drift waiting to happen, so it is asserted rather than assumed.
- **Charge/discharge summed per battery as magnitudes, not from the fleet net.** A fleet
  where one battery charges while another discharges nets those against each other —
  right for a grid identity, wrong for "how much energy moved".
- **The delta row checked against its own two source rows**, not an expected constant.

A real bug the tests caught, fixed in the source rather than the test: `sum()` over an
empty generator returns `int` `0`, so the `reference` row — which passes empty battery
lists by construction — published ints where every sibling row published floats.

The two reconciliation tests and the delta test were **mutation-checked**: pointing the
achieved row at the oracle's arrays fails exactly those three and restoring turns them
green.

## The validation found a bug, which is the point of doing it — v0.94.399

v0.94.398's changelog said devhub validation would *follow* the release rather than
precede it, with a specific reason: the new attribute only appears on a day actually
scored under the release, so a release that merely registers proves nothing. Doing it
surfaced a defect inside a few minutes.

**The gap.** `rescore_quality_history()` keeps the headline in sync with the rescored row
by copying `_QUALITY_HISTORY_FIELDS` — epr, j_ref, j_ach, j_star, regret_dollars.
`energy_decomposition` is deliberately **not** in that tuple: it belongs on top of the
sensor, not inside every history row, which has to stay small enough that a year of rows
fits in one attribute payload.

So it was computed on every rescore and then silently dropped. Observed on a real rescore:
the state and the five fields moved to the rescored day's figures while
`energy_decomposition` still described the **previous** computation. That is exactly the
defect #1120 exists to fix — *"correcting one and not the other would leave them
disagreeing"* — reappearing on a field that postdates the rescore path and was therefore
never part of its sync.

Fixed with a separate `_QUALITY_HEADLINE_ONLY_FIELDS` tuple rather than appending to the
existing one, so the distinction stays visible in the code: that set goes into every row,
this set goes only on top. Five tests, the two that matter mutation-checked.

**Re-verified under v0.94.399** on a real rescore — `rescored_count: 1`,
`latest_date_rescored: true`, row stamped `v: 0.94.399`, and the attribute lands:

```
reference              chg=   0.0  dis=   0.0  imp= 13.588  exp= 48.319
achieved               chg=108.12  dis=103.102 imp= 60.101  exp= 89.815
oracle                 chg=126.701 dis=126.125 imp= 80.386  exp=114.541
achieved_minus_oracle  chg=-18.581 dis=-23.023 imp=-20.285  exp=-24.726
```

Worth stating rather than glossing: **the delta is negative here** — on this install the
oracle moved *more* energy than achieved, the opposite direction from the reference
household's 19 Sep that motivated the issue. Different install, different configuration;
neither is evidence about the other. What the field buys is that the direction is readable
at all.

### Why this one is worth recording beyond "a bug was fixed"

The day's other corrections were all the same species — a claim that looked measured and
was an artifact of how it was looked at. This one is a different and better shape: a
deliberate decision to sequence validation *after* a release, stated in writing with its
reason, which then paid for itself immediately. The alternative — claiming devhub
validation on the strength of "the release deployed and the integration loaded" — would
have looked identical in the changelog and caught nothing.

### Also confirmed on both restarts

The `number.nimbus_solver_*` reset-on-restart bug did **not** fire on either of today's two
devhub restarts: all five hardware limits (122.2 / 40.0 / 40.0 / 42.0 / 40.0) restored

## The quality report had no recorder-cap guard, and its margin is a growth curve

Backlog work, no new activity from anyone. Started from a question about my own
change: `energy_decomposition` (#1149) added an attribute to the quality report, and
#944 documents a mechanism where an oversize attribute payload makes the Recorder drop
**the whole row**. So — did I make that worse?

### Measured before concluding

Real install, 2026-09-20, serialised the way the Recorder measures a state's attributes:

```
                            today (4 days)   at the 60-day cap
RECORDED (native path)           2,386 B          ~8,056 B    49% of cap
FULL (cron / mirror path)       19,139 B         ~24,809 B   151% of cap
```

Two things fell out that neither #944 nor the sensor's own class comment records.

**The quality report is a third sensor affected by #944's mechanism**, and it is worse
placed than the two that issue names. Its row carries `history` — the scored-day table
`nimbus-regret-card.js` treats as authoritative, and the only place EPR/regret history
exists. (Precisely: `_carry_forward_quality_history()` reads the **live** attribute via
`ha_get`, not recorder history, so the table survives and the card works. What is lost is
the recorded history of it, and long-term statistics once the unit goes with the row.)

**And its margin grows.** `history` is trimmed to `_QUALITY_HISTORY_MAX_DAYS` (60) and
that install is four days in, at ~101 B/day. So the overshoot is not a fixed 19 KB — it
heads for ~25 KB, **151% of the cap**, purely from the table filling. The two sensors
#944 already names are static by comparison.

### Checked rather than assumed: it is not firing

Zero `exceed maximum size` warnings for this entity in that install's log, and zero
`Nimbus #944` warnings; the six that do appear are for an unrelated non-Nimbus sensor.
That install publishes the quality report through the **native entity path**, where
`_unrecorded_attributes` applies and only the 2,386 B remainder is ever measured.

So: latent risk for the cron and mirror deployments #944 is about, not a live incident —
and incidentally a positive control for the native path on a third sensor.

### The guard (#1156)

`test_solver_push_attribute_size_budget.py` guards the two flagship Solver sensors
against the #625 shape. The quality report had no equivalent despite having the thinnest
margin in the project.

The design point worth keeping: **the budget is asserted against the projection, not
today's reading.** Scaling the measured per-day history cost to the retention cap is the
difference between a guard that means something and one that stays green for another
eight weeks while measuring something else. Two rules, each with its own
not-passing-vacuously assertion, and mutation-checked — dropping `j_ach_hourly` (4.5 KB)
from the exclusion set fails both and restoring turns them green.

The FULL column is deliberately **not** asserted. It is already over, that is #944's open
structural decision rather than a threshold this repo can set, and a test that fails for
a reason its owner cannot act on is worse than no test.

### On the answer to the original question

No — #1149 did not make this materially worse. `energy_decomposition` is ~400 B against a
projection dominated by a 6 KB history table. But the question was worth asking, and
asking it is what turned up both the third-sensor finding and the growth curve, neither of
which was recorded anywhere.

## Issue 594's step-9 grep, enforced in CI — and the measurement that stopped me shipping the wrong guard

Backlog, nothing new from anyone. Picked #594 (the release-validation practice) because it is
the oldest non-spec open issue and its criteria are concrete.

Reading it in full showed step 9's first half — grep a PR body for a closing keyword before
submitting — was already in CLAUDE.md but only as a **remembered rule**, and the issue's own
record says it *"has now failed four times as a remembered rule and worked twice as a run
command."* That is a gap with an obvious shape: run it where it cannot be forgotten.

### The measurement overturned my own first design

My first instinct — and what both this issue's wording and my own working directive suggest —
was to reject any closing keyword followed by an issue number. Measured the repo's own history
before building it:

```
120  merged PRs scanned
 27  bodies use a closing keyword + number   <- all deliberate and correct
  2  use the POSSESSIVE form                 <- both the incidents on record
```

**Those 27 are how this repo normally closes an issue from a PR.** A guard rejecting them
would have failed 27 compliant PRs — the exact over-tightening #1057's fix already warned
about, after a suggested pattern would have failed 15 truthful CHANGELOG entries.

I would have shipped it. The only reason I did not is that #1057's lesson is written down and
said to measure first.

So the guard matches the possessive and nothing else: **2 of 2 real incidents caught, 0 of 27
legitimate closes rejected**, replayed against all 120 real bodies end-to-end rather than only
against constructed strings. Two near-shapes were measured and excluded on evidence (narrowing
words after the number: zero occurrences; a narrowing clause after a sentence break or dash:
two, neither reported as wrong), each pinned by a test so widening later is a decision rather
than drift.

### Two defects the guard's own construction caught

- Its entry-point test found the script **leaking a file handle**. Fixed in the source, not
  silenced in the test.
- A null PR body would have **passed silently** — indistinguishable from a real pass, which is
  the vacuity failure this repo keeps recording, and which I had written into the job's own
  comment before writing the code that had it. It now reports how much it read. The CI log on
  its own PR says `No narrowed closing keyword found (3300 chars checked)`, which is the proof
  it was not passing on an empty string.

The PR is also its own demonstration: the body discusses the pattern throughout without
containing it, because a post-mortem that quotes the phrase verbatim really would re-close the
issue — the scanner does not care about quotation marks.

### What was deliberately not automated

Step 9's second half — confirm each referenced issue is in the state you intended after
merging — stays a remembered rule. It needs the merged state *plus* the author's intent, and
adding a third guard that looks like it works to a file whose own record is three
guards-that-did-not is a poor trade.

## The scorer can measure its own capacity error — v0.94.407

The whole EPR investigation came down to two configured numbers being wrong, and establishing
that took four days of raw recorder history and a hand-derived argument about which of the
two implied efficiencies moving the same direction means. The obvious question afterwards:
could the scorer have told us?

Yes, for the capacity half, from figures it already publishes.

### The thing that nearly stopped it, and shouldn't have

`battery_energy_balance()` already publishes both implied efficiencies, so the first instinct
was to add the diagnosis there. Its own source comment refuses, correctly:

> within one scored window `measured` is a NET swing, and a window with both directions
> cannot attribute it to either side. Computing k and e from a net would produce a confident
> number out of a quantity that does not contain the answer.

That is exactly why the four-day measurement had to split each day into a monotonic charge
phase first. Reading the comment changed the design rather than being argued around — and the
same comment already said where the answer lives: *"pairing two windows is the caller's job."*

### It needed no new data

Real SoC from `soc_discrepancy_hourly`, achieved power from `j_ach_hourly` — both already on
the report. Driven against the reference household's own 19 Sep report:

```
largest monotonic real-SoC rise : 06:00 -> 16:00, +97.3 pts
charge integrated over it       : 106.49 kWh
implied usable capacity         : 109.4 kWh
```

Against the 107.7 the raw-sample integration gives for that day. **1.6% apart at hourly
resolution, for zero extra recorder reads** — and confirmed live on devhub after deploying:
`measured_usable_capacity_kwh = 109.4`.

### The threshold is where the measurements are

The rise sits in the denominator, so a small one amplifies every error in it: at 50 points a
0.5-point reading error moves the answer 1%, at 5 points it moves it 10% — larger than the
effect. Four real days rose 97.3-98.0 points, so 50 accepts every genuine sweep with margin
and refuses shallow days. Those report `null`, which is an honest absence rather than a
number divided out of a denominator too small to hold one.

### Two mutations, one of which matters more than it looks

Loosening the threshold to 5 points fails the refusal tests. Netting discharge against charge
fails the charge-only test — and that second one guards against reintroducing the precise
net-swing confound the energy balance's comment warns about. Without it, the implementation
could drift back into the shape the design was chosen to avoid, and still pass.

### What it deliberately does not do

Change `solver_battery_capacity_kwh`. That re-prices every future dispatch decision on a live
install. What the household was missing was never the decision — it was the number.

## Auditing my own verification, and finding a hole in it

Twelve releases merged to `main` today. Each was green on its PR branch before merging — all
six jobs checked every time. What I had not checked was whether `main` itself stayed green
across the merges.

### The cause is my own cadence

The pattern all evening: merge the PR, then immediately commit and push the worklog entry.
That second push cancels the in-flight run for the merge commit — GitHub's concurrency

Net effect: for those two releases, the **post-merge full suite on `main` never completed**.

### Resolved, for today

Push the worklog commit **before** merging the PR, or wait for the merge run to finish. Either

## A 59% solve-failure regime on production tonight — and a correction I had to publish

Following the #773 occurrences, I quantified the solve-timeout warnings I had noticed
alongside them. The first analysis was wrong in a way that made a serious problem look like a
tuning detail, and I had already posted it.

### What I got wrong

I read `0.1s / 0.2s / 0.4s / 0.7s` as an **escalating time-limit ladder** — try fast, retry
with more budget — and concluded "the escalation working as designed, most cycles succeed on
the second attempt". It fits the numbers. It is not what the field is.

`solve_seconds = time.monotonic() - solve_started`. That figure is the **elapsed time of a
solve that failed**, not a limit it hit. There is no retry loop; `grep` finds none. The
function's own comment says it two lines up: *"these failures take ~60s (the per-call limit)
against a 0.6s healthy cycle"*.

A plausible story fitted to the shape of the data, published before checking what the number
actually was.

### What the numbers mean once read correctly

A healthy solve on that install reports **1.14s** right now. So 118 failures completing in
**0.1s** are not slow solves giving up — they are failing about ten times faster than a
successful solve completes. HiGHS returns `Unknown` almost immediately rather than working and
running out of road.

```
window               20:30:46 -> 23:13:50   (2.7 h)
failed solve cycles  153
distinct minutes     96 of ~163   (59%)
preceding 4 hours    0
```

**Around 59% of one-minute solve cycles produced no new plan**, each keeping the previous one
— correct per #757's guard, and it means the install dispatched on an increasingly stale plan
for most of a 2.7-hour stretch inside the P2P window. Zero such failures in the four hours
before 20:30, so this is a sharp regime change, not a background rate.

All three `phase2_secondary` failures fall inside that same band, sharing the `status='Unknown'`
signature. I had offered that as a coincidence worth someone checking; with the timing
measured it is stronger than that, and I said so — while still not asserting a cause, because
`n_vars` is only logged on #773's own failures and three samples establish nothing.

### Why the correction went on the issue rather than being quietly amended

The original comment is what someone reads first. A reassuring misreading of a 59%-failure
regime, left standing, is worse than not having commented — and this repo's own record is full
of confident-wrong-number findings that cost more than the bug did.

## Measuring the denominator instead of assuming it — 27%, and a clean two-night control

### Loop iteration after the retraction: a new, measured finding — #1181

| points | 640 in 11.0 h |

### Same iteration, one hour later: #1181's own framing falsified by measurement

#1181 was filed on a single window's coverage figure (54% of the charge window inside gaps
> 2 min) and let that imply a diagnosis of the SoC discrepancy. **Tested across three days,
the implication does not hold**, and a correction was posted before the household read it.

The gap fraction cannot be validated by integrating the gappy series -- circular, and the
move that produced the 43% artifact earlier tonight. The BMS energy counter is dense and
independent, so "how much energy does the configured power sensor fail to account for" is
directly measurable against it. Three consecutive local charge windows:

| local day | BMS dE | SoC pts | implied usable | power-sensor charge | gap >2min | shortfall |
|---|---|---|---|---|---|---|
| 18 Sep | 117.33 | 98.00 | 119.7 | 107.52 | **46.5%** | **8.4%** |
| 19 Sep | 116.57 | 97.30 | 119.8 | 108.15 | **66.6%** | **7.2%** |
| 20 Sep | 116.57 | 97.30 | 119.8 | 109.14 | **54.0%** | **6.4%** |

**Coverage swings 43% relative while the shortfall stays in a 6.4-8.4% band, ordered
INVERSELY.** If held-forward data drove the error the two would move together. They do not.
The gaps are real -- a direct measurement -- but they are not the mechanism. That also
withdraws the candidacy offered for #949's residual, which is unexplained again.

**Two findings survive, both stable, neither about coverage:**

2. **The configured power sensor accounts for less energy than the pack moved, in both

### Stress-testing the one claim that mattered: is the capacity confirmation circular?

All four capacity readings are `combined_battery_charge / SoC`. If that charge sensor were
itself `SoC x capacity`, the confirmation would be circular -- precisely the
two-views-of-one-instrument trap that produced #1172 in the first place, and which had caught
three separate claims already tonight. Worth testing rather than assuming, since the figure
now appears in the source, the CHANGELOG, a test docstring, two issue threads and a release
note.

**It is not derived.** A derived value cannot move while its input is static. On the 20 Sep
charge window `combined_battery_charge` moves by more than 0.05 kWh in **490 of 648 samples
(75.6%) where `logger_battery_level_soc` is unchanged**.

Supporting figure at SoC >= 40%, where 0.1% SoC quantisation is small: implied capacity
**119.882 kWh, stdev 0.132**, against **+/-0.093** explainable by quantisation alone. Real
independent variation, and two instruments agreeing to **0.16 kWh (0.13%)** against the
configured 119.72.

First positive claim of the night to survive its own independence test. Recorded in memory
as done, so it is not re-run.

### Controlled disproof of the gap hypothesis, and a precision fix to a published number

Re-reading what had been published found an imprecision: the charge shortfalls (6.4/7.2/8.4%)
came from `logger_battery_power` (the configured sensor), while the **5.3% discharge figure
quoted in the CHANGELOG, the source comment, the test docstring, the release notes and two
issue threads came from `combined_battery_power`** -- a different sensor. They had been quoted
side by side as if from one instrument.

Measured like-for-like on the same 7h discharge window:

| sensor | points | gaps >2 min | discharge energy | shortfall |
|---|---|---|---|---|
| `logger_battery_power` (configured) | 257 | **67.1%** | **82.56 kWh** | 5.4% |
| `combined_battery_power` | 2122 | **0.0%** | **82.58 kWh** | 5.4% |

**They agree to 0.02 kWh (0.03%).** So the published figure is accurate and the imprecision
turned out not to matter -- but that was luck, not care, and it is recorded rather than
quietly dropped.

**The bigger result is the control it accidentally provides for #1181.** One sensor is held
forward across 67.1% of the window, the other has no gap over 80 seconds, and they land on
the same integral. If interpolating across gaps distorted the result they could not match.
The gaps fall where the signal is steady -- which is exactly why the recorder stored nothing
there. That supersedes the correlation argument from the previous iteration and disproves
this issue's premise under control rather than by association.

It also establishes that the **5.4% shortfall is not sensor-specific**: both power sensors
agree with each other and both disagree with the pack's own energy counter by the same
amount. The disagreement is between the power-measurement plane and the BMS counter.

A story fits the shape -- AC-side measurement reading low on discharge by the conversion loss,
plus a DC-coupled charge path the sensor never sees reading low on charge -- but that is two
free parameters fitting two numbers, which is not evidence, and it is **not asserted**. The
test that would settle it is a charge event with no solar (night-time grid charge), where the
two explanations predict opposite signs. Not looked for yet.

Posted to #1181; option 3 (refuse the day above a coverage threshold) now looks actively
wrong, since it would discard days whose integrals are demonstrably fine.

### The reference instrument was not clean either: the BMS counter re-estimates in steps

Hunting the test named last iteration (a no-solar charge event, to separate an AC-side plane
from an unobserved DC path) found no overnight charging -- but the window it returned broke
the previous iteration's conclusion.

Same sensor, same day, two discharge windows: **5.4% short on the evening window, 44% short
overnight.** Window coverage checked first and ruled out (all three windows covered to 0.01h).
The two-sensor control was run again and BOTH sensors agreed with each other to **0.03 kWh**
on the night window too (10.74 vs 10.71, one with 0.0% gaps) -- so the 44% was real, and the
odd instrument was the counter.

The overnight trace shows why:

```
04:03   charge 15.95 kWh   soc 13.30%
04:12   charge 14.56 kWh   soc 11.80%
04:23   charge  6.57 kWh   soc  5.40%     <- 9.13 kWh in 12 min = ~45 kW sustained
```

Both power sensors saw a 1.79 kW time-weighted mean. A 45 kW sustained discharge did not
happen. SoC and charge fall together -- a **BMS re-estimating near the floor**, energy leaving
the bookkeeping rather than the terminals. Excluding only steps implying >40 kW, the counter
reads -10.59 against the sensors' -10.74: **agreement to 1.4%**.

**So the published "the power sensor under-reads by 5.3%" is not established** -- it treats
the stepping counter as ground truth. Size AND direction of the sensor/counter disagreement
are both now unestablished, and the sensors look like the better-behaved instrument. That
figure sits in `solver_writer.py`'s comment block, the #1172 guard test's docstring, CHANGELOG
v0.94.412 and the release notes; a correction is posted on #1172 and the source text should be
amended with the next real change rather than by cutting a release for a comment at 02:30.

**The v0.94.412 retraction is unaffected and strengthened.** It rests on (1) the quotient
being the wrong quantity -- now worse, since the disagreement is not even a stable fraction
and so cannot be calibrated out -- and (2) capacity confirmed as counter/SoC across four
windows. (2) survives the counter's stepping because SoC and charge step TOGETHER: implied
capacity reads 119.9 before the 04:11 event and 120.6-122.3 after, within ~2% across an event
moving 9 kWh.

Fourth correction of the night, and the same shape each time: a quantity trusted because
several views of one instrument agreed. The counter was the instrument this time.
