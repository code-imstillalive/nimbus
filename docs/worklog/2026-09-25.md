# 2026-09-25

## EPR root-caused after nine previous passes: the nightly score is P2P-blind, and the repair expired at midnight

**One release (v0.94.416), one issue filed (#1200), two PRs merged (#1201, #1202), and the root cause proven by experiment on the reference household's real install rather than argued.**

The household's own framing set the bar: *"epr is totally SHIT... it is 10th time we are at it"* and, later, the sentence that reframed the whole job — *"u always find root cause it just keeps hitting back...."* That second one is the useful half. Nine previous passes each found a real defect and fixed it. The figure kept coming back wrong. So the question worth answering was not "what is wrong with the scorer" but "why does fixing it not stick."

### The move that cracked it: an instrument from a different pipeline

The `feedback_nimbus_stop_daily_release_churn` lesson — *check the record first, cross-check against an independent instrument* — is what worked, and it worked in one step. `sensor.lv_v2_p2p_confirmed_history` carries the real settled LocalVolts revenue, produced by a pipeline with no connection to the scorer:

| day | settled P2P export | volume | EPR published |
|---|---:|---:|---:|
| 20 Sep | **$4.01** | 21.9 kWh | **88.6%** |
| 21 Sep | $14.91 | 49.4 kWh | 51.9% |
| 22 Sep | $12.71 | 57.9 kWh | 38.5% |
| 23 Sep | $13.46 | 50.0 kWh | 36.4% |

**Anti-correlated with the money.** The scorer read worst on the household's best-earning days and read 88.6% on the one day it genuinely under-exported by half. That is not a calibration problem, it is a sign error in what the metric is tracking — and it settled "is this the score or the dispatch?" before a line of the scorer was opened.

It also has a consequence worth stating plainly: **EPR on this install could not have detected a real dispatch failure.** #1179 records 59% of solve cycles failing for 2.7 h inside the P2P window on the night of 20 Sep — the day that scored best.

### Root cause

`quality_report.py:749` — `j_ach = j_ach_residual.total_cost - real_p2p_dollars_earned`.

A day is first scored just after local midnight. Its settlement does not arrive until **~09:00 local the following morning** (confirmed from the settlement sensor's own `last_updated`: 2026-09-23T23:00Z = 24 Sep 09:00 AEST, carrying `latest_date: 2026-09-23`). Until it does, `real_p2p_dollars` is 0 — and that *also* makes the `real_p2p_volume_kwh > 0.01` bonus gate false, so the bonus-priced `grid_oracle` rebuild never runs either. `j_ref`, `j_ach` and `j_star` go P2P-blind **together**, and the day is priced as though the household had no P2P arrangement at all.

#1082 already existed for exactly this, and was genuinely on production (shipped v0.94.380, well before 0.94.413). Its repair is reachable only from inside the `latest_date == yesterday_key` fast path, **so it expires at local midnight.** The production log:

```
2026-09-24 01:00  2026-09-23 was scored before its settlement was available
2026-09-24 02:00-06:00  same, hourly
2026-09-24 06:00  LAST firing
2026-09-24 09:00  settlement for 23 Sep arrives ($13.46)   <- nothing rescores it
2026-09-25 00:00  yesterday_key rolls over; the row is frozen at 36.4%
```

Identical shape on 22 Sep. **Why it stopped at 06:00 is not established.** The 06:00 ML retrain does starve the solve cycle (`previous cycle still in progress -- skipping this tick`, up to 5 consecutive skips) but that burst ends at 06:07, which does not explain silence until midnight. Left on #1200 as an open question rather than given a tidy cause, because this issue's history is tidy causes that did not survive.

### Proven by experiment

The household ran `nimbus_load.rescore_history` with `days: 30` on their own install (command handed over — nothing was executed on either NUC from here, per that repo's absolute rule):

| day | before | after | settled |
|---|---:|---:|---:|
| 21 Sep | 51.9% | **89.8%** | $14.91 |
| 22 Sep | 38.5% | **87.7%** | $12.71 |
| 23 Sep | 36.4% | **87.2%** | $13.46 |
| 24 Sep | 41.6% | 41.6% | none |

`j_ach` moved −12.21 → −21.45, −5.10 → −17.20, −3.40 → −11.93. `regret_dollars` fell $12.75 → $2.69, $13.22 → $2.91, $11.44 → $2.27.

**Two controls, and they are why this is a fix rather than inflation:** 16–20 Sep did not move *at all* (identical to four decimal places on every field), and 24 Sep — the only day whose settlement had not landed — is the only recent day that did not move. **The household's dispatch was ~88–90% the whole time.**

### Three hypotheses killed, two by the household

Recorded because the corrections were more useful than the conclusion.

1. **"The house is empty, so the load regime changed."** The break landed exactly on the household's departure date, which made this very tempting, and it was offered. The household: *"house is not empty and behavious is the same - stop excuses"*, then *"the household is unchanged... its like we are home."* Dropped on the spot. This is the tidy-explanation-that-fits-the-date failure, and following it would have cost the night.
2. **"The fix is merged but not deployed."** #1082 shipped in v0.94.380, long before production's 0.94.413 — found by reading the CHANGELOG properly after the household said *"check all the releases not just 380... that is not right... 413 was the last fix."* Reading one release header and stopping was the error.
3. **"The daily scorer and the rescore path disagree about partial windows."** Refuted by reading the code: both call `_compute_report_for_window(..., allow_partial=False)` (`solver_writer.py:6976` and `:9147`), so #984's coverage guard applies to both equally. The rescore-vs-native axis was a red herring; the settled-vs-unsettled axis was the real one, and they happened to coincide.

### What shipped — v0.94.416

- **`"p"` on a history row** whose figures were computed without settlement. Written only when provisional, self-clearing on re-score, one character. The attribute payload was already measured 27% over #944's 16 KB cap, so correct rows must cost nothing — hence the opposite convention to `"r"`, which is always written. Safe here because the sweep reads an absent key as "nothing to do": a wrongly-absent key costs a missed repair, never a wrong one.
- **`repair_provisional_quality_history()`** — re-scores any *past* flagged row once the real settlement entry is present. **No deadline.** Gated on `_settlement_entry_exists()` so a day whose settlement never arrives costs **zero** solves rather than one MILP per cycle, which would be #773/#757's executor starvation rebuilt on purpose. One day per cycle, oldest first. Checks *presence*, not a non-zero figure, because a settled day of genuinely zero export is a real result.
- **A conditional "Re-score with settlement" button on the Regret card.** Household ask: *"can we actually just add this rescore fix script in a form of a clickable button on the forecaster view next to epr table?"* Built into the card rather than as a dashboard button — it then needs **no lovelace edit at all**, which matters because that dashboard is under manual redesign and carries card-mod highlights that have been lost five times. Shown only when the displayed day is actually waiting; an always-present button invites buying oracle solves on a day that is already correct.
- **`only_dates` on `rescore_quality_history()`**, filtered before the solve, so repairing one row costs one MILP instead of thirty. The alternative was a second copy of the writeback and headline-sync logic — the enumeration defect #1167 recorded four times in two days.

Released together with **Mark Purcell's #949** (PR #1199, merged 23 Sep): the SoC-discrepancy comparison measured a capacity-weighted **fleet** SoC against the **home** battery's sensor alone, which disagrees structurally on any multi-battery install. That is the cause of the reference household's own long-standing `epr_reliable: False / achieved_soc_unreliable:disagreement` flag.

### Process notes

- **The #357 drift guard earned its keep immediately**, refusing the three new functions. Resolved by declaring them native-only *with the reasoning stated*: the standalone/cron FORECAST writer has no quality-report publisher at all, and #1162's own `"r"` field was never ported to the cron QUALITY writer either — so `"p"` follows an established precedent rather than overlooking a port. Writing down which it is was the point.
- **A version bump was deliberately kept out of the feature branch** and cut as its own release PR, per this repo's convention — bundling one is what blocked the release queue on 2026-09-16. The first commit did bundle it; caught and corrected during the rebase.
- **A 25-minute local suite run that overlapped a `git rebase` produced 8 fake failures** in `test_commanded_state_guard_reports_its_own_failure.py`. Re-running on the clean tree gave 9 passed, and CI on a clean checkout had been green all along. Worth remembering: a long local run spanning a rebase reads files mid-rewrite, and its failures mean nothing.
- **The 10-minute GitHub poll caught a real thing**: Mark had merged #1197 and #1199 on 23 Sep, which the local tree did not have. Without that, this work would have been built on a two-commit-stale base and the release would have shipped without his #949 fix.
