## The devhub incident (#773)

The household reported devhub repeatedly crashing, extremely slow, Dev Tools
unreachable, and backups failing. Root-caused live: the lex/calibration phase
`phase2_pin_resolve` was failing 14 times in under 8 minutes on the same install,
each attempt burning a full multi-minute MIP solve (12,245 vars / 1,312 binaries)
before falling back. #773's own existing v0.94.273 fallback correctly avoided a
crash every time — but its comment said "the next cycle retries the full phased
solve normally," and for a *deterministic* failure (the same too-large problem
shape, not a transient) that meant re-attempting and re-failing the same
expensive way on every cycle, forever.

The real damage was second-order: sustained executor-thread starvation. Backups
failed with `Could not lock database within 30 seconds`, HA's own startup phase
couldn't complete (a dozen-plus stuck price-change solve tasks), and the box
self-restarted repeatedly.

Shipped `_lex_calibration_failed_until`, a 5-minute module-level cooldown — once
a phase fails, skip the expensive phased path entirely for a real window rather
than hammering it every cycle. **This bounds the damage; it does not explain the
failure.** Still no local repro. #773 stays open.

Confirmed resolved the next morning by the thing that matters: the *automatic*
backup ran unattended at 05:35 and succeeded (3.8 GB, DB included), having failed
earlier the same night. Zero backup errors in the following 6 hours across three
restarts.

**Real follow-up, unfixed:** even the plain (non-calibrated) solve is
occasionally hitting HiGHS's own 60s per-call limit on this install. Devhub has
32 GB RAM (ruled out as memory-bound), so this points at genuine CPU/compute
capacity against its 38-subentry fixture count. `lp.py`'s own
`_solve_with_options()` docstring already anticipated exactly this — "worth
revisiting if a much larger real MIP ever appears in practice." It has.

## #843 — `resample_history_nearest()` returned samples from the future

Mark Purcell reported the quality report publishing ~1,500 kW of achieved battery
power (SoC to 7,849%) on his real household once EV participants were included —
about 19x the fleet's real ~80 kW physical ceiling, sustained for eight hours,
making EPR/regret unusable. Nimbus's own reliability flags correctly caught it
(`epr_reliable: false`), so this was about the computation, not the warning.

Two distinct bugs, compounding:

1. **A W-vs-kW wake transient.** Mark pulled raw recorder history *with*
   attributes and found the exact row: his EV's pack sensor reports `W` for ~80
   seconds as it wakes from sleep, then switches to `kW`. `_kw_scale_factor()`
   does a single *live-state* unit check and applies one scale to the whole day,
   so that one sample was treated as 1514 kW instead of 1.514 kW.
2. **The smear.** `resample_history_nearest()` — documented as a
   "nearest-at-or-**before**" lookup — always initialised its running value to
   `pts[0][1]`, the chronologically *first* sample. With nothing preceding the
   requested instant the inner loop broke immediately, that value survived, and
   the function returned a reading from *after* the instant asked for, never
   falling through to the `default` its callers passed. The EV slept 00:00→08:51,
   so every hour before the wake inherited that one bad sample.

Shipped the fix for (2). **The naive fix would have been wrong**: setting
`val = default` unconditionally breaks EV SoC reconstruction, because a car that
sleeps through the whole 6h SoC lookback genuinely *did* sit at its wake-up SoC
all night — falling through to `min_soc_pct` would newly corrupt the very
trajectory this issue was about. So backfill is retained as an explicit
`backfill_first=True` opt-in along the FLOW-vs-STATE split
`resample_history_mean()` already documents. All 23 call sites audited
individually: 7 strict, 16 backfill.

**Second instance found in the audit, previously unconnected:**
`_resolve_battery_participant_history()`'s availability mask documents an
explicit "no real history means assume away (0.0)" posture that the old init
silently defeated — a car whose first `binary_sensor` row read `"on"` had every
earlier period masked as home, the exact opposite of the stated intent.

(1) remains open, with three costed options put to Mark (per-row units vs a
physical-plausibility bound against each participant's configured
`max_charge_kw`/`max_discharge_kw` vs both). Note both fetch paths deliberately
strip attributes — `no_attributes=True` natively *and* `&minimal_response` over
REST — so per-row units aren't ignored-but-present, they're not fetched.

## #467 — per-period battery availability mask

`BatteryConfig` could only express availability as a contiguous prefix from
period 0, so "away 09:00–15:00, home either side" was inexpressible and a
two-trip day was impossible.

The real payoff was a correctness gap, not the feature:
`_resolve_battery_participant_history()` already built an `is_home_mask` from the
availability entity's recorded history, used it to zero the reconstruction
arrays, and **discarded it**. The oracle re-solve never saw it — so on any
multi-trip day the two halves of the scorer genuinely disagreed about where the
car was, letting the oracle "charge" an EV that was demonstrably out driving,
inflating its achievable floor and **overstating that participant's regret**.
Same mask now feeds both halves.

Chose a per-period index set over a `from`/`until` pair: a pair handles exactly
one trip and needs redesigning the first time someone does a school run *and* an
evening trip. Composes as a UNION with the existing gates, so `None` is
byte-identical to before.

**Live forward-solve path deliberately left alone.** `build_extra_batteries()`
only sees the availability sensor's *current* state and there's no
forward-looking source until calendar ingestion lands — synthesising a forward
mask from one live reading would fabricate information nobody has.

## Findings worth carrying forward

- **Devhub cannot validate everything, and "deployed, no new errors" is not
  verification.** #843's fix can only be proven against Mark's install — devhub's
  `Test EV` uses synthetic sensors with no sleep gap and never reproduced the
  failure. Likewise #481's ambient-temperature work: devhub's
  `solver_weather_forecast_sensor` is `null` and its thermal loads are synthetic.
- **A real thermal load is running on fallback rates.** Mark's HWS has no
  `controllable_load_power_sensor` (post-#809 there's no wizard field, and a
  `water_heater` entity can't report its own draw), so
  `_async_fetch_thermal_history()` gets nothing, `learn_thermal_rates()` finds no
  segments, and `thermal_rates_source` reads `"fallback"`. #800's learned-rate
  machinery is not actually delivering on the one real thermal load that exists.
  Proposed a `commanded_state × rated_kW` proxy — note the *decay* half needs no
  power signal at all (power only segments idle-vs-heating), so that half would
  be exact, not approximated.
- **Two remaining issues need a platform Nimbus doesn't have.** `PLATFORMS` is
  `[SENSOR, NUMBER, SWITCH]`. #495 needs `region`/`postcode_prefix` (no config
  field exists for either; `region` looks derivable from the spot sensor's
  entity_id but this codebase already fixed that exact hardcoding mistake once)
  and #485 needs `select.nimbus_household_mode`. Both imply a new platform
  module, which is real work and was not previously costed.
- **`main()` is now 1737 lines**, up from the 1646 recorded when #735 was filed
  three days ago — and this session contributed. Mapped the seams: input
  gathering alone is ~67% of it and is the safest extraction, so one move gets
  most of the benefit.
- **GitHub's closing-keyword scanner has no negation awareness** and bit this
  project three more times tonight, including once in a PR body written
  *specifically* to avoid it. Verify with a grep before submitting; don't trust
  "does NOT close #N" to be read as English.
- **Parallel agents duplicate comments.** Two near-identical summaries landed
  seconds apart on both #843 and #467. Collapsed the weaker of each to a pointer
  rather than deleting, preserving the one genuinely better detail from each.
