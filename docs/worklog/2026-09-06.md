## #391 -> regression -> #400: dispatch card landscape layout, three passes

1. **v0.94.126 (#392):** added a `@media (min-width: 900px)` two-column
   layout to `nimbus-dispatch-card-v4`. Closed #391.
2. **v0.94.127 (#395):** regression -- `@media` measures the BROWSER
   VIEWPORT, not the card's own rendered width, which can be much
   narrower behind HA's sidebar/dashboard chrome. Switched to a CSS
   container query (`container-type: inline-size` + `@container`).
3. **v0.94.130 (#402), closing #400:** the container query fired
   correctly, but the right column's grid-track minimum (460px) and its
   own children's real minimum (`table.ftable`, 640px) had never been
   reconciled -- a card between ~900-1020px wide fired two columns with
   too little room for the table. Fixed at the root, not just with new
   numbers: a single `--ftable-min-width` CSS custom property is now the
   one source of truth for both the table's own `min-width` and the grid
   track's minimum, so they structurally cannot drift apart again. New
   breakpoint (1020px) derived by hand from the same real minimums.

## #389 (v0.94.128, #394): solver_writer crash on every infeasible cycle

`solver_writer.main()`'s trailing status-summary print formatted
`plan.total_cost` with `.2f` without checking for `None` first --
crashed on every infeasible plan, 37 consecutive times over 41 minutes
on Mark's live install, skipping every other step in `main()` for the
whole window. Fixed with the same guarded-string pattern already used
two lines above for `cross_check_str`/`coverage_str`.

## #390 (v0.94.130, #401): forecast-driven whole-horizon infeasibility

The real, structural half of the #389 crash's root cause. `grid_import[t]`'s
hard upper bound (`import_limit_kw`) has no slack -- a load the recursive
forecaster extrapolated above `import_limit_kw + max_discharge_kw +
solar_kw` for longer than the battery's own energy could cover made HiGHS
correctly report infeasible over the WHOLE 96h horizon, discarding every
other, perfectly feasible period along with it. Confirmed live: a real
40-minute EV-charging transient held flat overnight by the recursive lag
chain needed ~90kWh of battery support a real pack didn't have -- 46
minutes with no usable plan.

Fixed with a new `grid_import_excess[t]` variable (unbounded, priced at
the real import price plus a heavy penalty -- 10x the peak import price
in the horizon, $5/kWh floor). The LP only reaches for it once
`grid_import[t]` is already pinned at its cap and nothing cheaper can
cover the rest; every normal solve leaves it at exactly 0. Exposed as
`Plan.grid_import_excess_kw` / `Plan.import_cap_breach_kwh`.

This is the Solver-side half of #390 only. The Forecaster-side half
(capping the recursive lag input at the training range so a transient
spike can't propagate as a flat plateau) is not attempted -- separate,
independent fix, still open.

Fixing this exposed two real test fragilities, both fixed as a direct
consequence (not collateral damage):
- `test_solver_rolling.py`'s "genuinely impossible tick" relied on a
  plain oversized load against a zero import cap -- the new slack now
  legitimately serves that (at a real cost) instead of discarding the
  plan. Rewritten to use a physically-impossible `AdequacyLoadConfig`
  deadline instead, the one hard constraint this fix doesn't touch.
  `RollingInputs`/`run_rolling_refinement` gained `adequacy_loads`
  plumbing to support this (`rolling.py` is otherwise dead code, per its
  own module docstring).
- `test_solver_soft_min_soc_constraint.py`'s backward-compat test
  expected a bit-identical SoC trajectory between two runs of a
  genuinely tied LP -- confirmed directly both price out to the
  identical objective, `grid_import_excess_kw` exactly 0.0 in both.
  Adding an inert variable gave HiGHS one more variable to pick an
  equally-optimal vertex over. Updated to assert `total_cost`/real
  energy served instead of the exact per-period array -- bit-identical
  trajectory was never a safe invariant under a genuine LP tie.

## EPR inconsistency (v0.94.129, #398): relayed via Discord, not a GitHub issue

Mark Purcell, via the household directly (not a filed issue at the
time): "EPR is inconsistent between charts and isn't being calculated
correctly" -- his install showed a genuinely negative EPR (-5.8%/-12.0%).
Root cause: `compute_quality_report()` credited leftover end-of-day
battery SoC using a forward-looking $/kWh valuation
(`salvage_value`/`headroom_value`/`terminal_value_breakpoints`) when
scoring the J_ref/J_ach/J_star trajectories -- a forward guess about
tomorrow's own prices this scorer has no honest basis for making, since
tomorrow's own report already values that same carried-over energy from
tomorrow's own real starting SoC. This exact distortion was already
found and fixed once (2026-08-29) in a sibling standalone script's own
local battery config, but never in this shared, canonical
`compute_quality_report()` that every dashboard card and the built-in
daily writer both call into -- so the two could legitimately disagree on
the same real day. Fixed by zeroing terminal-value credit for every
trajectory scored inside `compute_quality_report()` itself
(`battery_scoring = dataclasses.replace(battery, salvage_value=0.0,
headroom_value=0.0, terminal_value_breakpoints=None)`), so every caller
now agrees. Confirmed live post-fix on Mark's own install: `epr_pct:
-5.76` for 2026-09-05 now matches the Regret card's "Yesterday" tile
(-5.8%) instead of disagreeing.

## #388 (v0.94.131, #404): battery power sign convention hardcoded

`docs/dashboards.md` documented `battery_power_entity` as "positive =
discharging," and the card's status logic followed that -- but a
SigEnergy-style install's own real sensor is the opposite convention,
exactly why the Solver already has its own
`solver_battery_power_positive_is_charge` flag (#299/#307). Every
charging period rendered as DISCHARGING (and vice versa), and the 18h
"Actual" history line mirrored against the plan. Fixed via the issue's
own suggested fix #1: a new `_battSign()` helper auto-detects the sign
from that same Solver flag on `sensor.nimbus_solver_config`, applied at
both real consumption points (the live status reading and the raw
history-API fetch). An explicit `battery_power_positive_is_charge`
card-config override (fix #2) is also available as a fallback.
