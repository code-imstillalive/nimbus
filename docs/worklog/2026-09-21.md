# 2026-09-21 — the EPR fix finally reached the household, and Mark's four IV&V findings closed

## The headline: a merged fix is not a delivered fix

The household opened with *"my aim here is ot fix this rotten epr issue ... which
should have been addressed yesterday"*, and they were right.

**Ten EPR releases shipped on 2026-09-20 (v0.94.404–413). NUC1 was running
v0.94.391.** Twenty-two releases behind. Every fix was sitting on `main` doing
nothing for the number the household actually looks at, which still read
**28.61%** with `epr_reliable: None` and `epr_reason: None`.

That is the whole lesson of the day, and it is now in memory as
`reference_nimbus_deployment_model`: **devhub is the test environment, NUC1 is
production and deliberately lags until a build is tested and stable.** Production
lagging is correct by design — but it means "merged" and "delivered" are
different events, and a scorer fix is not delivered until it is on the box AND
the affected days are rescored.

### What the update actually did

Household ran the deploy themselves on NUC1 (commands handed over, nothing
executed remotely — `git pull origin main` + `docker restart
opt_homeassistant_1`), taking it v0.94.391 → **v0.94.413**.

Risk-checked first, because Nimbus is now driving the battery: of the 22
releases, only **v0.94.395** and **v0.94.396** touch the LP, and both are in the
battery-participant / shared-charger path. **This install has no participant
subentries**, so both are inert here. Everything else is scorer, report and
diagnostics.

Then `nimbus_load.rescore_history` with `days: 5`:

| day | EPR before | EPR after | j_ach before | j_ach after |
|---|---|---|---|---|
| 16 Sep | 106.4% (structurally impossible, #956) | **92.1%** | −7.62 | −20.90 |
| 17 Sep | 94.8% | **94.8%** | −24.28 | *unchanged* |
| 18 Sep | 46.8% | **92.1%** | −6.30 | −20.63 |
| 19 Sep | 54.1% | **91.7%** | −2.31 | −17.66 |
| **20 Sep** | **28.6%** | **88.6%** | **−0.51** | **−12.52** |

**The dispatch was never the problem — `j_ach` was.** The old scorer
reconstructed achieved value at −$0.51 for 20 Sep against a true −$12.52, then
reported the shortfall as the household's failure. Regret fell $12.20 → $2.26.

Two controls that say this is a real fix rather than blanket inflation:
**17 Sep did not move at all** (every figure identical), and **16 Sep's
impossible 106.4% came DOWN** to 92.1%. An inflating bug would have done
neither.

## devhub's duplicate entities — the mechanism, now understood

Raised after the v0.94.414 deploy showed 183 ERROR lines. The household explained it across
several messages, and each one corrected my framing:

1. *"devhub has some mirrored or duplicated entities simply due ot the fact how it was set
   up... we tried the clean up but it did not work"* — known, accepted, not a regression.
2. *"it is caused by remote ha connection and these are re-spawning"* — **not** static
   leftovers, as I had first recorded. Actively regenerating.
3. *"respawning means we tried ot clean and delete these but they would just recreate over
   time"* — **deletion has been tried and does not hold.** Nobody should propose it again.
4. *"the connection seems ot create _2 or _3 devices"* — devices as well as entities, matching
   the mechanism 116KAT's CLAUDE.md already documents.

**The practical filter for reading a devhub log**, now recorded in memory: exclude the startup
unique-ID burst, exclude #773's intermittent lex-phase failure, exclude #944's 16 KB
attribute-cap warnings, and judge the release on what remains. On the v0.94.415 deploy that
left **zero**.

### Can it be fixed long term — investigated, read-only

- **Option 1, scope the mirror with filters: already tried by the household.** And
  informative — if filters are in place and duplicates still respawn, entity *count* was never
  the driver; the re-registration is.
- **Option 2, upgrade or upstream fix: dead end.** devhub runs
  `custom-components/remote_homeassistant` **4.6, which is the latest release**. Upstream:
  last release and last commit both **2025-12-04**, nine months ago; 120 open issues; 1,269
  stars. Searched issue titles *and* bodies for "does not generate unique IDs", "duplicate
  entities", respawn/recreate wording — **the symptom is not reported upstream at all**. A fix
  arriving is not something to plan around.
- **What is left**: patch the component locally so its `unique_id` prefix is stable across
  sessions (a fork you then own, and HACS will offer to overwrite it), or replace the mirror
  with ~12 REST sensors defined locally — devhub's Nimbus config references 33 entities, but
  many are Nimbus's own forecast outputs; the genuine external inputs are about a dozen.

**Next concrete step, read-only and not yet done**: read the component's source on devhub and
determine whether that prefix is stable-able at all. That turns "maybe patchable" into a yes
or no, and decides between the two remaining routes. Queued, not started — the household is
travelling.

**Cost to note**: each devhub restart triggers a reconnect, which is what spawns a fresh
duplicate set. A devhub validation is not free, and is not worth running for a release with
nothing to demonstrate.
