## The releases

### v0.94.351 — #1013, State of Health actually derates capacity

`number.nimbus_solver_battery_soh_percent` was a dashboard dial created
in `number.py`, mirrored onto `sensor.nimbus_solver_config`, and **read
by nothing**. The reference household had it at 98% believing it derated
a 122.2 kWh pack; every solve planned against the full 122.2 — roughly
5.7 kWh of headroom that does not exist, on a pack #1012 established
reaches both rails every single day.

`const.py`'s own comment beside the field had documented
`effective_capacity = capacity_kwh * soh_percent / 100` since it was
added. Only the code was missing.

**The one real modelling question was measured, not argued.** #1013 asked
whether SoH should derate the ceiling, the floor, or both. Fourteen
consecutive days of daily statistics, two sensors describing one pack:

```
sensor.combined_battery_charge      max 119.72 kWh   min 2.39 kWh
sensor.logger_battery_level_soc     max 100.0 %      min 2.0 %
sensor.combined_battery_capacity        122.16 kWh, constant
```

The BMS reports 100% at **119.72 kWh, not at the nameplate** — so SoC is
a percentage of the pack's *current usable* capacity, and the nameplate
is not the scale the household's own sensor speaks in. The floor agrees
independently: Min SoC is 2.0% and the daily minimum lands at 2.39 kWh,
which is 2.0% of 119.72 (2.394) rather than of 122.16 (2.443). **Both
rails scale.** Intermediate points sit on the same scale (99.3% ↔ 118.96,
8.9% ↔ 10.69), ruling out two clamps coinciding.

And the configured dial was right all along: 122.2 × 0.98 = 119.756
against a measured 119.72 — **0.03%**.

Also settles one of #1012's three unknowns: real usable capacity is
119.72 kWh, not the 122.16 nameplate and not the 116.50 "health rated"
figure, which is a *third* reference frame the SoC sensor does not use.

### v0.94.352 — #949 made executable, and a retracted value swept

Characterisation tests for the fleet-blended SoC comparison:
`soc_discrepancy_*` measures one sensor (the home battery) against a
fleet-blended reconstruction. The fixture scores a day where every
battery sits perfectly still, so nothing but the blend can move the
number, and it reproduces the issue's own table exactly. Two properties
the table does not show: **the sign flips** (EVs arriving home empty drag
the blend below the home pack), and **magnitude follows capacity share,
not battery count**.

Deliberately not a fix — all three options change a published diagnostic
on live installs.

**The more important half was a correction.** #949's third comment used a
single-battery measurement of 30.46 pt to narrow the fix options. That
figure is `30.9 − 0.44`, where 0.44% is the achieved endpoint #1008
proved fictional. So a retracted value had propagated into a *design
decision*, not merely a diagnosis.

It was the third issue fed by that one endpoint — **#956** (cost side),
**#1001** (export band), **#949** (SoC side) — and each read as
independent corroboration of the others. The first two were corrected at
the time; #949 was never swept. Cross-referenced on #956 so the pattern
is recorded: when a shared upstream value is retracted, the sweep has to
cover every issue that quoted it.

### v0.94.353 — #1015, j_ref now prices P2P the way j_star does

One P2P program reached the three trajectories EPR divides by each other
through three mechanisms: `j_ref` got **nothing** (plain spot), `j_ach`
the real settled lump sum, `j_star` a modelled two-tier bonus.

**The fix is narrower than the issue proposed and right for a different
reason.** #1015 suggested pricing all three identically, which would
replace `j_ach`'s real settled dollars with a model of them — strictly
worse. The principle applied instead: **the two counterfactuals share one
model; the actual keeps its real money.**

The false premise that hid it is worth recording. `quality_report.py`'s
own module docstring claimed plain-spot pricing was *"already exactly
correct"* for `j_ref` because it is *"fully idle — zero export can never
earn a bonus anyway"*. **`j_ref` holds the battery idle. It does not hold
the house idle.** Its grid balance is still `load − solar`, so it exports
solar surplus like any other trajectory. One word, doing all the damage,
in a confident docstring.

Currently a verified no-op on the reference household (solar finishes
~18:00 against a 17:00–24:00 window), which is what the load-bearing test
pins. Longer days break that.

### v0.94.354 — #873, kind=thermal loads finally learn their own rates

Mark's green light (*"Build it"*). The `last_idle_temperature` sampler
and the rate fitter both sat inside the `load_kind == "adequacy"` branch,
so a `kind=thermal` load — the kind named for this — never learned
anything and ran forever on 8.0 °C/kWh and 0.5 °C/h.

**Two earlier attempts failed and both were misread.** Attempt 1's
module-level helper cannot compile — five `F821`s, because
`load_run_state`/`done_condition`/`thermal_forecast`/the `CONF_*` names
are deferred imports local to the guard. Attempt 2 was backed out when 13
dispatch tests reported `len(services.calls) == 0`, read as a production
regression. It was two things, neither of them one:

1. **A harness gap.** `tests/_ha_stubs.py` never exported
   `entity_registry.async_entries_for_device`. Real HA has it; the stub
   did not, because nothing reachable from a stub test had called it
   until #768's registry discovery started running for every load kind.
   The `AttributeError` was swallowed into silent absence — the #1019
   shape, and **only diagnosable because v0.94.350 had raised that
   handler from DEBUG to WARNING hours earlier.**

2. **The placement, wrong in a way nothing catches.** The hoisted block
   *begins* with `if (done_entity and power_sensor ...)`, so putting it
   between the chain's `if` and its `elif` **silently re-parents that
   `elif` onto the hoisted gate**. The adequacy branch then runs only
   when the hoisted condition is false. It parses; ruff passes; mypy
   passes; only behaviour disagrees.

That second trap is the reusable one: **hoisting any block that starts
with `if` into an `if/elif` chain is a silent semantic change with zero
diagnostics.** A test now fails if any statement appears at the chain's
own indent between its members.

### v0.94.356 — #1019's other half, per-load isolation

Every controllable load shared **one** try/except, so a single raise
abandoned the cycle for every load not yet processed. v0.94.350 made that
audible; this makes it survivable.

**A pure re-indent of 839 lines, verified mechanically** — the transform
asserts that dedenting the result by 4 reproduces the original bytes
exactly. That check exists *because* of #873's re-parenting trap: a pure
indent preserves every relative indentation and therefore every branch
parentage, which is why it was chosen over extracting a helper.

The per-load handler names the load; the outer one cannot, because by the
time it runs the frame is gone.

CI then caught a real flaw in the new tests that a local run could not:
which in-memory `Store` stand-in is installed depends on test-module
import order, and both persist across tests, so leftover state left
`commanded_state` already true and dispatch — which only fires on a
transition — never happened. Fixed with per-invocation ids rather than by
clearing one of the two stores.

### v0.94.357 / v0.94.358 — #937's horizon curve, and the bug in shipping it

#937 measured naive persistence beating the ML forecaster on 11 of 14
days (**−$0.71/day**) and asked whether the model's own validation
agrees. The leading suspicion — selection running on one-step MAE — is
**wrong and was already fixed** by #351.

The real gap is arithmetic: `RECURSIVE_VALIDATION_HORIZON_STEPS = 16` at
`RESAMPLE_MINUTES = 15` is **4 hours**, while the forecast is used to 48
and the dollar figure is scored at 24. **The winner is chosen on one
twelfth of the horizon it is chosen for.**

v0.94.357 added `validation_recursive_mae_by_horizon` (16/48/96 steps),
diagnostic only, with two tests pinning that it cannot influence
selection.

**v0.94.358 fixed the bug in v0.94.357**: the value was computed, stored
on `TrainedModel` and threaded into the coordinator — and stopped there.
`sensor.py` maps a fixed set of attribute keys, and a key absent from
that map is never published. **The #1013 class exactly**, shipped about
four hours after #1013 itself was fixed. A second, older instance fell
out of it: `validation_recursive_mae` — the metric that actually decides
`model_type` — had been stored since #351 and published nowhere.

Tests split deliberately: one that the coordinator **exports**, one that
the sensor **publishes**. Exporting is necessary and not sufficient, and
asserting only the first is what let it through.

**Then it produced a result.** Forced retrains on three real circuits:

```
cb_lt_l1    4h: gbrt 0.02203   12h: gbrt 0.03017   24h: naive 0.03554   <-- FLIPS
cb_pw_l1    4h: knn  0.05210   12h: knn  0.05927   24h: knn  0.05192
cb_pw_l2    4h: gbrt 0.02234   12h: gbrt 0.02675   24h: gbrt 0.02349
```

On `cb_lt_l1`, selection picks GBRT at 4 h and **naive persistence beats
it at 24 h** — #937's headline finding appearing inside the model's own
validation, at a horizon the deciding metric never looks at. One of three
flips: not universal, not zero.

It also measures a mechanism this project had asserted for weeks from
theory alone. On `cb_pw_l1`, k-NN is flat across a 6× horizon increase
(−0.3%) while GBRT degrades 49% — the convex-combination-vs-unbounded-
additive-sum argument, confirmed. `cb_pw_l2` is the honest counter-case
where GBRT stays flat too, so the argument predicts a *ceiling* on k-NN,
not that GBRT always degrades.

**Not** an explanation of the −$0.71: three loads, one install,
individual circuits, and the long horizons use 8 origins against
selection's 30.

## Corrections made this session

Recorded together because the pattern matters more than any one of them.

1. **"Devhub's canonical ids resolve to the NUC mirror."** Used twice to
   dismiss a `nimbus_version: 0.94.342` reading. The entity registry says
   `sensor.nimbus_solver_battery_forecast` is `platform: nimbus_load` —
   devhub's own — and the mirror got `_3`. **Ownership is per-entity, not
   per-install**, decided by whichever side registered each id first.

2. **"Devhub went backwards (349 → 342)."** Wrong, and wrong via the
   check just preached: having verified the plan sensor was devhub's own,
   I generalised to the quality report without checking it. That one *is*
   the mirror, so the missing key was NUC1's correct behaviour.

3. **The #949 option ranking**, built on the retracted 0.44% endpoint.

4. **A structural explanation for #773's phase-2 blowup** — that the
   ~1e-7 tie row makes branch-and-bound pathological. Tested against real
   HiGHS on the tie-heaviest scenarios available: synthetic tops out at
   3.1× and *inverts* at the largest size, against production's 21–60×.
   Refuted. The surviving signal is `mip_node_count` — 1 in every
   synthetic phase-2 solve, 5–60 in production.

5. **Over-reading a `nodes=0` timeout** on #773 as a new structural
   failure mode. With `status=Time limit reached` it means the root node
   had not finished, which is the known cost problem hitting the wall.
