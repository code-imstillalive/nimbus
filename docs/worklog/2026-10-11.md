## #1705: the four "frozen" Solver sensors are not frozen

Mark reported `lp_status`, `current_dispatch_direction`, `n_clamped_periods`
and `binding_constraint_now` stuck at their first value after a restart.
Production at 18:14 told two different stories depending on how they were read:

- `/api/states` `last_reported` read 15:45, 15:45, 16:59 and 17:45.
- `states.X.last_reported` read through `/api/template` was 18:10:53 for all
  four, the same second as `solve_seconds`.

HA core does not build a new `State` when a write is unchanged. It moves
`last_reported` on the existing one and fires `state_reported`. But
`as_dict` / `as_dict_json` are cached and not invalidated, so REST, the
websocket and ha-mcp all keep serving the old timestamp, and no history row is
written. Sensors whose value holds still therefore look frozen. Posted to
#1705, with the template check for Mark to run on his install. Not assumed to
match his.

## Night: the 12 Oct spike, the reserve, a tester's frozen plan, v0.94.450

All times AEST. Production was read only (REST and a read-only websocket on
the VIP).

### The spike reaches the plan, and the P2P pin wasted it

The morning check was not needed. By 22:0x the spike was inside LocalVolts'
24 h forecast, and production's plan priced 12 Oct 17:30-20:00 at about
$21/kWh sell. The block pins export to exactly 11.5 kW, so the plan could
not sell more in those hours. It sold its spare energy at 16:30 for 47c
instead: 39.4 kW for half an hour, 100% down to 82%.

**#1724:** while the spike override is armed, a block period whose forecast
import price is at or above the spike threshold keeps the block rate as a
floor, up to the export limit (`spike_export_ceiling` in `solver_plan.py`,
passed as `fixed_export_max_kw`). Replayed through `build_plan` on
production's published 12 Oct inputs, a simplified build without smoothing
or proximal terms:

| | without | with |
|---|---:|---:|
| 16:30 battery | 39.4 kW | 0 |
| 18:00 export | 11.5 kW | 38.7 kW |
| 18:30 export | 11.5 kW | 24.2 kW |
| plan total cost | -750.55 | -1167.98 |

Seven periods widened. The rest of the block stayed at 11.5 kW, and there
was no import excess in either run.

### The soft reserve never reached the solve (#1727)

The household set Reserve 5%, Release margin $0.20, Hold from 00:00,
Release at 05:30. The 22:46 plan still sold 24.8 kW at 05:00 for 10.4c,
down to 2.76%. None of the four reserve settings were in `_SOLVER_ALL_KEYS`,
so `sensor.nimbus_solver_config` never carried them, and
`fetch_solver_config()` read the reserve as 0. That was true on every
install since the reserve shipped. A new test fails if a live setting the
solve reads is missing from the config sensor.
