## #773 — the diagnostic answered, then quieted itself

Yesterday's entry records five hypotheses and five refutations. Today added a
sixth measurement and got a **positive** result.

### The answer

`mip_node_count` and `mip_gap`, added in v0.94.305, resolved it on the first
cycles after deploy:

```
'lex_phase:phase2_secondary' 12.8s  iters=25595  mip_node_count=1  mip_gap=0.0  n_vars=11958
'lex_phase:phase2_secondary' 17.1s  iters=28780  mip_node_count=7  mip_gap=0.0  n_vars=11905
'lex_phase:phase2_secondary'  9.3s  iters=12075  mip_node_count=1  mip_gap=0.0  n_vars=11852
```

**Node count 1, gap 0.0.** The search tree is trivial and optimality is
*proved*, so all 12,000–29,000 simplex iterations land at the **root**.

That makes the 1,134 binaries a red herring — they are resolved at the root, so
every candidate fix aimed at the integer formulation (tighter linking, cuts,
branching priorities, fewer binaries) would move nothing. What is actually left
is an expensive **LP relaxation** on this specific instance.

It also properly closes out hypothesis 4. I claimed "degeneracy/cycling" from a
200k iteration count, then withdrew it on seeing `n_binary=1134` and reframed it
as hard branch-and-bound. **Both were wrong the same way** — I was reasoning
about the integer search, and it was never the integer search.

### The measurement that closed off a whole class of explanation

A synthetic model *larger than production in the dimension that looked
decisive* — 8,800 variables and **4,800** binaries against the real ~11,800 and
**1,134** — solves in **0.2 s at 1,721 iterations**, where the real one runs
157,000–214,000. The fixture carries the full adequacy-load structure,
including the SoC coupling across periods I had initially left out.

So size, binary count and problem shape are all ruled out. Synthesising the
instance has failed, which is the signal to **capture** it rather than
reconstruct it — waiting on Mark, since a model file embeds a household's real
prices and load shape.

### Then the diagnostic was quieted (v0.94.306)

The 5 s line found the cause in a day and then kept firing at WARNING roughly
**once a minute** for a condition nobody can act on. That is exactly the log
noise **v0.94.297** had to clean up for this project's own `#757 diag` lines;
shipping it loud, knowing that, would have been a choice rather than an
oversight.

Now two-tier: every 5 s crossing still measured and logged, at DEBUG. WARNING
reserved for a call that did **not** reach optimal (whatever its duration) or
one past half the per-call limit. Verified live — `#773 diag` at WARNING went
to **zero occurrences**.

### A reading that looked like a fact

`n_controllable_loads: 0` was used as a load-bearing premise **twice** — once to
argue the stall was on a pure LP, once in a call-site elimination table. Both
wrong. The resolution is not a new bug and not the two-process theory:

The install genuinely has six controllable loads, genuinely in the plan (their
`commanded_state` sensors carry real per-load plan data), published **0.3 s
apart in the same cycle by the same process**. The tell was in what the dict was
*missing* — three keys where current code emits seven. That dict is produced by
**pre-v0.94.295** code, which omitted `thermal_loads`; six thermal loads report
as exactly 0 under that version. Meanwhile `lp.py` in the same package is
demonstrably **v0.94.305**. Per-file staleness, logged not chased.

**The generalisable part:** a number that is merely *absent* is easy to
distrust. A number that is *present, plausible and stale* reads exactly like
evidence. What gave it away was not the value but the **shape of the object
around it**.

## #735 — stage 3 pulled forward, because stage 2 could not start without it

`main()` 1,347 → **1,268** lines.

The load-input block stage 2 wants to extract had an `ha_post_state()` call
sitting *inside* it. Moving the block wholesale would have put a publish into an
inputs module and contradicted the very `solver_inputs/` vs `solver_publish.py`
split the issue is building. So the publish was hoisted first — a prerequisite,
not a detour, and stage 3 work that has to happen anyway.

New `solver_publish.py` holds `publish_household_load_total_forecast()`. The
96-line call moved **verbatim**, with only `ha_post_state` and `_cfg_num`
rebound onto the deferred module handle. Fifteen explicit parameters, computed
by walking the call's own AST rather than read off the screen — every blocker
found on #735 so far (#860, #861, stage 2's three traps) was invisible from
reading the code being moved.

### The grep became a test

Until the hoist, the only guard on this publish was source-inspection:
`test_solver_writer_load_total_state_consistency.py` searching the file for
`round(load_kw[0], 3)`. That was the honest choice when the call sat 1,600 lines
deep inside `main()`.

Now it is a function with a signature, so the property is asserted by **calling
it and reading back what it published** — 12 new tests. Strictly stronger: a
grep proves the source *contains* an expression; it cannot notice the
expression sits in a branch that never runs, or that the right expression was
applied to the wrong array.

The property is **#100**: `state` must be `load_kw[0]` *after* the live
cross-check anchor overwrites it, not the pre-anchor `summed_18_now_kw`
snapshot. `test_state_and_forecast_zero_agree` checks the two numbers actually
**match**, which the grep never could.
`test_summed_18_now_kw_is_not_a_parameter_at_all` makes reintroducing the
snapshot a visible API change rather than a one-word edit buried in `main()`.

Same payoff shape as stage 1, which converted text-matched logic into 15
executable behavioural tests.

### Two guard-repointing lessons

- **A source-inspection test whose target moves does not fail — it silently
  stops testing.** The helper now searches both candidate modules and raises
  loudly, naming every file checked, if the publish is in neither.
- **Then I over-applied that fix.** Three `read_text` sites were repointed, but
  one guards a *different* publish — `sensor.nimbus_solver_config`'s cross-check
  diagnostic, which correctly keeps reading the pre-anchor snapshot and stays in
  `solver_writer.py`. Left as-is it would have searched the wrong module and
  quietly asserted nothing. It is now pinned with a comment saying it must not
  use the helper.
