## #773 — the diagnostic answered, then quieted itself

Yesterday's entry records five hypotheses and five refutations. Today added a
sixth measurement and got a **positive** result.

### The answer

`mip_node_count` and `mip_gap`, added in v0.94.305, resolved it on the first
cycles after deploy:

```
'lex_phase:phase2_secondary' 12.8s  iters=25595  mip_node_count=1  mip_gap=0.0  n_vars=11958
'lex_phase:phase2_secondary' 17.1s  iters=28780  mip_node_count=7  mip_gap=0.0  n_vars=11905
'lex_phase:phase2_secondary'  9.3s  iters=12075  mip_node_count=1  mip_gap=0.0  n_vars=11852
```

**Node count 1, gap 0.0.** The search tree is trivial and optimality is
*proved*, so all 12,000–29,000 simplex iterations land at the **root**.

That makes the 1,134 binaries a red herring — they are resolved at the root, so
every candidate fix aimed at the integer formulation (tighter linking, cuts,
branching priorities, fewer binaries) would move nothing. What is actually left
is an expensive **LP relaxation** on this specific instance.

It also properly closes out hypothesis 4. I claimed "degeneracy/cycling" from a
200k iteration count, then withdrew it on seeing `n_binary=1134` and reframed it
as hard branch-and-bound. **Both were wrong the same way** — I was reasoning
about the integer search, and it was never the integer search.

### The measurement that closed off a whole class of explanation

A synthetic model *larger than production in the dimension that looked
decisive* — 8,800 variables and **4,800** binaries against the real ~11,800 and
**1,134** — solves in **0.2 s at 1,721 iterations**, where the real one runs
157,000–214,000. The fixture carries the full adequacy-load structure,
including the SoC coupling across periods I had initially left out.

So size, binary count and problem shape are all ruled out. Synthesising the
instance has failed, which is the signal to **capture** it rather than
reconstruct it — waiting on Mark, since a model file embeds a household's real
prices and load shape.

### Then the diagnostic was quieted (v0.94.306)

The 5 s line found the cause in a day and then kept firing at WARNING roughly
**once a minute** for a condition nobody can act on. That is exactly the log
noise **v0.94.297** had to clean up for this project's own `#757 diag` lines;
shipping it loud, knowing that, would have been a choice rather than an
oversight.

Now two-tier: every 5 s crossing still measured and logged, at DEBUG. WARNING
reserved for a call that did **not** reach optimal (whatever its duration) or
one past half the per-call limit. Verified live — `#773 diag` at WARNING went
to **zero occurrences**.

### A reading that looked like a fact

`n_controllable_loads: 0` was used as a load-bearing premise **twice** — once to
argue the stall was on a pure LP, once in a call-site elimination table. Both
wrong. The resolution is not a new bug and not the two-process theory:

The install genuinely has six controllable loads, genuinely in the plan (their
`commanded_state` sensors carry real per-load plan data), published **0.3 s
apart in the same cycle by the same process**. The tell was in what the dict was
*missing* — three keys where current code emits seven. That dict is produced by
**pre-v0.94.295** code, which omitted `thermal_loads`; six thermal loads report
as exactly 0 under that version. Meanwhile `lp.py` in the same package is
demonstrably **v0.94.305**. Per-file staleness, logged not chased.

**The generalisable part:** a number that is merely *absent* is easy to
distrust. A number that is *present, plausible and stale* reads exactly like
evidence. What gave it away was not the value but the **shape of the object
around it**.

## #735 — stage 3 pulled forward, because stage 2 could not start without it

`main()` 1,347 → **1,268** lines.

The load-input block stage 2 wants to extract had an `ha_post_state()` call
sitting *inside* it. Moving the block wholesale would have put a publish into an
inputs module and contradicted the very `solver_inputs/` vs `solver_publish.py`
split the issue is building. So the publish was hoisted first — a prerequisite,
not a detour, and stage 3 work that has to happen anyway.

New `solver_publish.py` holds `publish_household_load_total_forecast()`. The
96-line call moved **verbatim**, with only `ha_post_state` and `_cfg_num`
rebound onto the deferred module handle. Fifteen explicit parameters, computed
by walking the call's own AST rather than read off the screen — every blocker
found on #735 so far (#860, #861, stage 2's three traps) was invisible from
reading the code being moved.

### The grep became a test

Until the hoist, the only guard on this publish was source-inspection:
`test_solver_writer_load_total_state_consistency.py` searching the file for
`round(load_kw[0], 3)`. That was the honest choice when the call sat 1,600 lines
deep inside `main()`.

Now it is a function with a signature, so the property is asserted by **calling
it and reading back what it published** — 12 new tests. Strictly stronger: a
grep proves the source *contains* an expression; it cannot notice the
expression sits in a branch that never runs, or that the right expression was
applied to the wrong array.

The property is **#100**: `state` must be `load_kw[0]` *after* the live
cross-check anchor overwrites it, not the pre-anchor `summed_18_now_kw`
snapshot. `test_state_and_forecast_zero_agree` checks the two numbers actually
**match**, which the grep never could.
`test_summed_18_now_kw_is_not_a_parameter_at_all` makes reintroducing the
snapshot a visible API change rather than a one-word edit buried in `main()`.

Same payoff shape as stage 1, which converted text-matched logic into 15
executable behavioural tests.

### Two guard-repointing lessons

- **A source-inspection test whose target moves does not fail — it silently
  stops testing.** The helper now searches both candidate modules and raises
  loudly, naming every file checked, if the publish is in neither.
- **Then I over-applied that fix.** Three `read_text` sites were repointed, but
  one guards a *different* publish — `sensor.nimbus_solver_config`'s cross-check
  diagnostic, which correctly keeps reading the pre-anchor snapshot and stays in
  `solver_writer.py`. Left as-is it would have searched the wrong module and
  quietly asserted nothing. It is now pinned with a comment saying it must not
  use the helper.

## #735 stage 2 — the load slice, and why it was not stage 1 again

`main()` 1,268 → **1,118**. Across three stages: ~1,646 → 1,118, a third of
the function gone.

The issue's own staging implies "do what stage 1 did, for load". Measuring the
seam first showed that is wrong in three ways, each of which would have bitten
somebody assuming symmetry:

- **Four inputs, twelve outputs** (solar had three out). A twelve-tuple at the
  call site is unreadable and silently order-dependent, so this stage needed a
  frozen dataclass — a design step stage 1 never required.
- **An earlier count of this seam said eleven outputs.** It missed
  `load_forecast_entities`. An eleven-field result would have left a name
  unresolvable in `main()` afterwards.
- **A grep of the block's module-level dependencies finds 5 names. An AST walk
  finds 14.** The nine a grep misses — `json`, `re`, `urllib.error` and six
  helpers — are each a runtime `NameError` surfacing only on a real solve.
  Third time on this issue that computing beat reading.

### The ordering that must not be tidied

```
summed_18_now_kw = load_kw[0]          <- snapshot BEFORE the anchor
load_kw[0] = max(0.0, live_load_kw)    <- in-place overwrite
```

Both values are carried on the dataclass so no caller reconstructs the wrong
one. Recomputing the snapshot from the returned array *is* #100.

**The pair looks redundant, which is the whole danger.** On most installs the
two are equal — only a configured whole-house cross-check makes them diverge.
That is precisely why `test_the_two_values_genuinely_differ` exists and says so
bluntly: a comment cannot stop a plausible-looking simplification, an assertion
can.

8 new tests pin this **at the source**. The two pre-existing #100 guards both
sit at the publish, so a regression is now caught a layer earlier and does not
depend on the publish being wired correctly.

### Two fixture mistakes, both mine, both the same mistake

Writing those tests I guessed two shapes instead of reading them:

- `cfg["solver_load_forecast_sensor"]` is a **bare subscript**, not `.get()` —
  required even on the per-entity branch that never reads it.
- `sum_load_forecasts()` returns **six** values, not seven, and the error is
  not among them.

Both took seconds to find by running the test, which is the argument for
writing it rather than reasoning about the seam.

### The anti-drift guard did its job

`#357`'s test caught `build_load_arrays` as integration-only and **named its own
remedy** in the failure message — `INTENTIONAL_EXTRACTED_FROM_MAIN`, for a
function top-level only because #735 pulled it out of `main()` while the
docs/cron copy still has the logic inline.

Recorded there with a note that `LoadArrays` never appears in that comparison at
all, because it is a dataclass rather than a `def` — which is itself the reason
stage 2 needed one and stage 1 did not.

### Stage 3 first was not optional

The load block contained an `ha_post_state()`. Moving it while that was still
inside would have put a publish into an inputs module and contradicted the very
`solver_inputs/` vs `solver_publish.py` split being built. Hoisting the publish
first was a prerequisite, and it converted that publish's only guard from a grep
into 12 behavioural tests on the way past.

## #452 completed — and the architectural first that never happened

PR #892, v0.94.309. Mark's answer to the config question was one line:
*"proceed with auto discovery."*

Worth recording how this issue started, because the ending is a good argument
for checking what is installed before designing anything. Its own earlier
scoping concluded:

> this needs a real new fetch mechanism (pull NEMWEB's own `P5_Reports`
> CSV/zip, parse `P5MIN_REGIONSOLUTION`) before the cross-check itself can be
> built — a new external-data integration, not just wiring an existing sensor
> into a comparison.

That would have made Nimbus **the first thing in this codebase to make a direct
outbound HTTP call** — every external source it consumes today is published by
a separate already-installed integration and read as a plain entity. Mark
pointed at `HA_AemoNemData` instead. The feature resolved into two discovered
entities and a pure comparison function, with **no new config surface at all**.

### What shipped

AEMO's own 30-minute forecast against AEMO's own realised 5-minute prices for
the same window — **wholesale against wholesale, so no markup offset term at
all**, unlike the current-interval check that must correct for the household's
retail markup. A different question: is predispatch tracking dispatch?

### Discovery, with two failures this project already paid for

- **Suffix only, never a region.** `const.py` records that hardcoding
  `sensor.aemo_nem_qld1_...` was a real bug a NSW household could never reach.
  A test loops all five NEM regions.
- **Filter unusable states BEFORE counting.** v0.94.300 had to ship exactly
  this correction for #495's discovery after a live deploy found its sole
  candidate reading `unavailable`. Applied here from the start, with a test
  pinning the *ordering* — because the ordering is the fix.

### Two honest properties, stated rather than discovered later

- Weakest in a window's first five minutes (one sample), strongest by minute
  25. `n_samples` is returned and `min_samples` defaults to 1: the caller
  decides, since defaulting higher would quietly discard the early signal.
- **A completed window cannot be scored.** The forecast lives in an entity
  attribute and history fetches pass `no_attributes=True`. Retrospective
  scoring is arguably the more natural reading of Mark's ask, and building the
  in-progress version instead is an approximation — said plainly rather than
  substituted silently.

### Checked rather than assumed

`fetch_solver_config()` returns `state["attributes"]` wholesale, so the
discovered key reaches `cfg` with no known-key list to fall out of. Verified
because **#538** found two `number.*` fields missing from `sensor.py`'s
resolution list — adjusting either from the dashboard had *zero effect on the
solve, silently, forever* — and **#692**/v0.94.283 repeated the shape. Each
time both ends looked right and the connection did not exist.

### A bucket choice, deliberately the uncomfortable one

`#357`'s guard caught the new log-once helper as integration-only. Filed under
`KNOWN_OPEN_DRIFT_INTEGRATION_ONLY`, **not** `INTENTIONAL_NATIVE_ONLY`: it is
portable in principle, so the comfortable label would have quietly retired a
real porting task by mislabelling it. The two buckets mean opposite things —
"nobody should ever port this" versus "nobody has ported this yet".

## #890 filed — the flagship sensors have no long-term statistics

Found by checking #496's own acceptance criterion for the first time.

```
sensor.nimbus_flex_report              19 consecutive hourly buckets
sensor.nimbus_solver_solve_seconds     19 consecutive hourly buckets
sensor.nimbus_solver_battery_forecast  ABSENT ENTIRELY
```

Not a gap — nothing. Probable mechanism links two warnings that look unrelated:
the `forecast` arrays exceed the recorder's 16 KB attribute cap, so the stored
state carries no `unit_of_measurement`, so statistics compilation is suppressed
against the previously-compiled `kW`.

The **control** is what makes it conclusive: an empty result alone would have
been consistent with a malformed query; two siblings returning full series in
the same call rules that out.

Stated as probable, not proven — I have not confirmed HA reads the unit from the
stored state rather than the live one, and named that as the first check.
