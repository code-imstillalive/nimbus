## Findings

- **Time zone (#2007):** `solver_shared.LOCAL_TZ` stayed at its import-time
  `Australia/Brisbane` on every install; `set_native_hass()` updated
  `solver_writer`'s copy only. `_local()` reads `solver_shared`'s, so the local
  hour behind TOU fees, the EV departure hour, day boundaries and P2P
  checkpoints was Brisbane's everywhere (a London install read 12:00 UTC as
  22:00). Brisbane installs unchanged (tested).
- **Open-Meteo timing (#2004, #2005):** the library stores each instantaneous
  reading under the start of its 15-minute step, so `watts[t]` is the power at
  t + 15 min; held from its key, 5-minute periods read it 5-15 min early.
  Checked in the library's source. The reference production install has
  Open-Meteo with auto-include on, so this changes its dispatch: overnight hold.
- **HiGHS time limits (highspy 1.15.1, measured):** a MIP run is limited from
  its own start; an LP run on the same handle by `getRunTime()`, the handle's
  total. Restoring an absolute limit after a long MIP leaves the next LP no
  time (0 iterations) -- devhub's 19:14 and 19:22 errors. Fixed in #2010.
- **Phase-2 speed (#2010):** on 40 synthetic sites shaped like devhub (EV, three
  switchable loads, 202 periods), a 5 s phase-2 budget took the mean solve from
  21.1 s to 12.9 s with the primary cost identical on all 40; the tie-break
  differed slightly on two (+0.08%, +0.05%). Phase 1 is the remaining time; no
  HiGHS option tried made it faster (default fastest or tied, same objective).
- **nan/inf (#2006):** `float("nan")` passed every reader's `except
  ValueError`; four readers now refuse non-finite values.
- **Timestamps without a time zone (#2008):** read as UTC since #363; raised
  with Mark whether to read them in Home Assistant's zone. Measured 2,334 live
  timestamps across the reference install's sources: none without an offset.
